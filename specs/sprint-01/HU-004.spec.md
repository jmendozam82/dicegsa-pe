## Contexto

HU-004 del backlog (`docs/03_BACKLOG.md`, líneas 78-90): como **cualquier usuario** quiero iniciar sesión con correo y contraseña, recibir un JWT y mantener mi sesión con refresh token, para acceder de forma segura a las funciones de mi rol.

**Criterios de aceptación de la HU (backlog):**
1. Login con correo + contraseña; respuesta JWT (60 min) + refresh token (7 días).
2. Bloqueo de cuenta tras 5 intentos fallidos por 15 minutos.
3. Endpoint `/auth/refresh` renueva el JWT sin requerir contraseña.
4. Logout invalida el refresh token activo.
5. Contraseñas almacenadas con BCrypt (coste ≥ 12).

**Decisiones de Jorge que ya aplican (NO reabrir):**
- El **cambio de contraseña en primer login** (consumiendo `requiere_cambio_pwd` de HU-003) **SÍ entra en HU-004** (HANDOFF L199; spec HU-003 Flags #1).
- El **correo de bienvenida/activación** NO entra en HU-004 (HU de Notificaciones, MailKit, Sprint 2).
- `usuario` y `refresh_token` están **fuera de RLS** (verificado: no aparecen en `ENABLE ROW LEVEL SECURITY`, `06_MODELO_DATOS.md` L458-477) → el aislamiento se garantiza por capa de aplicación (TenantMiddleware + claims del JWT + BLL). Revisar en el Sprint de hardening (HANDOFF L156/L159).
- Glosario de roles: `SuperAdmin` (sin `tenant_id`, no cuenta plaza) · `AdminTenant` · `Gerente` · `JefeArea` (HANDOFF L188).
- ADR-003: auditoría JSON con `UnsafeRelaxedJsonEscaping` (aplica a eventos de login/logout/cambio de contraseña).

**Trazabilidad:** RNF-005 (JWT 60 min + refresh 7 días), RNF-010 (BCrypt ≥ 12), RNF-011 (bloqueo 5 intentos / 15 min), RNF-006 (HTTPS), RNF-009 (CSRF/XSS/SQLi), RNF-023 (logging estructurado), RNF-026 (REST + códigos HTTP), RF-003/RF-004 (usuarios y RBAC), SEC-01/02/03/06, ARCH-04/07, STACK-03.

## Alcance de esta HU

1. **100% backend** (API + BLL + DAL + Utility + Middleware), mismo alcance de HU-001/002/003. La UI de login pertenece al frontend MVC (`PE-GOL.Aplicacion`) y se planifica con las HUs de UI (HU-045 y siguientes).
2. **Endpoints de auth:** `login`, `refresh`, `logout`, `cambiar-contrasena` (4 endpoints).
3. **TenantMiddleware + TenantContext:** el JWT alimenta el contexto multi-tenant (SEC-06, ARCH-04) y se cablea `TenantContext.UserId` en la auditoría existente de HU-001/002/003 (el código lo promete: `UsuarioId = null // TenantContext.UserId se cableará con HU-004`).
4. **JWT helper en `PE-GOL.Utility`** (04_ARQUITECTURA § 2 lo declara pero no existe en código) → requiere **ADR-004** (paquete NuGet para generar tokens) — ver Flags #4.
5. **Sin RLS en `usuario`/`refresh_token`/`log_auditoria`** (decisión de Jorge, HANDOFF L156): el aislamiento de auth se garantiza por capa de aplicación. Los endpoints de auth NO filtran por tenant (el correo/token identifica al usuario); el `TenantContext` se propaga para el resto de endpoints.
6. **Fuera de alcance:** correo de bienvenida/activación (Sprint 2, MailKit), UI de login, rate-limiting por IP (hardening), limpieza programada de refresh tokens huérfanos (D7 — ver Flags #7).

## Endpoints

Todos bajo `/api/v1/auth`. `login`/`refresh`/`logout` son `[AllowAnonymous]` (el access token puede estar expirado o no existir aún); `cambiar-contrasena` es `[Authorize]` (cualquier rol autenticado — incl. SuperAdmin, que también tiene `requiere_cambio_pwd=TRUE` en el seed, 06 L592-598).

| Método | Ruta | Auth | Descripción |
|--------|------|------|-------------|
| POST | `/api/v1/auth/login` | AllowAnonymous | Login correo+contraseña. Body: `LoginRequest`. 200 con `LoginResponse` (access token 60 min + refresh token 7 días + usuario) · 401 credenciales inválidas / cuenta bloqueada / usuario inactivo / tenant inactivo · 422 forma inválida. |
| POST | `/api/v1/auth/refresh` | AllowAnonymous | Renueva el access token con el refresh token (rotación D1). Body: `RefreshRequest`. 200 con `RefreshResponse` · 401 token inválido/revocado/expirado/usuario no activo. |
| POST | `/api/v1/auth/logout` | AllowAnonymous | Revoca el refresh token presentado (idempotente — D10). Body: `LogoutRequest`. 200 con `ApiResponse<object>` (Data null). |
| POST | `/api/v1/auth/cambiar-contrasena` | Authorize (cualquier rol) | Cambio de contraseña (primer login y autoservicio). Body: `CambiarContrasenaRequest`. El `usuarioId` sale del JWT (SEC-06), NUNCA del body. 200 · 401 · 422 (actual incorrecta / política débil / igual a la actual). |

**Códigos HTTP posibles:** 200, 400, 401, 403, 404, 422, 500 (wrapper `ApiResponse<T>`, ARCH-07). Nota: 423 no está en el catálogo de ARCH-07 → el bloqueo de cuenta se responde como **401** con mensaje específico (D8).

## DTOs

### Requests

```
LoginRequest
├── correo     string — requerido, email válido, máx 200 (se normaliza trim + LOWER)
└── password   string — requerido, máx 128 (límite anti-DoS de hashing)

RefreshRequest
└── refreshToken  string — requerido

LogoutRequest
└── refreshToken  string — requerido

CambiarContrasenaRequest
├── contrasenaActual  string — requerido, máx 128
└── nuevaContrasena   string — requerido, mín 8, máx 128, al menos 1 mayúscula,
                       1 minúscula y 1 dígito (D4)
```

### Responses

```
LoginResponse
├── accessToken        string
├── refreshToken       string
├── expiraEn           DateTimeOffset   — expiración del access token (NOW + 60 min)
├── refreshExpiraEn    DateTimeOffset   — expiración del refresh token (NOW + 7 días)
├── requiereCambioPwd  bool             — true si el usuario debe cambiar su contraseña (D5)
└── usuario            UsuarioResponse  — reutiliza el DTO de HU-003 (tenantId, rol, areaId, estado, etc.)

RefreshResponse
├── accessToken        string
├── refreshToken       string           — NUEVO token (rotación D1)
├── expiraEn           DateTimeOffset
├── refreshExpiraEn    DateTimeOffset
└── requiereCambioPwd  bool

ApiResponse<T>     (wrapper global, ARCH-07)
PagedResult<T>     (no aplica en auth)
```

> `password`/`password_hash`/`intentos_fallidos`/`bloqueado_hasta` NUNCA viajan en responses (SEC-02). El refresh token viaja UNA sola vez en la respuesta de login/refresh; el cliente lo conserva para las llamadas siguientes (D23 — ver Flags).

## Lógica BLL (paso a paso)

Implementación en `PE-GOL.BLL/Services/AuthService.cs` (interface `IAuthService`) + `PE-GOL.DAL/Repositories/Saas/AuthRepository.cs` (interface `IAuthRepository`). Helper de tokens en `PE-GOL.Utility/Security/JwtTokenHelper.cs` + `JwtOptions` en `PE-GOL.Utility/Security/JwtOptions.cs` (04_ARQUITECTURA § 2: Utility = "JWT helper"). `TenantContext` en `PE-GOL.Utility/Security/TenantContext.cs` (scoped, poblado por `TenantMiddleware`).

**Ctor:** `AuthService(IAuthRepository repository, JwtOptions jwtOptions)` + overload `(..., ILogger<AuthService>? logger)` — patrón de `UsuarioService` (RNF-023). `JwtOptions` se registra como Singleton en IOC, enlazado desde la sección `Jwt` de appsettings (`AccessTokenMinutes=60`, `RefreshTokenDays=7` ya definidos en `PE-GOL.API/appsettings.json` L11-17).

### 1. `LoginAsync(LoginRequest request, CancellationToken ct)`

1. Normalizar `correo` (trim + `ToLowerInvariant()` — patrón D2 de HU-003).
2. **DAL-A1**: `ObtenerUsuarioPorCorreoAsync(correo)` → si `null`:
   - Auditar `LOGIN` fallido (DAL-A10): `Entidad="Auth"`, `usuario_id=NULL`, `tenant_id=NULL`, `valor_nuevo={ correo, resultado:"fallido", motivo:"credenciales_invalidas" }` (ADR-003).
   - Ejecutar un **BCrypt.Verify dummy** contra un hash fijo para mitigar enumeración de usuarios por timing (D16 — ver Flags #8).
   - → `UnauthorizedException` → 401 "Credenciales inválidas".
3. **Estado del usuario** (SEC-03, D8):
   - `estado == "Inactivo"` → auditar `LOGIN` fallido (`motivo:"usuario_inactivo"`) → 401 "El usuario está inactivo. Contacte al administrador."
   - `estado == "Bloqueado"` y `bloqueado_hasta > NOW()` → auditar `LOGIN` fallido (`motivo:"cuenta_bloqueada"`) → 401 "Cuenta bloqueada temporalmente. Intente nuevamente en {minutos} minutos."
   - `estado == "Bloqueado"` y `bloqueado_hasta <= NOW()` → **desbloqueo automático**: `DAL-A8` (intentos=0, bloqueado_hasta=NULL, ultimo_login=NOW()) y continuar.
4. **Tenant activo** (D15): si `tenant_estado == "Inactivo"` (DAL-A1 trae el estado del tenant vía JOIN) → auditar `LOGIN` fallido (`motivo:"tenant_inactivo"`) → 401 "El tenant está inactivo." (SuperAdmin: `tenant_estado` NULL → se omite).
5. **Verificar contraseña**: `BCrypt.Net.BCrypt.Verify(request.Password, usuario.PasswordHash)`:
   - **false** → incrementar intentos (D9):
     - `nuevosIntentos = usuario.IntentosFallidos + 1`.
     - Si `nuevosIntentos >= 5` → **bloquear**: `DAL-A7` con `intentos_fallidos=0`, `estado='Bloqueado'`, `bloqueado_hasta = NOW() + 15 min` (SEC-03). Auditar `LOGIN` fallido (`motivo:"cuenta_bloqueada", intento:5`). → 401 "Cuenta bloqueada temporalmente. Intente nuevamente en 15 minutos."
     - Si `nuevosIntentos < 5` → `DAL-A7` con `intentos_fallidos=nuevosIntentos`, `estado='Activo'`, `bloqueado_hasta=NULL`. Auditar `LOGIN` fallido (`motivo:"password_incorrecto", intento:nuevosIntentos`). → 401 "Credenciales inválidas."
   - **true** → login exitoso:
     - `DAL-A8`: reset `intentos_fallidos=0`, `bloqueado_hasta=NULL`, `ultimo_login=NOW()`.
     - Generar access token: `JwtTokenHelper.GenerarAccessToken(jwtOptions, usuario.Id, usuario.TenantId, usuario.Rol, usuario.AreaId)` — claims `user_id`, `tenant_id` (omitido si null), `rol`, `area_id` (omitido si null); expiración `NOW + AccessTokenMinutes` (SEC-01, 04_ARQUITECTURA § 5).
     - Generar refresh token: `JwtTokenHelper.GenerarRefreshToken()` (32 bytes aleatorios → Base64Url, D13) y persistir **solo su hash SHA-256** (D2): `DAL-A2` con `expira_en = NOW + RefreshTokenDays` (7 días, SEC-01).
     - Auditar `LOGIN` exitoso (DAL-A10): `Entidad="Auth"`, `usuario_id=usuario.Id`, `tenant_id=usuario.TenantId`, `valor_nuevo={ correo, resultado:"exitoso" }` (ADR-003).
     - → 200 `LoginResponse { accessToken, refreshToken, expiraEn, refreshExpiraEn, requiereCambioPwd: usuario.RequiereCambioPwd, usuario: MapToResponse(usuario) }`.
6. **`requiere_cambio_pwd == true`** → la respuesta lleva `requiereCambioPwd=true` y los tokens se emiten igual (D5): el frontend redirige al flujo de cambio de contraseña (endpoint #4). El cambio de contraseña revoca los refresh tokens → fuerza re-login con la nueva contraseña.

### 2. `RefreshAsync(RefreshRequest request, CancellationToken ct)`

1. `hash = JwtTokenHelper.HashRefreshToken(request.RefreshToken)` (SHA-256 hex).
2. **DAL-A3**: `ObtenerRefreshTokenPorHashAsync(hash)` → si `null` → 401 "Sesión inválida o expirada."
3. **Replay detection (D1)**: si `token.revocado == true` → el token ya fue rotado/usado → **revocar TODOS los tokens del usuario** (`DAL-A6`) → 401 "Sesión inválida o expirada."
4. **Expiración**: si `token.expira_en <= NOW()` → 401 "Sesión inválida o expirada."
5. **Usuario activo (D24, defensa en profundidad)**: `DAL-A4` `ObtenerUsuarioPorIdAsync(token.UsuarioId)` → si `null` o `estado != "Activo"` → 401 "Sesión inválida o expirada."
6. **Rotación (D1)**: en una sola transacción:
   - `DAL-A5`: revocar el token presentado (`revocado=TRUE`).
   - `DAL-A2`: insertar el nuevo refresh token (hash, `expira_en = NOW + 7 días`).
   - Commit.
7. Generar nuevo access token (60 min) con los claims del usuario (DAL-A4).
8. → 200 `RefreshResponse { accessToken, refreshToken (nuevo), expiraEn, refreshExpiraEn, requiereCambioPwd }`.
   > El refresh NO se audita (D3): es una operación silenciosa de fondo; auditar cada refresh (cada 60 min por sesión activa) inundaría `log_auditoria`.

### 3. `LogoutAsync(LogoutRequest request, CancellationToken ct)`

1. `hash = JwtTokenHelper.HashRefreshToken(request.RefreshToken)`.
2. **DAL-A3**: buscar el token → si `null` o ya `revocado` → 200 idempotente (no revelar existencia — D10).
3. Si existe y no revocado: `DAL-A5` (revocar) + auditar `LOGOUT` (DAL-A10): `Entidad="Auth"`, `usuario_id=token.UsuarioId`, `tenant_id` del usuario, `valor_nuevo={ resultado:"logout" }` (ADR-003).
4. → 200 `ApiResponse<object>` (Data null, mensaje "Sesión cerrada").

### 4. `CambiarContrasenaAsync(Guid usuarioId, CambiarContrasenaRequest request, CancellationToken ct)`

> `usuarioId` proviene de `TenantContext.UserId` (claim `user_id` del JWT) — SEC-06: NUNCA del body.

1. **DAL-A1b**: `ObtenerUsuarioPorIdConHashAsync(usuarioId)` → si `null` → `NotFoundException` → 404 (defensivo: el usuario autenticado existe).
2. **Verificar contraseña actual**: `BCrypt.Net.BCrypt.Verify(request.ContrasenaActual, usuario.PasswordHash)` → false → `ValidacionException("La contraseña actual es incorrecta")` → 422.
3. **Re-validar política** (fuente de verdad BLL, UX-04): `nuevaContrasena` mín 8, máx 128, al menos 1 mayúscula, 1 minúscula y 1 dígito (D4) → 422.
4. **No reutilizar la actual (D26)**: `BCrypt.Net.BCrypt.Verify(request.NuevaContrasena, usuario.PasswordHash)` → true → 422 "La nueva contraseña no puede ser igual a la actual."
5. `nuevoHash = BCrypt.Net.BCrypt.HashPassword(request.NuevaContrasena, workFactor: 12)` (SEC-02).
6. **Transacción única** (patrón HU-003):
   - `DAL-A9`: `UPDATE usuario SET password_hash=@NuevoHash, requiere_cambio_pwd=FALSE, intentos_fallidos=0, bloqueado_hasta=NULL, updated_at=NOW()`.
   - `DAL-A6`: revocar TODOS los refresh tokens del usuario (fuerza re-login — D14).
   - Auditoría (DAL-A10): `Entidad="Usuario"`, `Accion=UPDATE`, `valor_anterior={ requiere_cambio_pwd: <previo> }`, `valor_nuevo={ requiere_cambio_pwd: false, pwd_cambiada: true }` — serializado con `JsonOpcionesAuditoria` (ADR-003), **nunca el hash**.
   - Commit.
7. → 200 `ApiResponse<object>` (Data null, mensaje "Contraseña actualizada. Inicie sesión nuevamente.").
   > El access token actual sigue válido hasta expirar (≤ 60 min) — los JWT son stateless y no hay blacklist en v1.0 (D14, trade-off documentado).

## Queries DAL

Implementación en `PE-GOL.DAL/Repositories/Saas/AuthRepository.cs` + `IAuthRepository`. Dapper + SQL parametrizado (STACK-03, SEC-05). Las tablas `usuario`/`refresh_token`/`log_auditoria` **no están bajo RLS** (06 L458-477) → sin `WHERE tenant_id` de política; el aislamiento lo garantiza la capa de aplicación (el correo/token identifica al usuario). Parámetros nombrados siempre; `CancellationToken` vía `CommandDefinition` (patrón `UsuarioRepository`).

### DAL-A1 · Obtener usuario por correo (con hash e intentos — SOLO uso interno de auth)

```sql
SELECT u.id, u.tenant_id, u.nombre, u.correo, u.password_hash, u.rol, u.area_id,
       u.estado, u.intentos_fallidos, u.bloqueado_hasta, u.requiere_cambio_pwd, u.ultimo_login,
       t.estado AS tenant_estado
FROM usuario u
LEFT JOIN tenant t ON t.id = u.tenant_id
WHERE LOWER(u.correo) = LOWER(@Correo);
```
> ⚠️ ÚNICA query de auth que lee `password_hash` (junto con DAL-A1b): el hash NUNCA sale del DAL-BLL (SEC-02/ADR-003). `tenant_estado` es NULL para SuperAdmin (sin tenant) → la BLL omite la validación de tenant (D15).

### DAL-A1b · Obtener usuario por id (con hash — para cambiar-contrasena)

```sql
SELECT id, tenant_id, nombre, correo, password_hash, rol, area_id, estado,
       intentos_fallidos, bloqueado_hasta, requiere_cambio_pwd, ultimo_login
FROM usuario
WHERE id = @Id;
```

### DAL-A2 · INSERT refresh_token (persiste el HASH del token)

```sql
INSERT INTO refresh_token (usuario_id, token, expira_en)
VALUES (@UsuarioId, @TokenHash, @ExpiraEn)
RETURNING id;
```
> El DDL (`06_MODELO_DATOS.md` L100-108) define la columna `token TEXT NOT NULL UNIQUE` — se persiste el **hash SHA-256 hex** del token (D2), no el token en claro. El UNIQUE aplica al hash (único por construcción). Sin migración.

### DAL-A3 · Obtener refresh token por hash

```sql
SELECT id, usuario_id, token, expira_en, revocado, created_at
FROM refresh_token
WHERE token = @TokenHash;
```

### DAL-A4 · Obtener usuario por id (sin hash — para refresh)

```sql
SELECT id, tenant_id, nombre, correo, rol, area_id, estado, requiere_cambio_pwd, ultimo_login
FROM usuario
WHERE id = @Id;
```

### DAL-A5 · Revocar refresh token por hash

```sql
UPDATE refresh_token
SET revocado = TRUE
WHERE token = @TokenHash
  AND revocado = FALSE
RETURNING id;
```

### DAL-A6 · Revocar TODOS los refresh tokens del usuario

```sql
UPDATE refresh_token
SET revocado = TRUE
WHERE usuario_id = @UsuarioId
  AND revocado = FALSE;
```
> Mismo SQL que DAL-U9 (HU-003) — se duplica en `AuthRepository` para mantener el repo de auth autocontenido (patrón establecido: cada repo tiene su propio `InsertLogAsync`).

### DAL-A7 · Registrar intento fallido (o bloqueo)

```sql
UPDATE usuario
SET intentos_fallidos = @Intentos,          -- 0 si se bloquea (D9)
    bloqueado_hasta   = @BloqueadoHasta,    -- NOW()+15min si se bloquea; NULL si no
    estado            = @Estado::estado_usuario,  -- 'Activo' | 'Bloqueado'
    updated_at        = NOW()
WHERE id = @Id
RETURNING id;
```

### DAL-A8 · Registrar login exitoso / desbloqueo

```sql
UPDATE usuario
SET intentos_fallidos = 0,
    bloqueado_hasta   = NULL,
    ultimo_login      = NOW(),
    updated_at        = NOW()
WHERE id = @Id
RETURNING id;
```

### DAL-A9 · Cambiar contraseña

```sql
UPDATE usuario
SET password_hash       = @NuevoHash,
    requiere_cambio_pwd = FALSE,
    intentos_fallidos   = 0,
    bloqueado_hasta     = NULL,
    updated_at          = NOW()
WHERE id = @Id
RETURNING id;
```

### DAL-A10 · INSERT log_auditoria (entidad 'Auth' | 'Usuario')

```sql
INSERT INTO log_auditoria (tenant_id, usuario_id, accion, entidad, entidad_id,
                           valor_anterior, valor_nuevo)
VALUES (@TenantId, @UsuarioId, @Accion, @Entidad, @EntidadId,
        @ValorAnterior::jsonb, @ValorNuevo::jsonb);
```
> `@Accion ∈ LOGIN | LOGOUT | UPDATE` (enum `accion_auditoria`, 06 L46 — LOGIN/LOGOUT ya existen, sin migración). `@Entidad = "Auth"` para LOGIN/LOGOUT (permite registrar intentos con correo inexistente, `usuario_id=NULL`) y `"Usuario"` para el cambio de contraseña (consistente con HU-003). JSON serializado con `UnsafeRelaxedJsonEscaping` (ADR-003).

## Decisiones de diseño (para @Orquestador)

| ID | Decisión | Justificación |
|----|----------|---------------|
| D1 | **Rotación de refresh tokens + detección de replay** | Cada `/auth/refresh` revoca el token usado y emite uno nuevo. Si se presenta un token ya revocado → se revoca TODA la familia del usuario (DAL-A6). Es el estándar OAuth2; limita la ventana de reuso de un token robado. Funciona con el DDL actual (sin migración). **Flag #1 — RESUELTO por Jorge (2026-09-13): SÍ.** |
| D2 | **Refresh token persistido como hash SHA-256 en la columna `token`** | El DDL (L103) define `token TEXT NOT NULL UNIQUE` (no `token_hash`). Se persiste el hash hex (64 chars) en esa columna: si la BD se filtra, los refresh tokens no son reutilizables. El UNIQUE aplica al hash. Sin migración. |
| D3 | **Auditoría de auth: LOGIN (éxito Y fallo), LOGOUT, UPDATE (cambio pwd)** | El enum `accion_auditoria` (L46) ya incluye LOGIN/LOGOUT. Auditar ambos permite rastrear accesos (HU-005) y detectar fuerza bruta; el volumen es bajo (SaaS interno). El refresh NO se audita (silencioso, evitaría inundar el log). `Entidad="Auth"` para login/logout (soporta correo inexistente con `usuario_id=NULL`), `"Usuario"` para cambio de pwd. **Flag #3 — RESUELTO por Jorge (2026-09-13): éxito Y fallo.** |
| D4 | **Política de contraseña: mín 8 chars + 1 mayúscula + 1 minúscula + 1 dígito (sin símbolo obligatorio)** | Alineada con HU-003 (mín 8). 3 clases sin símbolo reduce fricción; la contraseña temporal generada por HU-003 (4 clases) la cumple de sobra. **Flag #2 — RESUELTO por Jorge (2026-09-13): sin símbolo obligatorio.** |
| D5 | **Login con `requiere_cambio_pwd=true` → emite tokens + flag en la respuesta** | El frontend redirige al flujo de cambio sin round-trip extra; el endpoint de cambio exige la contraseña actual (que el usuario ya demostró conocer). Alternativa (bloquear login hasta cambiar) complica el flujo sin ganancia de seguridad real. **Flag #5 — RESUELTO por Jorge (2026-09-13): emitir tokens + flag.** |
| D6 | **`TenantContext` scoped poblado por `TenantMiddleware` (sin `IHttpContextAccessor`)** | El middleware inyecta `TenantContext` por parámetro de `InvokeAsync` (DI de ASP.NET Core) y lo puebla desde los claims del JWT. Los servicios BLL lo inyectan; los existentes (HU-001/002/003) reciben overload opcional para cablear `UsuarioId` en auditoría sin romper sus tests. **Flag #6 — RESUELTO por Jorge (2026-09-13): cablear en esta HU.** |
| D7 | **Limpieza de refresh tokens huérfanos: rechazo en validación; limpieza diferida** | Los tokens expirados/revocados se rechazan en validación (DAL-A3 + checks). La limpieza física (HostedService diario, ARCH-05) se difiere al Sprint de hardening — no bloquea la HU. **Flag #7 — RESUELTO por Jorge (2026-09-13): diferir a hardening.** |
| D8 | **Bloqueo de cuenta → HTTP 401 con mensaje específico** | 423 no está en el catálogo de ARCH-07. 401 con mensaje ("Cuenta bloqueada...") permite al usuario entender el estado sin exponer datos sensibles. |
| D9 | **Conteo de intentos: incremento por fallo; al 5º → Bloqueado + 15 min + reset del contador** | SEC-03. Al expirar el bloqueo, el contador reinicia (el usuario tiene 5 intentos frescos). Login exitoso resetea el contador. |
| D10 | **Logout `[AllowAnonymous]` + refresh token en body (revocación por poseedor)** | Si el access token expiró, el usuario aún puede cerrar sesión. Revocar por poseedor no es un riesgo (solo cierra la sesión). Idempotente: no revela si el token existía. **Flag #8.** |
| D11 | **JWT claims: `user_id`, `tenant_id`, `rol`, `area_id`** | Exactamente los claims de 04_ARQUITECTURA § 5 (y los que leen las funciones RLS `auth.tenant_id()`/`auth.user_rol()`/`auth.area_id()`, 06 L488-498). `tenant_id`/`area_id` se omiten si null (SuperAdmin). |
| D12 | **`JwtTokenHelper` + `JwtOptions` en `PE-GOL.Utility`** | 04_ARQUITECTURA § 2 declara "JWT helper" en Utility (capa transversal). Requiere añadir el paquete NuGet de generación JWT a Utility → **ADR-004 obligatorio** (regla: nueva librería fuera del stack → ADR). **Flag #4 — RESUELTO por Jorge (2026-09-13): SÍ, crear ADR-004.** |
| D13 | **Refresh token: 32 bytes aleatorios (RNGCryptoServiceProvider) → Base64Url** | Entropía suficiente (256 bits) para tokens de larga duración. |
| D14 | **Cambio de contraseña: verifica actual + política + ≠ actual + BCrypt 12 + limpia flag + revoca TODOS los refresh tokens** | Fuerza re-login con la nueva contraseña (HANDOFF L199). El access token actual sigue válido hasta expirar (≤ 60 min) — JWT stateless sin blacklist en v1.0 (trade-off aceptado). |
| D15 | **Login de usuario de tenant Inactivo → 401** | Un tenant desactivado no debe permitir accesos (CA HU-001: "Al desactivar un tenant, sus usuarios no pueden iniciar sesión"). Se valida con `tenant_estado` del JOIN en DAL-A1. **Flag #8 — RESUELTO por Jorge (2026-09-13): incluir.** |
| D16 | **BCrypt.Verify dummy en correo inexistente** | Mitiga enumeración de usuarios por timing (el login de correo inexistente tarda lo mismo que uno con password incorrecto). **Flag #8 — RESUELTO por Jorge (2026-09-13): incluir.** |
| D17 | **`TenantContext.TenantId` es `Guid?` (nullable)** | El SuperAdmin tiene `tenant_id = NULL` en BD (DDL L97, sin NOT NULL). El middleware debe tolerar el claim `tenant_id` ausente y dejar `TenantId = null`; nunca lanzar error de parseo. Observación técnica de Jorge (2026-09-13), no bloqueante pero obligatoria para @BackendDev. |
