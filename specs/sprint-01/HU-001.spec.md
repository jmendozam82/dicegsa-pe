## Contexto

HU-001 del backlog (`docs/03_BACKLOG.md`, líneas 33-45): como **SuperAdmin (SA)** quiero crear, editar, activar y desactivar Tenants (Gerencias) con nombre, descripción, plan de suscripción y estado, para administrar las gerencias que usan la plataforma.

**Criterios de aceptación de la HU:**
1. Formulario con: nombre, descripción, plan (Básico / Estándar / Premium), estado (Activo/Inactivo).
2. Listado paginado de tenants con filtro por estado y plan.
3. Al desactivar un tenant, sus usuarios no pueden iniciar sesión.
4. Validación: nombre único en la plataforma.
5. Log de auditoría registra create/update/deactivate.

**Alcance de esta HU:** 100% backend (API + BLL + DAL). El formulario de UI no se implementa aquí; las vistas de administración SaaS corresponden a una HU de frontend posterior. El listado paginado se entrega como endpoints REST consumibles por esa futura UI.

**Decisión arquitectónica clave ya tomada (no requiere ADR):** schema compartido + `tenant_id` + RLS. La tabla `tenant` es la **tabla raíz del multitenancy**: NO lleva columna `tenant_id` (verificado en `06_MODELO_DATOS.md` líneas 62-73) — es la excepción explícita a [DB-03]. El aislamiento multi-tenant (ARCH-04) aplica a las tablas de dominio hijas (ciclo, area, etc.), no a la tabla raíz. Las tablas `tenant`, `plan`, `usuario`, `refresh_token` y `log_auditoria` están **fuera del alcance RLS** (no aparecen en el bloque `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` de `06_MODELO_DATOS.md` líneas 458-477); su seguridad se garantiza por: (a) los endpoints exigen rol `SuperAdmin`, (b) el DAL del SuperAdmin no aplica filtro de tenant (04_ARQUITECTURA § 4.3), y (c) el JWT/RLS de las tablas hijas es la segunda línea de defensa.

**Requerimientos trazables:** RF-001 (CRUD tenants), RF-005 (asignación de plan), RN-001 (aislamiento total, el SA solo gestiona metadatos), RN-005 (el SA no accede a datos de negocio de tenants), RNF-007 (aislamiento por RLS en tablas de dominio), RNF-016 (20 tenants activos simultáneos), RNF-023 (logging estructurado).

## Endpoints

Todos los endpoints bajo `/api/v1/tenants`, protegidos con `[Authorize(Roles = "SuperAdmin")]`. No se acepta `tenant_id` como parámetro del body ni del query string (SEC-06); el tenant gestionado se identifica por el `{id}` de la ruta. Todas las respuestas usan el wrapper `ApiResponse<T>` (ARCH-07).

| Método | Ruta | Auth | Descripción |
|--------|------|------|-------------|
| GET | `/api/v1/tenants` | SuperAdmin | Listado paginado de tenants. Query params opcionales: `page` (int, default 1), `pageSize` (int, default 10, max 100), `estado` (`Activo`\|`Inactivo`), `planId` (UUID). Retorna `PagedResult<TenantResponse>`. |
| GET | `/api/v1/tenants/{id}` | SuperAdmin | Obtiene un tenant por id. Param de ruta `id` (UUID). 404 si no existe. |
| POST | `/api/v1/tenants` | SuperAdmin | Crea un tenant. Body: `TenantCreateRequest`. Retorna 201 con `TenantResponse`. |
| PUT | `/api/v1/tenants/{id}` | SuperAdmin | Actualiza datos generales del tenant (nombre, descripción, plan, logo, eslogan, zona horaria). Body: `TenantUpdateRequest`. El campo `estado` NO se modifica por este endpoint (se usa activar/desactivar). Retorna 200 con `TenantResponse`. |
| POST | `/api/v1/tenants/{id}/activar` | SuperAdmin | Activa un tenant inactivo (transición `Inactivo` → `Activo`). Sin body. Retorna 200 con `TenantResponse`. 422 si el tenant ya está `Activo`. |
| POST | `/api/v1/tenants/{id}/desactivar` | SuperAdmin | Desactiva un tenant activo (transición `Activo` → `Inactivo`). Sin body. Bloquea el inicio de sesión de sus usuarios y revoca sus refresh tokens. Retorna 200 con `TenantResponse`. 422 si el tenant ya está `Inactivo`. |

**Nota:** No existe endpoint DELETE. La eliminación física de un tenant no está contemplada (soft state mediante `estado`), consistente con la convención "soft delete no se usa — se usa campo estado" de `06_MODELO_DATOS.md` § 1.

**Códigos HTTP posibles (por endpoint):** 200 (GET/PUT/activar/desactivar), 201 (POST), 400 (validación de formato de request), 401 (sin token), 403 (rol distinto a SuperAdmin), 404 (tenant inexistente), 422 (regla de negocio violada), 500 (error no controlado, `ExceptionMiddleware`).

## Lógica BLL (paso a paso)

Implementación en `PE-GOL.BLL/Services/TenantService.cs` (interface `ITenantService.cs`). Todas las operaciones de escritura ejecutan **una sola transacción** (INSERT/UPDATE + auditoría juntos) vía `IDbTransaction` de Dapper. El `TenantContext` (del JWT vía `TenantMiddleware`) provee `UserId` y `Rol` — para estos endpoints el rol es siempre `SuperAdmin`.

### 1. `CrearAsync(TenantCreateRequest request)`

1. Normalizar `nombre`: trim + colapso de espacios internos múltiples.
2. **Validar unicidad de nombre**: si `ExisteNombreAsync(nombre)` → lanzar `ValidacionException` ("Ya existe un tenant con el nombre 'X'") → HTTP 422.
3. **Validar plan**: si `ExistePlanAsync(planId)` es false → `ValidacionException` ("El plan seleccionado no existe") → HTTP 422.
4. Establecer `zonaHoraria` = request ?? `"America/Managua"` (default del dominio).
5. Ejecutar `INSERT` (query DAL-1) dentro de transacción; capturar el `id` y `createdAt` generados.
6. Serilog: `Log.Information("Tenant {TenantId} creado por {UserId}", id, TenantContext.UserId)` con los parámetros enriquecidos de tenant/usuario/módulo (RNF-023).
7. Registrar auditoría (DAL-7): `accion = CREATE`, `entidad = "Tenant"`, `entidad_id = id.ToString()`, `valor_anterior = null`, `valor_nuevo = JSON(request creado)`.
8. Commit; retornar `TenantResponse` mapeado. → HTTP 201.

### 2. `ActualizarAsync(Guid id, TenantUpdateRequest request)`

1. Normalizar `nombre` (trim + colapso de espacios).
2. Obtener tenant actual: si null → `NotFoundException` → HTTP 404.
3. **Validar unicidad excluyendo self**: `ExisteNombreAsync(nombre, excludeId: id)` → si true → `ValidacionException` ("Ya existe un tenant con el nombre 'X'") → HTTP 422.
4. **Validar plan** existente → si no → `ValidacionException` → HTTP 422.
5. **Snapshot de auditoría**: `valor_anterior = JSON(tenant actual con sus campos previos)`.
6. Ejecutar `UPDATE` (DAL-4) en transacción.
7. Registrar auditoría (DAL-7): `accion = UPDATE`, `valor_nuevo = JSON(estado posterior)`.
8. Commit; retornar `TenantResponse` actualizado. → HTTP 200.

### 3. `DesactivarAsync(Guid id)`

> Regla de negocio crítica (CA #3): "Al desactivar un tenant, sus usuarios no pueden iniciar sesión". Se implementa en dos frentes complementarios:
> 1. **Preventivo (futuro HU-004):** el flujo de login consultará el `estado` del tenant del usuario y rechazará la autenticación con 403 si el tenant está `Inactivo`. Se deja registrado como dependencia de HU-004 (ver "Decisiones pendientes").
> 2. **Inmediato/Reactivo (esta HU):** al desactivar, se **revocan todos los refresh tokens** de los usuarios del tenant, invalidando sesiones activas de inmediato (los access tokens JWT expiran solos a los 60 min; al vencer, el refresh fallará y el usuario quedará fuera).

1. Obtener tenant por id: si null → `NotFoundException` → HTTP 404.
2. Si `estado == "Inactivo"` → `ValidacionException` ("El tenant ya está desactivado") → HTTP 422 (evita log duplicado y mantiene auditoría precisa).
3. Ejecutar en **una transacción**:
   - `UPDATE tenant SET estado = 'Inactivo', updated_at = NOW() WHERE id = @Id` (DAL-6).
   - **Revocar refresh tokens** de todos los usuarios del tenant: `UPDATE refresh_token SET revocado = TRUE WHERE usuario_id IN (SELECT id FROM usuario WHERE tenant_id = @TenantId)` (DAL-5).
   - Registrar auditoría: `accion = DEACTIVATE`, `valor_anterior = JSON(estado 'Activo')`, `valor_nuevo = JSON(estado 'Inactivo')` (DAL-7).
4. Commit. Serilog información del evento. Retornar `TenantResponse` con estado `Inactivo`. → HTTP 200.

### 4. `ActivarAsync(Guid id)`

1. Obtener tenant por id: si null → `NotFoundException` → HTTP 404.
2. Si `estado == "Activo"` → `ValidacionException` ("El tenant ya está activo") → HTTP 422.
3. Ejecutar en transacción: `UPDATE tenant SET estado = 'Activo', updated_at = NOW()` (DAL-6) + auditoría `accion = ACTIVATE`.
4. Commit. **Nota:** reactivar el tenant NO re-habilita los refresh tokens previamente revocados; los usuarios deben volver a iniciar sesión (comportamiento deseado). Retornar `TenantResponse` con estado `Activo`. → HTTP 200.

### 5. `ListarAsync(int page, int pageSize, string? estado, Guid? planId)`

1. Sanear `page` (>= 1, default 1) y `pageSize` (1..100, default 10; >100 → truncar a 100).
2. Ejecutar `SELECT COUNT` con filtros (DAL-3b) para obtener `total`; si `total == 0` retornar página vacía sin ejecutar el SELECT de datos.
3. Ejecutar `SELECT` paginado con los mismos filtros + `ORDER BY created_at DESC` (DAL-3a); `offset = (page - 1) * pageSize`.
4. Calcular `totalPages = ceil(total / pageSize)`.
5. Retornar `PagedResult<TenantResponse>` con los items y metadatos. → HTTP 200.
6. Nota: la tabla tenant es raíz del multitenancy → **no** se aplica `WHERE tenant_id` (el SuperAdmin ve todos los tenants; solo metadatos — RN-001/RN-005).

### 6. `ObtenerPorIdAsync(Guid id)`

1. Ejecutar `SELECT` por id (DAL-2). Si null → `NotFoundException` → HTTP 404.
2. Retornar `TenantResponse`. → HTTP 200.

## Queries DAL

Implementación en `PE-GOL.DAL/Repositories/Saas/TenantRepository.cs` + `PE-GOL.DAL/Interfaces/ITenantRepository.cs` (carpeta `Saas/` para reflejar la zona SaaS de `PE-GOL.Entity/Saas/`). Solo Dapper + SQL parametrizado (STACK-03). La tabla `tenant` **no lleva `tenant_id`** (excepción de [DB-03], verificado en DDL) → estas queries NO incluyen `WHERE tenant_id = @TenantId`. El alcance se garantiza por `[Authorize(Roles = "SuperAdmin")]` + `TenantContext.Rol`.

### DAL-1 · INSERT tenant

```sql
INSERT INTO tenant (nombre, descripcion, plan_id, logo_url, eslogan, zona_horaria, estado)
VALUES (@Nombre, @Descripcion, @PlanId, @LogoUrl, @Eslogan, @ZonaHoraria, 'Activo')
RETURNING id, created_at, updated_at;
```

### DAL-2 · SELECT por id (con nombre del plan)

```sql
SELECT t.id, t.nombre, t.descripcion, t.plan_id, p.nombre AS plan_nombre,
       t.logo_url, t.eslogan, t.zona_horaria, t.estado, t.created_at, t.updated_at
FROM tenant t
JOIN plan p ON p.id = t.plan_id
WHERE t.id = @Id;
```

### DAL-3a · SELECT paginado con filtros

```sql
SELECT t.id, t.nombre, t.descripcion, t.plan_id, p.nombre AS plan_nombre,
       t.logo_url, t.eslogan, t.zona_horaria, t.estado, t.created_at, t.updated_at
FROM tenant t
JOIN plan p ON p.id = t.plan_id
WHERE (@Estado IS NULL     OR t.estado = @Estado::estado_tenant)
  AND (@PlanId IS NULL     OR t.plan_id = @PlanId)
ORDER BY t.created_at DESC
LIMIT @PageSize OFFSET @Offset;
```

### DAL-3b · COUNT con los mismos filtros (para paginado)

```sql
SELECT COUNT(1)
FROM tenant t
WHERE (@Estado IS NULL     OR t.estado = @Estado::estado_tenant)
  AND (@PlanId IS NULL     OR t.plan_id = @PlanId);
```

### DAL-4 · UPDATE datos generales

```sql
UPDATE tenant
SET nombre       = @Nombre,
    descripcion  = @Descripcion,
    plan_id      = @PlanId,
    logo_url     = @LogoUrl,
    eslogan      = @Eslogan,
    zona_horaria = @ZonaHoraria,
    updated_at   = NOW()
WHERE id = @Id
RETURNING id, created_at, updated_at;
```

### DAL-5 · Revocar refresh tokens de usuarios del tenant (en desactivar)

```sql
UPDATE refresh_token
SET revocado = TRUE
WHERE usuario_id IN (SELECT id FROM usuario WHERE tenant_id = @TenantId);
```

### DAL-6 · UPDATE estado

```sql
UPDATE tenant
SET estado     = @Estado,          -- 'Activo' | 'Inactivo' (cast implícito a estado_tenant)
    updated_at = NOW()
WHERE id = @Id
RETURNING id, created_at, updated_at;
```

### DAL-7 · INSERT log_auditoria (una por operación de escritura)

```sql
INSERT INTO log_auditoria (tenant_id, usuario_id, accion, entidad, entidad_id,
                           valor_anterior, valor_nuevo)
VALUES (@TenantId, @UsuarioId, @Accion, 'Tenant', @EntidadId,
        @ValorAnterior::jsonb, @ValorNuevo::jsonb);
```
> `@TenantId` = id del tenant gestionado (columna nullable de log_auditoria para acciones globales; aquí siempre se informa). `@UsuarioId` = id del SuperAdmin desde `TenantContext`. `@Accion` ∈ `CREATE | UPDATE | ACTIVATE | DEACTIVATE` (enum accion_auditoria - verificado en DDL línea 46). `@ValorAnterior/@ValorNuevo` = JSON serializado de los DTOs (null en CREATE para valor_anterior).

### DAL-8 · Validación de unicidad de nombre

```sql
-- Crear: sin exclusión
SELECT COUNT(1) FROM tenant WHERE LOWER(nombre) = LOWER(@Nombre);

-- Actualizar: excluye el propio tenant
SELECT COUNT(1) FROM tenant WHERE LOWER(nombre) = LOWER(@Nombre) AND id <> @ExcludeId;
```
> Comparación **case-insensitive** (`LOWER`) para que "Gerencia A" y "gerencia a" se consideren duplicados. Ejecutada dentro de la misma transacción de escritura para minimizar condiciones de carrera (carrera residual documentada en "Decisiones pendientes").

### DAL-9 · Validación de existencia de plan

```sql
SELECT COUNT(1) FROM plan WHERE id = @PlanId;
```

> Nota sobre [DB-04]: estos COUNTs son validaciones de negocio, no campos calculados persistidos; no hay cálculos BLL en SQL.

## Validaciones FluentValidation

Clases en `PE-GOL.API` (reglas de forma del request) + re-validación en BLL (reglas de negocio con estado persistido). La validación del servidor es siempre la fuente de verdad (UX-04).

### `TenantCreateRequestValidator` / `TenantUpdateRequestValidator`

| Campo | Regla |
|-------|-------|
| `nombre` | `NotEmpty` · `MaximumLength(150)` · `Must` no contener solo espacios (trim no vacío). Unicidad NO se valida aquí (requiere BD) → se valida en BLL. |
| `descripcion` | `MaximumLength(1000)` (opcional; si viene null/empty, ok). |
| `planId` | `NotEmpty` (Guid != Guid.Empty). Existencia en BD → BLL. |
| `logoUrl` | Opcional · `MaximumLength(500)` · si no vacío, `Must` ser URL válida (`Uri.TryCreate` absoluto http/https). |
| `eslogan` | `MaximumLength(200)` (opcional). |
| `zonaHoraria` | `MaximumLength(50)` (opcional; default aplicado en BLL). |

**Separación de responsabilidades:**
- API/FluentValidation: forma y longitud del request → respuesta `ApiResponse<T>` con `errors` y HTTP 400/422.
- BLL: unicidad de nombre (DAL-8), existencia de plan (DAL-9), transiciones de estado válidas → HTTP 422. La BLL es la autoridad final y debe re-ejecutar estas validaciones (el `ValidationFilter` no sustituye al BLL).

## Decisiones pendientes de ADR

> No se creó ADR en esta entrega (estado Borrador). Estas son decisiones que **recomiendo resolver antes de la implementación o durante Sprint 1**, con ADR aprobado por Jorge:

1. **Índice único sobre `tenant(nombre)`.** El DDL actual (06_MODELO_DATOS.md líneas 62-73) **no define `UNIQUE` sobre `tenant.nombre`**, pero el CA #4 exige "nombre único en la plataforma". La BLL lo valida (DAL-8), pero persiste una condición de carrera TOCTOU en creaciones concurrentes. **Recomendación:** ADR para agregar `CREATE UNIQUE INDEX uq_tenant_nombre ON tenant (LOWER(nombre));` en una migración `db/migrations/` (DB-02), manteniendo la validación BLL como primera capa.
2. **Alcance RLS para tablas SaaS.** `tenant`, `plan`, `usuario`, `refresh_token` y `log_auditoria` quedaron fuera del `ENABLE ROW LEVEL SECURITY` (06_MODELO_DATOS.md líneas 458-477). Esto es correcto para `tenant`/`plan` (globales, solo SA) y `log_auditoria` (debe poder leerse de forma global por el SA), pero `usuario` y `refresh_token` **sí tienen `tenant_id`** y su aislamiento depende solo de la capa de aplicación. **Recomendación:** ADR evaluando habilitar RLS en `usuario`/`refresh_token` con política que permita filas `tenant_id IS NULL` (SuperAdmin) y `tenant_id = auth.tenant_id()`, como segunda línea de defensa de datos personales.
3. **Mecanismo de bloqueo de login al desactivar.** Esta HU implementa la parte reactiva (revocación de refresh tokens en DAL-5). La parte preventiva —rechazar el login si `tenant.estado = 'Inactivo'`— recae en `LoginService` de **HU-004 (Autenticación, mismo Sprint 1)**. **Coordinación:** HU-004 debe consultar el estado del tenant del usuario antes de emitir el JWT (403 con mensaje "Tenant desactivado"). No requiere ADR (es el diseño ya definido: el tenant gestionado por SA gobierna el acceso), pero se deja constancia explícita de la dependencia entre HUs para que `@Orquestador` lo tenga presente en la planificación de HU-004.

Sugerir a `@Orquestador` crear HU de frontend "Administración SaaS: gestión de tenants" o asignarla a HU-005.
