## Contexto

HU-007 del backlog (`docs/03_BACKLOG.md`, líneas 151-163, épica EP-02 líneas 130-132): como **ADM (AdminTenant)** quiero crear y gestionar ciclos anuales con año fiscal, mes de inicio y estado, para organizar la planificación estratégica por período.

**Criterios de aceptación de la HU:**
1. Crear ciclo con: nombre (ej: PE 2026), año fiscal, mes de inicio, estado (Borrador).
2. No pueden existir dos ciclos con el mismo año fiscal en el mismo tenant.
3. El ADM puede activar un ciclo (pasa a estado Activo); solo un ciclo puede estar Activo a la vez.
4. El GER puede cerrar el ciclo activo (pasa a Cerrado → solo lectura).
5. Clonar ciclo anterior: copia áreas, responsables y umbrales al nuevo ciclo.

**Trazabilidad:** RF-002 (crear ciclos anuales por tenant), RF-005 (plan con `max_ciclos_activos`), RF-007 (parámetros globales del ciclo — **contradice CA #1, ver D-A/Flag #1**), RF-011 (clonar configuración de ciclo anterior), RN-002 (un año fiscal por ciclo; no dos activos del mismo año), RN-003 (estados del ciclo — **contradice CA #3/#4, ver D-A/Flag #1**), RN-004 (ciclo Cerrado = solo lectura), RN-007 (JefeArea solo lectura de configuración del ciclo), RN-039 (umbrales por ciclo, no retroactivos), RNF-018 (UI en español), RNF-023 (logging estructurado), SEC-06 (tenant_id desde JWT, nunca del body), ARCH-07 (wrapper `ApiResponse<T>`).

**Alcance de esta HU:** **100% backend** (API + BLL + DAL + Entity + DTO + IOC). La vista Razor de gestión de ciclos se **difiere a las HUs de UI** (HU-045 y siguientes), cuando `PE-GOL.Aplicacion` tenga sesión/ApiClient (decisión de Jorge 2026-09-14 en HU-006, Flag #3 de este spec — ver sección «UI»). Los endpoints y DTOs de este spec quedan listos para ser consumidos por el frontend en ese sprint.

### Verificación del modelo de datos (punto técnico #1 del prompt)

La tabla `ciclo` del DDL (`06_MODELO_DATOS.md` líneas 129-143) **YA contiene todas las columnas** que la HU necesita, incluyendo la restricción de unicidad del CA #2:

```
ciclo
├── id              UUID PRIMARY KEY DEFAULT gen_random_uuid()
├── tenant_id       UUID NOT NULL REFERENCES tenant(id)
├── nombre          VARCHAR(100) NOT NULL
├── año_fiscal      INT NOT NULL
├── mes_inicio      INT NOT NULL DEFAULT 1 CHECK (mes_inicio BETWEEN 1 AND 12)
├── estado          estado_ciclo NOT NULL DEFAULT 'Borrador'      ← enum: Borrador|Activo|Cerrado (L35)
├── created_by      UUID NOT NULL REFERENCES usuario(id)
├── activated_at    TIMESTAMPTZ
├── closed_at       TIMESTAMPTZ
├── created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
├── updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
└── UNIQUE (tenant_id, año_fiscal)                                 ← CA #2 YA garantizado a nivel BD (L141)
```

La tabla `umbral_semaforo` (`06` L145-157) **también existe** con `tenant_id`, `tipo` (enum `tipo_umbral`: KPI|PlanAccion, L36), `umbral_verde`/`umbral_amarillo` (DECIMAL(3,2), defaults 0.90/0.70, CHECK verde > amarillo y ambos 0..1) y `UNIQUE (ciclo_id, tipo)` — necesaria para el CA #5 (clonación de umbrales) y para los defaults del CA #1 (ver D-B).

**Conclusión: NO se requiere migración para esta HU.** El único cambio de esquema evaluado (índice parcial para RC-01 "solo un Activo") **no existe en el DDL** y se documenta como decisión pendiente de ADR (D-ADR-1, ver sección «Decisiones pendientes de ADR»). La columna `año_fiscal` usa la letra `ñ` (identificador Unicode válido en PostgreSQL; parámetro Dapper `@AñoFiscal` es identificador C# válido) — sin migración ni alias.

**Naming:** el DDL/dominio usan `año_fiscal` y `mes_inicio`; los DTOs usan `añoFiscal`/`mesInicio` (convención camelCase de HU-006). `estado` se expone como string `'Borrador'|'Activo'|'Cerrado'` (mismo patrón que `estado_tenant`/`estado_usuario` en HU-001/HU-003).

## Endpoints

Todos bajo `/api/v1/ciclos`, en `PE-GOL.API/Controllers/CicloController.cs` (raíz de `Controllers/`, **no** en `Controllers/Saas/`: este recurso es de alcance tenant, no SaaS — mismo criterio que `EmpresaController` de HU-006). **SEC-06:** el `tenant_id` NUNCA viaja en body ni query string; se resuelve del JWT vía `TenantContext.TenantId`. **SEC-07:** `ciclo` no es entidad de área (no tiene columna `area_id`) → **no aplica `AND area_id`** para ningún rol; el JefeArea lee la configuración del ciclo (RN-007) sin filtro adicional. Todas las respuestas usan el wrapper `ApiResponse<T>` (ARCH-07).

| Método | Ruta | Auth | Descripción |
|--------|------|------|-------------|
| GET | `/api/v1/ciclos` | `[Authorize(Roles = "AdminTenant,Gerente,JefeArea")]` | Listado de ciclos del tenant autenticado, ordenado por `año_fiscal` DESC. **Sin paginación** (catálogo acotado: 1-3 ciclos por año, esperado ≤ 10-15 — D3). Retorna `ApiResponse<List<CicloResponse>>`. 404 si `TenantContext.TenantId` es null. |
| GET | `/api/v1/ciclos/{id}` | `[Authorize(Roles = "AdminTenant,Gerente,JefeArea")]` | Detalle de un ciclo por id (param de ruta UUID). Retorna `ApiResponse<CicloResponse>`. 404 si no existe o pertenece a otro tenant (el DAL filtra por `tenant_id`). |
| POST | `/api/v1/ciclos` | `[Authorize(Roles = "AdminTenant")]` | Crea un ciclo en estado `Borrador` + **2 umbrales por defecto** (KPI y PlanAccion, 0.90/0.70 — DDL defaults, HU-008 CA #4). Body: `CicloCreateRequest`. Retorna 201 con `ApiResponse<CicloResponse>`. 422 si: año fiscal duplicado en el tenant, `mesInicio` fuera de 1..12, o nombre inválido. |
| PUT | `/api/v1/ciclos/{id}` | `[Authorize(Roles = "AdminTenant")]` | Edita nombre, año fiscal y mes de inicio. Body: `CicloUpdateRequest`. Retorna 200 con `ApiResponse<CicloResponse>`. **404** si no existe · **422** si: el ciclo no está en `Borrador` (RC-12/RN-004), año fiscal duplicado de otro ciclo del tenant, o forma inválida. |
| POST | `/api/v1/ciclos/{id}/activar` | `[Authorize(Roles = "AdminTenant")]` | Activa un ciclo `Borrador → Activo` (CA #3). Sin body. Retorna 200 con `ApiResponse<CicloResponse>`. **404** si no existe · **422** si: ya está `Activo`, está `Cerrado` (RC-12), **ya existe otro ciclo Activo en el tenant (RC-01)**, o el tenant excede `max_ciclos_activos` del plan (D-C, CA #2 HU-002). |
| POST | `/api/v1/ciclos/{id}/cerrar` | `[Authorize(Roles = "Gerente")]` | Cierra el ciclo activo `Activo → Cerrado` (CA #4, D-A). Sin body. Retorna 200 con `ApiResponse<CicloResponse>`. **404** si no existe · **422** si el ciclo no está `Activo`. |
| POST | `/api/v1/ciclos/{id}/clonar` | `[Authorize(Roles = "AdminTenant")]` | Clona el ciclo `{id}` (origen): crea un ciclo nuevo en `Borrador` y **copia los umbrales de semáforo** del origen (D-B). Body: `ClonarCicloRequest` (identidad del ciclo nuevo). Retorna 201 con `ApiResponse<CicloResponse>` del ciclo nuevo. **404** si el origen no existe · **422** si: año fiscal duplicado, o forma inválida. |

**Códigos HTTP posibles:** 200 (GET/PUT/activar/cerrar), 201 (POST crear/clonar), 400 (body malformado), 401 (sin token), 403 (rol distinto al autorizado — p. ej. Gerente intentando POST/PUT/activar/clonar, ADM intentando cerrar, o SuperAdmin en cualquier endpoint), 404 (ciclo inexistente o `TenantContext.TenantId` null), 422 (regla de negocio violada), 500 (error no controlado, `ExceptionMiddleware`).

**Notas de diseño de endpoints:**
- **No existe DELETE de ciclos** (D15): los ciclos son históricos (años concluidos); el ciclo de vida se gestiona por estados `Borrador → Activo → Cerrado` (RC-12). Eliminar un ciclo rompería las FKs de `umbral_semaforo`/`filosofia`/`area` (CASCADE) y el historial de planificación.
- **SuperAdmin queda fuera de todos los endpoints (403):** no tiene `tenant_id` (D17 HU-004) y los ciclos son un concepto de tenant; el SA gestiona tenants vía `/api/v1/tenants` (HU-001).
- **JefeArea puede leer** ciclos (GET listado/detalle): es configuración del ciclo, no datos de área → SEC-07 no aplica (RN-007: solo lectura a configuración del ciclo). No hay endpoints de escritura para JEF.
- **Sin caché:** cada GET lee la BD directamente (los estados cambian con activar/cerrar; el frontend debe ver el estado fresco).

## Lógica BLL (paso a paso)

Implementación en `PE-GOL.BLL/Services/CicloService.cs` (interface `ICicloService`). Todas las operaciones de escritura ejecutan **una sola transacción** (`BeginTransactionAsync` + `IDbTransaction` de Dapper, patrón HU-001) que incluye la auditoría. **Ctor:** `CicloService(ICicloRepository repository, IPlanService planService, TenantContext tenantContext)` + overload `(..., ILogger<CicloService>? logger)` — patrón de `UsuarioService`/`AuthService`/`EmpresaService` (RNF-023, D13). `TenantContext` provee `TenantId` (Guid?, D17), `UserId` (wiring D6 HU-004) y `Rol`.

**Regla transversal (D12):** cada método de escritura re-valida el rol desde `_tenantContext.Rol` (el `[Authorize(Roles=...)]` del controller es la primera capa; la BLL es la fuente de verdad — patrón HU-001..006). Los métodos de lectura validan solo que `TenantId` no sea null.

### 1. `ListarAsync(CancellationToken ct)`

1. `tenantId = _tenantContext.TenantId` → si `null` → `NotFoundException("No se pudo determinar el tenant del usuario autenticado")` → 404 (defensivo: los roles autorizados siempre tienen tenant_id; el SuperAdmin queda fuera por `[Authorize(Roles=...)]`).
2. `ciclos = _repository.ListarAsync(tenantId.Value, ct)` (DAL-C3, `ORDER BY año_fiscal DESC`).
3. Mapear a `List<CicloResponse>`. → HTTP 200.

### 2. `ObtenerPorIdAsync(Guid id, CancellationToken ct)`

1. `tenantId = _tenantContext.TenantId` → si `null` → `NotFoundException` → 404.
2. `ciclo = _repository.ObtenerPorIdAsync(tenantId.Value, id, ct)` (DAL-C2) → si `null` → `NotFoundException("El ciclo '{id}' no existe")` → 404 (el filtro por `tenant_id` del DAL garantiza que un ciclo de otro tenant también devuelve null → 404, sin fuga de información).
3. Mapear a `CicloResponse`. → HTTP 200.

### 3. `CrearAsync(CicloCreateRequest request, CancellationToken ct)`

1. **Validar rol (defensivo, D12):** si `_tenantContext.Rol != "AdminTenant"` → `AccesoDenegadoException` → 403.
2. `tenantId = _tenantContext.TenantId` → si `null` → `NotFoundException` → 404.
3. Normalizar `nombre`: trim + colapso de espacios internos múltiples (helper `NormalizarNombre`, mismo que `TenantService`).
4. **Re-validar `mesInicio` ∈ 1..12** (BLL fuente de verdad, espejo del CHECK del DDL) → si viola → `ValidacionException("El mes de inicio debe estar entre 1 y 12")` → 422.
5. **Validar unicidad de año fiscal (CA #2):** `_repository.ExisteAñoFiscalAsync(tenantId.Value, request.AñoFiscal, excludeId: null, ct)` (DAL-C6) → si true → `ValidacionException("Ya existe un ciclo con el año fiscal '{X}' en este tenant")` → 422.
6. Ejecutar en **una sola transacción**:
   - `INSERT ciclo` (DAL-C1) con `estado = 'Borrador'`, `created_by = _tenantContext.UserId`, capturando `id`/`createdAt`/`updatedAt`.
   - `INSERT` **2 umbrales por defecto** (DAL-C9): `tipo='KPI'` y `tipo='PlanAccion'`, ambos con `umbral_verde=0.90`, `umbral_amarillo=0.70` (defaults del DDL L150-151; HU-008 CA #4 "Valores por defecto al crear ciclo").
   - Auditoría (DAL-C11): `accion = CREATE`, `entidad = "Ciclo"`, `entidad_id = id`, `valor_anterior = null`, `valor_nuevo = JSON(ciclo creado)` serializado con `JsonOpcionesAuditoria` (ADR-003).
   - Commit.
7. Serilog: `Log.Information("Ciclo {CicloId} creado por {UserId}. Modulo=Ciclo, Accion=CREATE, Entidad=Ciclo", ...)` (RNF-023).
8. Captura de `PostgresException` **23505** (colisión concurrente de `UNIQUE (tenant_id, año_fiscal)`) → rollback explícito → `ValidacionException` → 422 (patrón ADR-001; el UNIQUE ya existe en el DDL L141 — D8).
9. Lectura posterior al commit (`ObtenerPorIdAsync`) → mapear a `CicloResponse`. → HTTP 201.

### 4. `ActualizarAsync(Guid id, CicloUpdateRequest request, CancellationToken ct)`

1. **Validar rol (defensivo):** `Rol != "AdminTenant"` → 403.
2. `tenantId` → si `null` → 404.
3. `original = ObtenerPorIdAsync(id, ct)` → si `null` → `NotFoundException` → 404.
4. **RC-12/RN-004 (solo Borrador editable):** si `original.Estado != "Borrador"` → `ValidacionException("Solo se puede editar un ciclo en estado Borrador")` → 422. (Un ciclo `Activo` o `Cerrado` es inmutable en sus parámetros.)
5. Normalizar `nombre`; re-validar `mesInicio` ∈ 1..12 → 422.
6. **Unicidad de año fiscal excluyendo self:** `ExisteAñoFiscalAsync(tenantId, request.AñoFiscal, excludeId: id, ct)` (DAL-C6) → si true → `ValidacionException` → 422.
7. **Snapshot de auditoría:** `valor_anterior = JSON(original con nombre/añoFiscal/mesInicio previos)` (ADR-003).
8. Ejecutar en **una sola transacción**:
   - `UPDATE ciclo` (DAL-C4) con `updated_at = NOW()`.
   - Auditoría (DAL-C11): `accion = UPDATE`, `valor_nuevo = JSON(estado posterior)`.
   - Commit.
9. Serilog información del evento.
10. Lectura posterior → `CicloResponse`. → HTTP 200.

### 5. `ActivarAsync(Guid id, CancellationToken ct)`

1. **Validar rol (defensivo):** `Rol != "AdminTenant"` → 403. (D-A: el ADM activa `Borrador → Activo`; el GER solo cierra.)
2. `tenantId` → si `null` → 404.
3. `ciclo = ObtenerPorIdAsync(id, ct)` → si `null` → `NotFoundException` → 404.
4. Si `ciclo.Estado == "Activo"` → `ValidacionException("El ciclo ya está activo")` → 422 (evita log duplicado y auditoría imprecisa).
5. Si `ciclo.Estado == "Cerrado"` → `ValidacionException("Un ciclo Cerrado es de solo lectura")` → 422 (RC-12/RN-004).
6. **RC-01 (solo un Activo por tenant):** `_repository.ContarCiclosActivosAsync(tenantId.Value, excludeId: id, ct)` (DAL-C7) → si `> 0` → `ValidacionException("Ya existe un ciclo activo en este tenant")` → 422. (El `excludeId` excluye el ciclo que se está activando, aún `Borrador`.)
7. **Límite del plan (D-C, CA #2 HU-002):**
   - `planId = _repository.ObtenerPlanIdDelTenantAsync(tenantId.Value, ct)` (DAL-C8) → si `null` → `NotFoundException("El tenant no tiene un plan asignado")` → 404 (defensivo; todo tenant tiene `plan_id NOT NULL`).
   - `resultado = _planService.ValidarLimitesParaTenantAsync(tenantId.Value, planId, ct)` (mismo patrón que `UsuarioService` HU-003).
   - Si `!resultado.EsValido` → `ValidacionException(string.Join(" ", resultado.Errores))` → 422, **sin** llegar al UPDATE ni a la auditoría.
   - **Nota semántica (ver Flag #5):** DAL-P8 de HU-002 cuenta solo ciclos `estado='Activo'`; el ciclo que se activa aún es `Borrador` → no cuenta. Combinado con RC-01 (máx 1 activo), la comparación `>` del `PlanLimitValidator` es segura. Si Jorge relaja RC-01 (p. ej. Premium con 2 activos), el check debe ajustarse a `count >= max` (validar el estado post-activación).
8. Ejecutar en **una sola transacción**:
   - `UPDATE ciclo SET estado='Activo', activated_at=NOW(), closed_at=NULL, updated_at=NOW()` (DAL-C5).
   - Auditoría (DAL-C11): `accion = ACTIVATE`, `valor_anterior = JSON({ estado: 'Borrador' })`, `valor_nuevo = JSON({ estado: 'Activo', activatedAt })`.
   - Commit.
9. Serilog información del evento.
10. Lectura posterior → `CicloResponse` con `estado='Activo'` y `activatedAt` poblado. → HTTP 200.

### 6. `CerrarAsync(Guid id, CancellationToken ct)`

1. **Validar rol (defensivo):** `Rol != "Gerente"` → `AccesoDenegadoException` → 403. (D-A: el GER cierra `Activo → Cerrado`; el ADM no puede cerrar.)
2. `tenantId` → si `null` → 404.
3. `ciclo = ObtenerPorIdAsync(id, ct)` → si `null` → `NotFoundException` → 404.
3. Si `ciclo.Estado != "Activo"` → `ValidacionException("Solo se puede cerrar el ciclo activo (estado Activo)")` → 422 (solo el ciclo activo se cierra; un `Borrador` no se cierra; un `Cerrado` ya está cerrado).
4. Ejecutar en **una sola transacción** (`activated_at` se conserva; se registra `closed_at` — D11 audita como `UPDATE` porque el enum `accion_auditoria` no tiene acción CLOSE, ver D11):
   - `UPDATE ciclo SET estado='Cerrado', closed_at=NOW(), updated_at=NOW()` (DAL-C5).
   - Auditoría (DAL-C11): `accion = UPDATE`, `valor_anterior = JSON({ estado: 'Activo' })`, `valor_nuevo = JSON({ estado: 'Cerrado', closedAt })` (ADR-003).
   - Commit.
5. Serilog información del evento.
6. Lectura posterior → `CicloResponse` con `estado='Cerrado` y `closedAt` poblado. → HTTP 200.

> **RC-12 (RC-12/RN-004):** una vez `Cerrado`, ningún endpoint de escritura lo modifica (edición bloqueada en paso 4 de `ActualizarAsync`; activación bloqueada en paso 5 de `ActivarAsync`; cerrar un `Cerrado` bloqueado en paso 3 de `CerrarAsync`). Las entidades hijas del ciclo cerrado quedan protegidas por las HUs de dominio correspondientes (HU-009+ y siguientes, que validarán el estado del ciclo padre).

### 7. `ClonarAsync(Guid idOrigen, ClonarCicloRequest request, CancellationToken ct)`

1. **Validar rol (defensivo):** `Rol != "AdminTenant"` → 403.
2. `tenantId` → si `null` → 404.
3. `origen = ObtenerPorIdAsync(idOrigen, ct)` → si `null` → `NotFoundException("El ciclo origen '{id}' no existe")` → 404.
4. Normalizar `nombre`; re-validar `mesInicio` ∈ 1..12 → 422.
5. **Unicidad de año fiscal:** `ExisteAñoFiscalAsync(tenantId, request.AñoFiscal, excludeId: null, ct)` → si true → `ValidacionException` → 422.
6. `umbralesOrigen = _repository.ObtenerUmbralesAsync(tenantId.Value, idOrigen, ct)` (DAL-C10).
7. Ejecutar en **una sola transacción**:
   - `INSERT ciclo` nuevo (DAL-C1) con `estado='Borrador'`, `created_by = _tenantContext.UserId`.
   - **Copiar umbrales (D-B):** para cada `UmbralSemaforoEntity` de origen → `INSERT umbral_semaforo` (DAL-C9) con `ciclo_id = nuevoId`, `tipo`, `umbral_verde`, `umbral_amarillo` copiados. **Defensivo:** si el origen no tiene umbrales (0 filas), insertar los 2 defaults (0.90/0.70) para que el ciclo nuevo nunca quede sin configuración de semáforo.
   - Auditoría (DAL-C11): `accion = CREATE`, `valor_nuevo = JSON(ciclo nuevo + origenId)` (D11: el clon se audita como CREATE con trazabilidad del origen).
   - Commit.
8. **D-B (CA #5 parcial — Flag #2):** áreas y responsables **NO se clonan en esta HU** (HU-009 áreas y HU-010 responsables son Sprint 2 y aún no existen como servicios). El contrato `ClonarAsync` queda **preparado** para que HU-009/HU-010 extiendan el flujo de clonación (ver sección «Decisiones de diseño» D5 y «Flags» #2).
9. Serilog información del evento (incluye `origenId`).
10. Lectura posterior → `CicloResponse` del ciclo nuevo. → HTTP 201.

## Queries DAL

Implementación en `PE-GOL.DAL/Repositories/Ciclo/CicloRepository.cs` + `PE-GOL.DAL/Interfaces/ICicloRepository.cs` (carpeta `Ciclo/` nueva, reflejando `PE-GOL.Entity/Ciclo/` — patrón de `Repositories/Saas/` para el dominio Ciclo). Solo Dapper + SQL parametrizado (STACK-03, SEC-05). **Toda query incluye `WHERE tenant_id = @TenantId` como primera condición** (SEC-06; `@TenantId` = `TenantContext.TenantId`, nunca del body/query). **No aplica `AND area_id`** (SEC-07): `ciclo` y `umbral_semaforo` no son entidades de área. RLS habilitado en ambas tablas (`06` L464-465) con políticas por tenant (`ciclo_tenant_policy` L506-507, `umbral_semaforo_policy` L561) — doble capa con el filtro del DAL.

> **Nota RLS (mismo criterio que HU-002 D8):** las queries de esta HU se ejecutan con el rol de BD del tenant autenticado (JWT con `tenant_id`), por lo que las políticas RLS aplican correctamente. No se requieren queries con `service_role` en esta HU (a diferencia de DAL-P8 de HU-002, que era del SuperAdmin).

### DAL-C1 · INSERT ciclo (estado Borrador)

```sql
INSERT INTO ciclo (tenant_id, nombre, año_fiscal, mes_inicio, estado, created_by)
VALUES (@TenantId, @Nombre, @AñoFiscal, @MesInicio, 'Borrador', @CreatedBy)
RETURNING id, created_at, updated_at;
```
> `@CreatedBy` = `TenantContext.UserId` (wiring D6 HU-004). `año_fiscal` con `ñ` es identificador Unicode válido en PostgreSQL (sin comillas: ya está en minúsculas).

### DAL-C2 · SELECT por id (aislado por tenant)

```sql
SELECT id, tenant_id, nombre, año_fiscal, mes_inicio, estado, created_by,
       activated_at, closed_at, created_at, updated_at
FROM ciclo
WHERE tenant_id = @TenantId
  AND id = @Id;
```

### DAL-C3 · SELECT listado del tenant (orden por año fiscal DESC)

```sql
SELECT id, tenant_id, nombre, año_fiscal, mes_inicio, estado, created_by,
       activated_at, closed_at, created_at, updated_at
FROM ciclo
WHERE tenant_id = @TenantId
ORDER BY año_fiscal DESC;
```

### DAL-C4 · UPDATE datos generales (solo Borrador — la BLL valida el estado antes)

```sql
UPDATE ciclo
SET nombre      = @Nombre,
    año_fiscal  = @AñoFiscal,
    mes_inicio  = @MesInicio,
    updated_at  = NOW()
WHERE tenant_id = @TenantId
  AND id = @Id
RETURNING id, created_at, updated_at;
```

### DAL-C5 · UPDATE estado (activar / cerrar)

```sql
UPDATE ciclo
SET estado       = @Estado::estado_ciclo,
    activated_at = @ActivatedAt,   -- NOW() al activar; NULL al cerrar (se conserva el valor previo)
    closed_at    = @ClosedAt,      -- NOW() al cerrar; NULL al activar
    updated_at   = NOW()
WHERE tenant_id = @TenantId
  AND id = @Id
RETURNING id, created_at, updated_at;
```
> `@Estado` ∈ `'Activo' | 'Cerrado'` (cast al enum `estado_ciclo`, `06` L35). En `ActivarAsync` se pasa `@ActivatedAt = NOW()`, `@ClosedAt = NULL`; en `CerrarAsync` se pasa `@ClosedAt = NOW()` y `@ActivatedAt = <valor actual del ciclo>` (se conserva).

### DAL-C6 · Validación de unicidad de año fiscal (CA #2)

```sql
-- Crear / clonar: sin exclusión
SELECT COUNT(1) FROM ciclo
WHERE tenant_id = @TenantId
  AND año_fiscal = @AñoFiscal;

-- Actualizar: excluye el propio ciclo
SELECT COUNT(1) FROM ciclo
WHERE tenant_id = @TenantId
  AND año_fiscal = @AñoFiscal
  AND id <> @ExcludeId;
```
> Capa 1 (BLL, mensaje amigable → 422). Capa 2 (BD): el `UNIQUE (tenant_id, año_fiscal)` del DDL (L141) elimina la carrera TOCTOU → captura 23505 → 422 (patrón ADR-001, D8). **No requiere ADR nuevo**: la restricción ya existe en el DDL.

### DAL-C7 · COUNT ciclos activos (RC-01 — solo un Activo por tenant)

```sql
SELECT COUNT(1) FROM ciclo
WHERE tenant_id = @TenantId
  AND estado = 'Activo'::estado_ciclo
  AND id <> @ExcludeId;   -- excluye el ciclo que se está activando (aún Borrador)
```

### DAL-C8 · plan_id del tenant (para ValidarLimitesParaTenantAsync, D-C)

```sql
SELECT plan_id FROM tenant WHERE id = @TenantId;
```
> `ciclo` no tiene FK a `plan`; el límite `max_ciclos_activos` vive en `plan` (L57) y se resuelve vía el `plan_id` del tenant. Esta query evita que `CicloService` dependa de `ITenantRepository` (acoplamiento entre dominios).

### DAL-C9 · INSERT umbral_semaforo (defaults al crear / copiados al clonar)

```sql
INSERT INTO umbral_semaforo (ciclo_id, tenant_id, tipo, umbral_verde, umbral_amarillo)
VALUES (@CicloId, @TenantId, @Tipo::tipo_umbral, @UmbralVerde, @UmbralAmarillo);
```
> Defaults al crear (DAL-C9a): `@Tipo='KPI'` y `@Tipo='PlanAccion'`, `@UmbralVerde=0.90`, `@UmbralAmarillo=0.70` (defaults del DDL L150-151, HU-008 CA #4). Al clonar (DAL-C9b): valores copiados del origen (DAL-C10). El `UNIQUE (ciclo_id, tipo)` (L153) garantiza 2 filas máx por ciclo nuevo; la BLL inserta exactamente 2 filas.

### DAL-C10 · SELECT umbrales del ciclo origen (para clonar)

```sql
SELECT id, ciclo_id, tenant_id, tipo, umbral_verde, umbral_amarillo, updated_at
FROM umbral_semaforo
WHERE tenant_id = @TenantId
  AND ciclo_id = @OrigenId;
```

### DAL-C11 · INSERT log_auditoria (entidad Ciclo) — REUTILIZA el patrón DAL-7 de HU-001

```sql
INSERT INTO log_auditoria (tenant_id, usuario_id, accion, entidad, entidad_id,
                           valor_anterior, valor_nuevo)
VALUES (@TenantId, @UsuarioId, @Accion, 'Ciclo', @EntidadId,
        @ValorAnterior::jsonb, @ValorNuevo::jsonb);
```
> `@Accion ∈ CREATE | UPDATE | ACTIVATE` (enum `accion_auditoria`, `06` L46 — el enum **no tiene CLOSE/CLONE**; cerrar se audita como `UPDATE` con el cambio de estado en `valor_nuevo`, clonar como `CREATE` con `origenId` en `valor_nuevo` — D11). `@TenantId` = tenant del contexto. `@UsuarioId` = `TenantContext.UserId` (wiring D6 HU-004). JSON serializado con `JsonOpcionesAuditoria` (ADR-003).

> Nota [DB-04]: no hay campos calculados en SQL; las validaciones (RC-01, unicidad, límites del plan) son de negocio y viven en la BLL (mismo criterio documentado en HU-001/HU-002/HU-006).

## Validaciones FluentValidation

`PE-GOL.API/Validators/` (forma del request) + re-validación en BLL (reglas de negocio con estado persistido, fuente de verdad — UX-04). Patrón HU-001..006.

### `CicloCreateRequestValidator` / `CicloUpdateRequestValidator` / `ClonarCicloRequestValidator`

| Campo | Regla |
|-------|-------|
| `nombre` | `NotEmpty` · `MaximumLength(100)` · `Must` no contenga solo espacios (trim no vacío). Unicidad NO aquí (requiere BD) → BLL. |
| `añoFiscal` | `NotEmpty` (int distinto de 0) · `InclusiveBetween(2000, 2100)` — horizonte de planificación de la plataforma; regla de negocio de API/BLL (el DDL no tiene CHECK sobre `año_fiscal`). Unicidad NO aquí → BLL (DAL-C6). |

> Los endpoints `activar`/`cerrar` no tienen body → sin validators (solo `[Authorize(Roles)]` + re-validación de rol y reglas de negocio en BLL).
