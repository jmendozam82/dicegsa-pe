### Justificación de cada decisión

**F0 — Frontera de meses editables (Opción A).**
El CA habla de «los 12 meses del año» y `valor_mensual_kr.mes` está documentado como `1=Enero … 12=Diciembre` (`05_DOMINIO.md` L289), con `UNIQUE (key_result_id, mes)` y `CHECK (mes BETWEEN 1 AND 12)`. El trimestre, por tanto, es **calendario** (Q1=1-3, Q2=4-6, Q3=7-9, Q4=10-12) y la grilla es ENE–DIC. Eso descarta el «índice de mes dentro del ciclo» (offset desde `mes_inicio`), que además no dejaría mapear `mes` ↔ trimestre de forma estable.

Sobre esa base, la ventana editable es:

```
mesMinEditable = ciclo.MesInicio                      // los meses previos al inicio del ciclo no existen para él
mesMaxEditable = ciclo.año_fiscal >  año(hoy) ? 0     // ciclo del futuro: no hay meses editables
               : ciclo.año_fiscal <  año(hoy) ? 12    // ciclo de un año anterior aún no cerrado (RC-12 es la única barrera)
               : mes(hoy);                            // ciclo del año en curso: hasta el mes actual, inclusive
mesesEditables = { m : mesMinEditable <= m <= mesMaxEditable }   // vacío si mesMin > mesMax
```

Tres consecuencias deliberadas:
1. **`mes_inicio` recorta por abajo.** Un ciclo con `mes_inicio = 3` no admite ENE ni FEB: esas celdas se muestran con `Editable = false` y `MotivoBloqueo = "Mes anterior al inicio del ciclo"`, no se pueden enviar y el servidor las rechaza.
2. **La frontera solo avanza.** Como los valores se escriben únicamente en meses ya-PROsheet dentro de la ventana, **toda fila existente en `valor_mensual_kr` es por construcción editable-ontológicamente**: no puede haber un valor en un mes futuro o pre-ciclo. Por eso `EliminarValorAsync` **no** revalida la ventana (solo RC-12): si la fila existe, se puede borrar. Esto evita el absurdo operativo de «el valor de marzo ya no se puede corregir porque estamos en junio» sin abrir una segunda autorización.
3. **El servidor es la autoridad.** La UI marca `Editable` para dar feedback, pero `GuardarValoresAsync` vuelve a evaluar la ventana y devuelve 422 con el detalle de los meses rechazados. Un POST directo a la API con un mes futuro no cuela.

**F0c — Fuente de la fecha del negocio (Opción A).**
«Mes actual» es una decisión de negocio y debe ser **determinista en tests** y **coherente con la zona horaria del tenant**. El proyecto ya tiene el patrón: `EntregableAdjuntoReglasNegocio` y `EntregableAdjuntoService` reciben `TimeProvider` por constructor explícitamente «en vez de `DateTime.Now`» (precedente HU-022). `DateTime.UtcNow` (usado hoy en `AccionPlanService`/`DashboardService` para otros fines) daría el mes equivocado entre las 00:00 y las 05:00 UTC de cada día 1 — exactamente el día en que más importa la frontera. `DateTime.Now` depende del TZ del host de despliegue. Con `TimeProvider` + `tenant.zona_horaria` (ya modelada en HU-006, `ZonasIANA`/`ZonaHorariaHelper`), el «mes de negocio» es el mes calendario en la zona del cliente, y un `Mock<TimeProvider>` fija la fecha en los tests (incluido el caso límite del día 1).

**F1 — Puntuación final del KR (Opción B).**
RN-025 ya fijó el principio para el trimestre: *«los meses sin valor no afectan el promedio»*. Aplicarlo de forma coherente al año evita un sesgo sistemático contra el método: el 3 de marzo, con un solo mes registrado, el KR tendría `puntuacion_q1 = 0.500` y `puntuacion_final = (0.500 + 0 + 0 + 0)/4 = 0.125` → semáforo **Rojo** aunque el desempeño registrado sea del 50 %. La Opción B (`final = promedio de los trimestres con al menos un mes con valor`) da `0.500` → **Amarillo**, que es la lectura correcta de «lo que va se promedia; lo que no ha ocurrido, no cuenta». El sesgo de «no penalizar lo futuro» es inherente al modelo y ya está aceptado en RF-036/RN-025; además el consolidado de HU-027 es el que hace la lectura de cierre de año. Si Jorge prefiere la Opción A estricta (los trimestres sin datos cuentan como 0), es un cambio de **una línea** (`RecalcularKeyResultAsync` paso 5) que quedaría documentado aquí para que sea explícito.

**F2 — Fórmulas (confirmadas).**
`puntuacion_ponderada = puntuacion_final × peso` es literal de RF-037 y de `05_DOMINIO.md` L275. Para `okr.puntuacion_final` se suma la columna **persistida** `puntuacion_ponderada` de cada KR del OKR (RN-026 literal: «suma de las puntuaciones ponderadas de todos sus KRs») en vez de recomputar `Σ(final × peso)`: es la fuente única de verdad, evita drift y respeta DB-04 (lo que se persiste es lo que se lee). La diferencia entre ambas rutas está acotada a ±0.001 por el redondeo a 3 decimales de cada ponderada; con `DECIMAL(4,3)` es la diferencia correcta a persistir.

**F3 — Edición en línea (Opción B).**
La CA #1 pide literalmente una «grilla de 12 columnas (ENE–DIC) por KR». Lamodal obligaría a un ciclo abrir→cargar→cerrar por cada KR (hasta 5 por OKR) y escondería el efecto del cálculo: el JEF no vería cómo su 输入 mueve Q1..Q4, la final y el semáforo del OKR. Con edición en línea, una fila = un KR, el botón «Guardar» de esa fila envía solo sus celdas modificadas (1..12 ítems, F6) y la respuesta trae **la fila recalculada + el agregado del OKR**, que el JS pinta en el acto (`Guardar` responde 200 con los nuevos `PuntuacionQ1..Q4`, `PuntuacionFinal`, `PuntuacionPonderada`, `Semaforo` y el `CalculoOkr`). Restricciones de diseño (UX-01, sin CSS nuevo): cabeceras de mes abreviadas a 3 letras con `title="Enero"`; el contenedor va en `.table-responsive` (UX-06 a ≥ 768 px) y los inputs usan la clase existente `.form-pe-input`; las celdas no editables se renderizan como texto `—` con `title` explicativo, nunca como input deshabilitado vacío.

**F4 — Proxy MVC (Opción A).**
ADR-016 es ley del proyecto y el bug de HU-023-v2 (`fetch('/api/v1/...')` relativo al MVC → 404) y el Defecto D de HU-022 (`<meta access-token>` con el JWT en el DOM) son exactamente lo que previene. El mismo patrón de HU-022/HU-023 se aplica: acción MVC → `IApiClient.PutAsync/DeleteAsync` → el JWT se adjunta server-side desde la sesión. Ningún archivo `wwwroot/js/*.js` de esta HU contendrá `/api/v1` ni un token, y `JsApiBaseUrlRegressionTests` (con `ExcepcionesConocidas` **vacía**) lo blinda.

**F5 — Una entrada de auditoría por operación (Opción A).**
Un guardado de 12 celdas son 12 filas afectadas; 12 entradas de auditoría serían ilegibles y no aportarían información («mes 3 del KR.1 pasó de 0.4 a 0.5» ya está en el vector). Una entrada con el delta antes/después es más útil para una revisión posterior y es el precedente exacto de HU-025 F4 (`ActualizarPesosAsync` → una entrada con el reparto completo). La granularidad es **la operación del usuario**, no la fila de base de datos. `accion` es determinista: `CREATE` si al menos un mes no tenía fila, `UPDATE` si todas existían (el enum `accion_auditoria` solo admite `CREATE|UPDATE|DELETE|LOGIN|LOGOUT|ACTIVATE|DEACTIVATE` — `V000__schema_base.sql` L42 — no hay acciones libres).

**F6 — Batch por KR (Opción A).**
Un endpoint `PUT .../valores` que acepta de 1 a 12 ítems cubre el guardado de una fila completa y el de una sola celda con el mismo contrato: menos superficie en Swagger, menos código en el MVC, y una **transacción única** por KR (UPSERT de N meses + recálculo + auditoría atómicos). El límite de 12 es natural (`mes` ∈ [1,12]) y descarta de entrada cualquier intento de payload masivo.

**F7 — Navegación por fila (Opción A).**
Mismo criterio que HU-025 F6: los valores mensuales pertenecen a un KR, que pertenece a un OKR. Un ítem global en `_Sidebar` («Valores OKR») no tendría contexto de OKR ni de área. El botón `bi-calendar-month` en la columna «Acciones» de `KeyResult/Index` es el punto de entrada; el icono queda registrado en `docs/07_DESIGN_SYSTEM.md` § 7 como se hizo con `bi-bullseye` en HU-025 F7.

**F8 — Semáforo del KR: calculado, no persistido (Opción A) — resuelta por Jorge el 2026-10-02.**
RF-039 exige «el semáforo de estado **por KR** y por OKR», y RN-027 define la regla de los tres estados. Pero `key_result` (`06_MODELO_DATOS.md` L250-267) **no tiene columna `semaforo`** — solo `okr` la tiene (L234). La causa raíz es que RF-039 no se descomposió en RFs por nivel y la HU-025, que crea la tabla, no lo modeló.
- **Opción A (recomendada)** — el semáforo del KR se evalúa en la BLL con los mismos umbrales y se devuelve en `ValorMensualKrFilaResponse.Semaforo`. Cero desviación del modelo de datos, cero migración, cero ADR, y cumple RF-039 para el JEF que está registrando el valor. HU-027, si el Gerente lo necesita en el consolidado, lo recalcularía en su BLL a partir de `puntuacion_final` ya persistido (misma regla, sin duplicar persistencia).
- **Opción B** — agregar `semaforo semaforo_color NOT NULL DEFAULT 'Rojo'` a `key_result` vía `V0NN__…sql`. **Exige ADR aprobado (DB-01) + migración + RLS/índices verificados**, y abre la pregunta de quién recalcula el semáforo del KR cuando cambia un peso (la ponderación no cambia la final, pero sí… no: la final del KR no depende del peso, así que el semáforo del KR tampoco → la Opción B es *técnicamente* más frágil que parece).

**Resolución (2026-10-02):** Jorge aprobó la **Opción A** — el semáforo del KR se calcula en la BLL y se devuelve en la respuesta, **no se persiste** → sin migración y sin ADR nuevo.

- Doble compuerta SEC-07: `OkrService`/`IOkrRepository.ObtenerPorIdAsync(tenantId, areaId, okrId)` en la BLL (→ 404/403 según corresponda) + `AND okr_id = @OkrId` en **todas** las queries de `valor_mensual_kr` y `key_result`, incluido el `UPDATE` de `okr` que además lleva `AND area_id = @AreaId`.

**Códigos de respuesta HTTP** (ARCH-07): 200 (éxito en los 3 endpoints) · 400 (JSON mal formado) · 401 (no autenticado) · 403 (rol ≠ JefeArea / OKR de otra área) · 404 (OKR, KR, ciclo activo o valor inexistente) · **422** (regla de negocio: ciclo `Cerrado`, mes no editable, mes repetido, lista vacía, valor fuera de escala) · 500 (error interno).

### Helpers compartidos

**`ObtenerOkrConAreaOThrowAsync(Guid okrId)`** — SEC-07:
1. `tenantId = ObtenerTenantIdOThrow()` · `areaId = ObtenerAreaIdOThrow()` (`NotFoundException` si el JEF no tiene área).
2. `_okrRepository.ObtenerPorIdAsync(tenantId, areaId, okrId)` → `null` ⇒ `NotFoundException("El OKR no existe o no pertenece a su área.")` (no se distingue entre inexistente y ajeno: no se filtra información — mismo criterio que `KeyResultService`).
3. Verifica `okr.CicloId == cicloActivo.Id` → si no, `NotFoundException("El OKR no pertenece al ciclo activo.")`.

**`ObtenerVentanaEdicionAsync()`** — F0 + F0c (devuelve `(ciclo, mesMin, mesMax, fechaNegocio, umbrales)`):
1. `_cicloRepository.ObtenerCicloActivoAsync(tenantId)` → `null` ⇒ `NotFoundException("No hay ningún ciclo activo para este tenant.")`.
2. `fechaNegocio = TimeZoneInfo.ConvertTime(_timeProvider.GetUtcNow(), zonaTenant).Date` con `zonaTenant` resuelta por `ResolverZonaHorariaAsync()` (`tenant.zona_horaria` → `TimeZoneInfo.FindSystemTimeZoneById`; si `null`/vacío/inexistente ⇒ `TimeZoneInfo.CreateCustomTimeZone("PE-GOL/PET", OffsetFallbackPeru, …)`).
3. `mesMin = ciclo.MesInicio` · `mesMax` según la tabla de F0.
4. Umbrales: `_cicloRepository.ObtenerUmbralesAsync(tenantId, ciclo.Id)` → fila `Tipo == "KPI"`; ausente ⇒ defaults `0.90/0.70` **en memoria** (patrón HU-008 D5, idéntico a `DashboardService` L77-83).

**`EsMesEditable(int mes, int min, int max)`** → `mes >= min && mes <= max`.

### `ObtenerGrillaAsync(Guid okrId, ct)` — GET (lectura, **sin** bloqueo por RC-12)

1. `tenantId`, `areaId` · `okr = ObtenerOkrConAreaOThrowAsync(okrId)` (**SEC-07**, también en lecturas).
2. `ciclo = ObtenerCicloActivoAsync` · `ventana = await ObtenerVentanaEdicionAsync()` (F0).
3. `krs = await _keyResultRepository.ListarAsync(tenantId, okrId)` (orden `orden ASC, created_at ASC`).
4. `valores = await _repo.ListarPorOkrAsync(tenantId, okrId)` → se indexa por `(keyResultId, mes)`.
5. Por cada KR, construir **12** `ValorMensualKrCeldaResponse` (`m = 1..12`):
   - `Registrado = valores.ContainsKey((krId, m))` · `Valor = …` o `null`.
   - `Editable = EsMesEditable(m, mesMin, mesMax)`.
   - `MotivoBloqueo = null` si `Editable`; si no, `"Mes anterior al inicio del ciclo"` cuando `m < mesMin`, `"Mes aún no ocurrido"` cuando `m > mesMax`.
6. `Semaforo` de la fila = `SemaforoHelper.Evaluar(kr.PuntuacionFinal, umbralVerde, umbralAmarillo)` (**F8: calculado, nunca persistido**).
7. `CalculoOkr` = agregado **persistido** (`okr.PuntuacionFinal`, `okr.Semaforo`) + `KrsConValor = krs.Count(k => k.MesesConValor > 0)`. No se recalcula nada en el GET (DB-04).
8. Mapear a `ValorMensualKrGrillaResponse`.

### `GuardarValoresAsync(Guid okrId, Guid keyResultId, ValorMensualKrUpdateRequest request, ct)` — PUT

1. **Permiso** — `ValidarPermisoEscritura()` (rol `JefeArea` ⇒ si no, `AccesoDenegadoException`).
2. **RC-12 (ciclo)** — `ciclo = ObtenerCicloActivoAsync`; `null` ⇒ 404 «No hay ningún ciclo activo…»; `ciclo.Estado == "Cerrado"` ⇒ `ValidacionException("El ciclo activo se encuentra cerrado. No se pueden registrar valores mensuales.")` (422).
3. **SEC-07 + pertenencia** — `okr = ObtenerOkrConAreaOThrowAsync(okrId)`; `_keyResultRepository.ObtenerPorIdAsync(tenantId, okrId, keyResultId)` → `null` ⇒ 404 «El Key Result no existe o no pertenece a este OKR».
4. **Validación del vector (F6 + CA #1)** —
   - `request.Valores` vacío ⇒ 422 «Debe enviar al menos un valor mensual».
   - `request.Valores.Count > 12` ⇒ 422 «Un KR tiene como máximo 12 meses».
   - **Meses repetidos** ⇒ 422 indicando los duplicados.
   - Cada `Valor`: `0.0 ≤ v ≤ 1.0` y `decimal.Round(v, 1) == v` (escala 1 decimal) ⇒ si no, 422 con el mensaje de `ValorMensualKrItemRequestValidator`.
5. **Ventana editable (F0 — regla dura, CA #2/CA #3)** — `ventana = await ObtenerVentanaEdicionAsync()`; para **cada** ítem: si `!EsMesEditable(mes, mesMin, mesMax)` ⇒ `ValidacionException` con el detalle («El mes 11 (noviembre) aún no ha ocurrido y no puede registrarse»; «El mes 1 (enero) es anterior al inicio del ciclo (mes 3)»). Si la ventana está vacía (`mesMin > mesMax`) ⇒ 422 «El ciclo aún no se ha iniciado; no hay meses editables».
6. **Snapshot previo** — `previos = await _repo.ListarPorKrAsync(tenantId, okrId, keyResultId)` → `Dictionary<int, decimal?>`; se construye `valorAnterior` con **solo** los meses del vector (null si no existían).
7. **Transacción** (`_repo.BeginTransactionAsync`) — **atómica**: N UPSERTs + `UPDATE key_result` + `UPDATE okr` + auditoría.
   - Por cada ítem: `_repo.UpsertAsync(tenantId, keyResultId, mes, valor, usuarioId, tx)` (RC-07 / DB-06). `registrado_por` = `_tenantContext.UserId`; `updated_at = CURRENT_TIMESTAMP`.
8. **Recálculo del KR** — `await RecalcularKeyResultAsync(tenantId, okrId, keyResultId, tx)` (§ siguiente) → `_repo.ActualizarPuntuacionesKrAsync(...)`.
9. **Recálculo del OKR** — `await RecalcularOkrAsync(tenantId, areaId, okrId, umbralVerde, umbralAmarillo, tx)`.
10. **Auditoría (ADR-003 · F5)** — **una** entrada `_repo.InsertLogAsync(new LogAuditoriaInsert { TenantId, UsuarioId = UserId, Accion = algunMesIbaInserte ? "CREATE" : "UPDATE", Entidad = "ValorMensualKR", EntidadId = keyResultId.ToString(), ValorAnterior = json, ValorNuevo = json }, tx)`, donde el JSON es `{ "krId": "…", "codigo": "KR.1", "meses": { "1": 0.5, "3": null→1.0 } }` (solo los meses del vector).
11. `tx.Commit()`.
12. Respuesta: releer la fila (`_keyResultRepository.ObtenerPorIdAsync` + `ListarPorKrAsync`) y devolver `ValorMensualKrGuardarResponse` con `Semaforo` recalculado en memoria (F8) y `CalculoOkr` con los valores persistidos.
13. **Capa 2 (defensa en profundidad)**: `PostgresException 23505` en el UPSERT ⇒ `ValidacionException("Conflicto al registrar el valor del mes. Intente de nuevo.")` · `23514` (`CHECK`) ⇒ `ValidacionException("Valor fuera del rango permitido (0.0–1.0).")` · cualquier otra ⇒ `Rollback` + rethrow.

### `EliminarValorAsync(Guid okrId, Guid keyResultId, int mes, ct)` — DELETE

1. **Permiso** — `ValidarPermisoEscritura()`.
2. **RC-12** — idéntico al paso 2 del PUT (ciclo `Cerrado` ⇒ 422).
3. **SEC-07 + pertenencia** — `ObtenerOkrConAreaOThrowAsync(okrId)` + `ObtenerPorIdAsync` del KR (404).
4. **`mes` ∈ [1,12]** ⇒ fuera de rango, 422 (no 404: es un error de contrato del request, no de estado).
5. **Existencia** — `_repo.ObtenerValorAsync(tenantId, keyResultId, mes)` → `null` ⇒ `NotFoundException("No hay un valor registrado para ese mes.")`.
   **No se revalida la ventana editable**: por el argumento de F0.2 toda fila existente pertenece a una ventana que ya fue válida y la frontera solo avanza.
6. **Transacción** — `_repo.EliminarAsync(...)` → recálculo de KR → recálculo de OKR → auditoría `accion = "DELETE"`, `ValorAnterior = { mes, valor }`, `ValorNuevo = null` → `Commit`.
7. Respuesta `ValorMensualKrGuardarResponse` (misma forma que el PUT).

### `RecalcularKeyResultAsync(tenantId, okrId, keyResultId, tx)` — el corazón del cálculo (DB-04)

Trabaja **íntegramente en memoria** a partir de las filas de `valor_mensual_kr` del KR, y **persiste** al final (1 solo `UPDATE`).

```
1.  valores = ListarPorKrAsync(tenantId, okrId, keyResultId)          // 0..12 filas
2.  porMes  = valores.ToDictionary(v => v.Mes, v => v.Valor)
3.  for q in 1..4:
4.      mesesTrimestre = (q*3-2 .. q*3)                                // Q1=1-3, Q2=4-6, Q3=7-9, Q4=10-12
5.      conValor = mesesTrimestre.Where(m => porMes.ContainsKey(m))
6.      puntuacionQ[q] = conValor.Any()
7.                          ? Math.Round(conValor.Sum() / conValor.Count(), 3, MidpointRounding.AwayFromZero)   // RN-025: promedio de los meses CON VALOR
8.                          : 0.000m                                                                              // trimestre sin datos
9.  trimestresConDatos = [1..4] donde puntuacionQ tiene al menos un mes con valor
10. puntuacionFinal = trimestresConDatos.Any()
11.                     ? Math.Round(trimestresConDatos.Average(), 3, MidpointRounding.AwayFromZero)              // F1 Opción B
12.                     : 0.000m
13. puntuacionPonderada = Math.Round(puntuacionFinal * peso, 3, MidpointRounding.AwayFromZero)                     // RF-037
14. _repo.ActualizarPuntuacionesKrAsync(tenantId, okrId, keyResultId, q1..q4, final, ponderada, tx)
```

> `MidpointRounding.AwayFromZero` es obligatorio (no el `ToEven` por defecto): con valores de 1 decimal, `0.05 + 0.15 = 0.20 / 2 = 0.10` es exacto, pero `(0.1+0.1+0.2)/3 = 0.13333…` debe ir a `0.133` y no a `0.134`. El redondeo explícito elimina la ambigüedad y hace los tests deterministas.

### `RecalcularOkrAsync(tenantId, areaId, okrId, umbralVerde, umbralAmarillo, tx)`

```
1.  krs = _keyResultRepository.ListarAsync(tenantId, okrId)              // peso + puntuacion_ponderada persistidos
2.  okrPuntuacionFinal = Math.Round(krs.Sum(k => k.PuntuacionPonderada), 3, MidpointRounding.AwayFromZero)   // RN-026: Σ ponderadas
3.  okrSemaforo        = SemaforoHelper.Evaluar(okrPuntuacionFinal, umbralVerde, umbralAmarillo)               // RN-027, bordes inclusivos
4.  _okrRepository.ActualizarPuntuacionAsync(tenantId, areaId, okrId, okrPuntuacionFinal, okrSemaforo, tx)
```

**Tipo de umbral (decisión documentada, verificada en `V000__schema_base.sql` L32):** el enum `tipo_umbral` solo admite **`KPI`** y **`PlanAccion`** — no existe un tipo `OKR`. Los OKRs son indicadores de gestión y `DashboardService` L116 **ya** evalúa el semáforo global de OKRs con los umbrales `KPI` (`SemaforoHelper.Evaluar(resumenOkrs.PromedioPuntuacionOkrs, umbralKpiVerde, umbralKpiAmarillo)`). Reutilizar `KPI` mantiene una **fuente única de umbrales** y no requiere migración ni ADR. Si Jorge quiere umbrales independientes para OKR, eso sería una extensión de HU-008 con su propio ADR (`ALTER TYPE tipo_umbral ADD VALUE 'OKR'` + fila por ciclo) — **no** se incluye en esta HU.

### DAL-1 · `ListarPorOkrAsync(tenantId, okrId)` — todos los valores de todos los KRs del OKR

```sql
SELECT vmk.key_result_id    AS KeyResultId,
       vmk.mes              AS Mes,
       vmk.valor            AS Valor,

       vmk.updated_at       AS UpdatedAt
FROM valor_mensual_kr vmk
INNER JOIN key_result kr ON kr.id = vmk.key_result_id
WHERE vmk.tenant_id = @TenantId
  AND kr.tenant_id = @TenantId
  AND kr.okr_id    = @OkrId          -- SEC-07 (doble compuerta: okr_id verificado en BLL)

```

### DAL-2 · `ListarPorKrAsync(tenantId, okrId, keyResultId)` — los 12 meses de un KR

### DAL-3 · `UpsertAsync(tenantId, keyResultId, mes, valor, usuarioId, tx)` — **RC-07 / DB-06**

```sql
INSERT INTO valor_mensual_kr (tenant_id, key_result_id, mes, valor, registrado_por, updated_at)
VALUES (@TenantId, @KeyResultId, @Mes, @Valor, @UsuarioId, CURRENT_TIMESTAMP)
ON CONFLICT (key_result_id, mes) DO UPDATE
    SET valor         = EXCLUDED.valor,
        registrado_por = EXCLUDED.registrado_por,
        updated_at     = CURRENT_TIMESTAMP
RETURNING id, valor, registrado_por, updated_at;
```

> `ON CONFLICT (key_result_id, mes)` usa el `UNIQUE` del DDL base (L277). **Nunca** `SELECT` + `UPDATE` separados (DB-06 explícito). `EXCLUDED` es el idioma estándar de PostgreSQL para el nuevo valor propuesto.

### `ValorMensualKrUpdateRequestValidator`

```csharp
public class ValorMensualKrUpdateRequestValidator
    : AbstractValidator<ValorMensualKrUpdateRequest>
{
    public ValorMensualKrUpdateRequestValidator()
    {
        RuleFor(x => x.Valores)
            .NotNull().WithMessage("Debe enviar la lista de valores mensuales.")
            .Must(l => l is not null && l.Count is >= 1 and <= 12)
            .WithMessage("Debe enviar entre 1 y 12 valores (los meses del KR).");

        RuleForEach(x => x.Valores).ChildRules(item =>
        {
            item.RuleFor(x => x.Mes)
                .InclusiveBetween(1, 12)
                .WithMessage("El mes debe estar entre 1 (enero) y 12 (diciembre).");

            // RF-035 / RN-024: escala 0.0–1.0
            item.RuleFor(x => x.Valor)
                .InclusiveBetween(0.0m, 1.0m)
                .WithMessage("El valor debe estar entre 0.0 y 1.0.");

            // RN-024: «hasta 1 decimal» (columna DECIMAL(2,1))
            item.RuleFor(x => x.Valor)
                .Must(v => decimal.Round(v, 1, MidpointRounding.ToZero) == v)
                .WithMessage("El valor admite como máximo 1 decimal (por ejemplo 0.5).");

            // F6: un valor por mes (mismo requisito que UNIQUE (key_result_id, mes))
            item.RuleFor(x => x.Mes)
                .Must((parent, mes) => parent.Valores.Count(v => v.Mes == mes) == 1)
                .WithMessage("No se puede enviar el mismo mes más de una vez.");
        });
    }
}
```

Arreglado leyendo `okrId` y los KRs de `data-*` del DOM (patrón de `okrs.js`, ADR-016) y mandando el vector form-encoded.
