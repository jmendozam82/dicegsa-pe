## Endpoints

| Método | Ruta | Auth | Descripción |
|--------|------|------|-------------|
| `GET` | `/api/v1/acciones/gantt` | JWT · `[Authorize(Roles = "JefeArea,Gerente")]` | Datos del Gantt del plan de acción del **ciclo activo** del tenant: 12 meses de escala, grupos (Objetivos CG) y acciones planas. **Solo lectura.** |

- Controller: `PE-GOL.API/Controllers/AccionPlanController.cs` (`[Route("api/v1/acciones")]`, `[Authorize]` de clase) — se **agrega** `[HttpGet("gantt")]`. No hay colisión de rutas: `{id:guid}` exige GUID y `gantt` es un segmento literal (`MEDIO-02` de la auditoría, cerrado en ADR-010, se mantiene intacto).
- **Sin body y sin query string** (SEC-06). El `tenant_id` viene del `TenantContext` (claims del JWT) y el `ciclo_id` se resuelve en BLL con DAL-D1 (`ciclo.estado = 'Activo' LIMIT 1`, RC-01). Patrón idéntico a HU-015/HU-016.
- Respuesta siempre con wrapper `ApiResponse<GanttPlanResponse>` (**ARCH-07**). Códigos: `200` · `401` · `403` · `404` · `500`.
  - `403` → rol ∉ {JefeArea, Gerente} (atributo) **o** rol `JefeArea` sin `area_id` en el JWT (defensivo en BLL, paso 3).
  - `404` → sin `tenant_id` en el contexto, o no hay ciclo `Activo` para el tenant.
  - `200` con payload **vacío** (grupos y acciones vacíos, conteos en 0) cuando el ciclo no tiene acciones — la vista responde con `.empty-state` (**UX-05**), no con 404.
- **Swagger (ARCH-03):** `[ProducesResponseType(typeof(ApiResponse<GanttPlanResponse>), 200)]` + 403/404/500, y descripción de la acción con los 4 roles/tipos de payload (patrón del resto de controllers).

**No se agregan endpoints de escritura.** HU-021 no toca `POST/PUT/PATCH/DELETE /api/v1/acciones/**`.

### Response — `GanttPlanResponse` (`PE-GOL.DTO/Responses/PlanOperativo/`)

```csharp
public class GanttPlanResponse
{
    public Guid CicloId { get; set; }
    public string CicloNombre { get; set; } = string.Empty;   // "PE 2026"
    public int AñoFiscal { get; set; }                        // ciclo.año_fiscal
    public int MesInicio { get; set; }                        // ciclo.mes_inicio (1..12)

    /// <summary>Primer día del ciclo — base de la escala y de gantt.config.min_date.</summary>
    public DateTime FechaInicioCiclo { get; set; }

    /// <summary>Último día del ciclo — gantt.config.max_date (CicloFechaHelper.ObtenerRango).</summary>
    public DateTime FechaFinCiclo { get; set; }

    /// <summary>CA #1 — exactamente 12 meses, desde MesInicio inclusive.</summary>
    public List<GanttMesResponse> Escala { get; set; } = new();

    /// <summary>CA #3 — un grupo por Objetivo CG **que tenga al menos una acción**.</summary>
    public List<GanttGrupoResponse> Grupos { get; set; } = new();

    /// <summary>Acciones planas; cada una referencia su grupo por ObjetivoCgId.</summary>
    public List<GanttAccionResponse> Acciones { get; set; } = new();

    /// <summary>RF-031 parcial — totales por status. Las 4 claves siempre presentes (0 si no hay).</summary>
    public Dictionary<string, int> ConteoPorStatus { get; set; } = new();
}

public class GanttMesResponse
{
    public int Anio { get; set; }
    public int Mes { get; set; }              // 1..12
    public string Etiqueta { get; set; } = string.Empty;   // "ENE 2026" (CAE #1)
}

public class GanttGrupoResponse
{
    public Guid ObjetivoCgId { get; set; }
    public string Codigo { get; set; } = string.Empty;      // "GOL1.CG1"
    public string Descripcion { get; set; } = string.Empty;
    public Guid AreaId { get; set; }
    public string AreaCodigo { get; set; } = string.Empty;  // "GOL1"
    public string AreaNombre { get; set; } = string.Empty;  // "CEDIS FARMA"
    public decimal Progreso { get; set; }                   // LÍDO de objetivo_cg.progreso (DB-04) — escala 0..1 (DECIMAL(5,4)), NO 0..100
    public string Semaforo { get; set; } = string.Empty;    // LÍDO de objetivo_cg.semaforo (DB-04) — "Verde"|"Amarillo"|"Rojo"
    public int TotalAcciones { get; set; }                 // calculado en BLL (DB-04)
}

public class GanttAccionResponse
{
    public Guid Id { get; set; }
    public Guid ObjetivoCgId { get; set; }
    public Guid AreaId { get; set; }
    public string Codigo { get; set; } = string.Empty;      // "GOL1.CG1.03"
    public string Descripcion { get; set; } = string.Empty;
    public DateTime FechaInicio { get; set; }
    public DateTime FechaVencimiento { get; set; }
    public decimal Progreso { get; set; }                   // LÍDO (DB-04), 0..100 (DECIMAL(5,2) con CHECK 0..100)
    public string Status { get; set; } = string.Empty;      // LÍDO: NoIniciado|EnProgreso|Terminado|Atrasado
    public string Clasificacion { get; set; } = string.Empty;   // Proyecto|Iniciativa|Operativa
    public string TipoPresupuesto { get; set; } = string.Empty; // OPEX|CAPEX
    public decimal Peso { get; set; }                       // LÍDO, 0.001..1 (DECIMAL(4,3)) — es un factor, NO un porcentaje
    public string? ResponsableNombre { get; set; }          // LEFT JOIN usuario (puede ser null)
    public int Orden { get; set; }
}
```

> **Ojo con la escala del `Progreso` del CG:** `accion_plan.progreso` es `DECIMAL(5,2)` con `CHECK (progreso BETWEEN 0.00 AND 100.00)` → **0..100**; `objetivo_cg.progreso` es `DECIMAL(5,4)` → **0..1**. Los DTOs los exponen **tal cual** (D-M, sin transformar en BLL) y es el front quien formatea: `Math.round(g.progreso * 100) + '%'` para el CG y `a.progreso + '%'` para la acción. El `Peso` (0.001..1) **no** se muestra como porcentaje en ningún lado. Mezclar ambas escalas en el mismo tooltip sin esta regla mostraría "0.35%" donde debe decir "35%".

**Vocabulario (alineado con el código real, no con el DDL en prosa):** los valores de `Status`, `Clasificacion` y `TipoPresupuesto` viajan como **`Enum::text` de PostgreSQL** — exactamente las cadenas que ya usa `AccionPlanService.CalcularStatus` y que ya devuelve `AccionPlanResponse` (`"NoIniciado"`, `"EnProgreso"`, `"Terminado"`, `"Atrasado"`; `"Proyecto"`, `"Iniciativa"`, `"Operativa"`; `"OPEX"`, `"CAPEX"`). No se inventan alias ni enums nuevos; los `<select>` de filtros se construyen con estas literales.

**No incluir `TenantId` en ningún DTO** (SEC-06) — ver tests 23 y 26.

## Lógica BLL (paso a paso)

Servicio: `PE-GOL.BLL/Services/AccionPlanService.cs` — se **extiende** con `ObtenerGanttAsync` (misma clase, mismo ctor; patrón aditivo de HU-020). `IAccionPlanService` suma el método; **las 7 firmas existentes quedan intactas**. La BLL retorna el DTO plano y el controller envuelve en `ApiResponse<T>` (**ADR-010 Decisión 1** — la BLL nunca conoce `ApiResponse<T>`).

```
Task<GanttPlanResponse> ObtenerGanttAsync(CancellationToken ct = default)
```

1. **Tenant (SEC-06):** `tenantId = ObtenerTenantIdOThrow()` — helper privado **existente** en `AccionPlanService` (L324-329). `null` → `NotFoundException` → **404**.
2. **Rol (RN-007/RN-006, doble capa):** si `_tenantContext.Rol` ∉ {`JefeArea`,`Gerente`} → `AccesoDenegadoException` → **403**. El atributo `[Authorize(Roles="JefeArea,Gerente")]` ya lo bloquea en la API; la re-validación en BLL protege el caso de invocación desde otra capa (patrón D12 de HU-015).
3. **Filtro de área (SEC-07):** `areaIdFiltro = (Rol == "JefeArea") ? _tenantContext.AreaId : null`. Si `Rol == "JefeArea"` y `AreaId` es `null` → `AccesoDenegadoException` → **403** (JWT sin `area_id`: se trata como acceso denegado, no como "todas las áreas" — nunca se degrada el filtro).
4. **Ciclo activo (RC-01):** `ciclo = await _cicloRepository.ObtenerCicloActivoAsync(tenantId, ct)` (DAL-D1 de HU-015, reuso sin cambios). `null` → `NotFoundException("No hay un ciclo activo para el tenant")` → **404** (mensaje idéntico a HU-015/HU-016).
5. **Datos (1 sola query):** `acciones = await _repository.ListarParaGanttAsync(tenantId, ciclo.Id, areaIdFiltro, ct)` (DAL-G1). Lista plana con los metadatos de CG y área por JOIN. **Sin paginación** (D-E) y **sin parámetros de filtro del cliente**.
6. **Sin acciones → no es un error:** si `acciones` viene vacía se construye y retorna el payload con `Grupos = []`, `Acciones = []`, `Escala` de 12 meses (el ciclo sí existe) y los 4 conteos en `0` → **200**. La vista decide el `.empty-state` (UX-05). Patrón D-B/D-N de HU-016.
7. **Agrupar en BLL (CA #3, DB-04):** `Grupos` = CGs **distintos** presentes en las filas, ordenados por `objetivo_orden ASC, objetivo_codigo ASC` (los mismos campos por los que llega la lista). `TotalAcciones` = número de acciones del grupo **contadas en BLL sobre las filas** (no un `COUNT` en SQL). Los CGs sin acciones **no aparecen** (el Gantt agrupa lo que hay).
8. **Conteo por status (RF-031 parcial, DB-04):** `ConteoPorStatus` se cuenta en BLL agrupando las filas por `Status`. Las 4 claves (`NoIniciado`, `EnProgreso`, `Terminado`, `Atrasado`) se inicializan en `0` y luego se sobrescriben — **nunca faltan claves** (el front no debe adivinar).
9. **Escala de 12 meses (CA #1):** con `base = new DateTime(ciclo.AñoFiscal, ciclo.MesInicio, 1)`, para `i` en `0..11`: `mes = base.AddMonths(i)` → `GanttMesResponse { Anio = mes.Year, Mes = mes.Month, Etiqueta = $"{ABREV[mes.Month-1]} {mes.Year}" }` con `ABREV = [ENE, FEB, MAR, ABR, MAY, JUN, JUL, AGO, SEP, OCT, NOV, DIC]` (AS-IS L125). Con `mes_inicio ≠ 1` la escala **cruza de año** (p. ej. `JUN 2026 … MAY 2027`) y por eso la etiqueta siempre lleva el año.
10. **Rango del ciclo:** `var (inicio, fin) = CicloFechaHelper.ObtenerRango(ciclo.AñoFiscal, ciclo.MesInicio)` — helper **existente** (`PE-GOL.Utility/Helpers/CicloFechaHelper.cs`, usado ya por `ValidarFechasCicloAsync`). **Ojo con los tipos:** `ObtenerRango` devuelve `(DateOnly Inicio, DateOnly Fin)`; la conversión es explícita: `FechaInicioCiclo = inicio.ToDateTime(TimeOnly.MinValue)` y `FechaFinCiclo = fin.ToDateTime(TimeOnly.MinValue)`. Se usa `TimeOnly.MinValue` (medianoche del último día) porque `FechaFinCiclo` viaja a `gantt.config.max_date` como fecha, no como límite de comparación; `ValidarFechasCicloAsync` (L66) usa `TimeOnly.MaxValue` porque ahí sí compara instantes. **No se crea utility nuevo** ni ADR ni se modifica el helper.
11. **Mapear y retornar `GanttPlanResponse`.** Los valores de `Progreso`, `Status`, `Grupo.Progreso` y `Grupo.Semaforo` se **copian tal cual** de la BD (D-M: no se recalculan). **Sin auditoría**: `AccionPlanService` **no tiene** dependencia de `ILogAuditoriaRepository` (verificado en sus 2 constructores, L26-48), así que "no audita" es estructural — y como `IAccionPlanRepository` tampoco expone `InsertLogAsync`, no hay forma de auditar desde aquí (test 22 lo fija por reflexión) · **sin transacción** · **sin escrituras de ningún tipo**.

**"Solo lectura" — justificación (requisito 2 del encargo):** el drag & drop de DHTMLX está activo por defecto en la librería; se **desactiva explícitamente** en la vista (D-R) y, sobre todo, la vista **no tiene ninguna ruta de escritura**: el `AccionPlanController` (MVC) de esta pantalla solo hace `GET`, y el endpoint de la API es de solo lectura. Las razones para no persistir el arrastre de barra:
1. **Bypass de validación.** Mover una barra cambiaría `fecha_inicio`/`fecha_vencimiento` saltándose RN-019 (`fecha_vencimiento >= fecha_inicio`), RN-021 (dentro del año fiscal del ciclo) y el `CHECK (fecha_vencimiento >= fecha_inicio)` del DDL solo si el cliente valida; el `PUT /api/v1/acciones/{id}` de HU-019 valida todo eso en BLL y es la **única** vía autorizada de edición de fechas.
2. **Auditoría y trazabilidad.** El contrato ADR-003 exige registrar `log_auditoria` con snapshot en cada escritura. Un arrastre de barra que no pase por la BLL deja cambios sin rastro; un `PUT` por arrastre además debería re-evaluar RN-016 (suma de pesos) y recalcular el status (RN-017) y el progreso/semáforo del CG (RN-018) como hace HU-020.
3. **HU-021 es una HU de visualización.** Sus 5 CA son de lectura (escala, color, agrupación, tooltip, filtros). Persistir desde el arrastre es alcance de una HU nueva (ver F9).
4. **Coherencia de UX.** El JEF ya tiene el formulario de edición (HU-019 `AccionPlan/Editar/{id}`, contrato intacto) con validación de servidor como fuente de verdad (UX-04).

**DAL-G1** — un único `SELECT`, **todos los valores parametrizados** (SEC-05), `WHERE tenant_id` primero (SEC-06), filtro de área en SQL (SEC-07). Patrón de filtro idéntico a DAL-A3/DAL-R3 (`(@AreaIdFiltro IS NULL OR …)`) — sin concatenación de SQL:

```sql
SELECT a.id             AS id,
       a.objetivo_cg_id AS objetivo_cg_id,
       a.area_id        AS area_id,
       a.codigo         AS codigo,
       a.descripcion    AS descripcion,
       a.fecha_inicio   AS fecha_inicio,
       a.fecha_vencimiento AS fecha_vencimiento,
       a.clasificacion::text    AS clasificacion,
       a.tipo_presupuesto::text AS tipo_presupuesto,
       a.peso           AS peso,
       a.progreso       AS progreso,
       a.status::text   AS status,
       a.orden          AS orden,
       u.nombre         AS responsable_nombre,
       oc.orden         AS objetivo_orden,
       oc.codigo        AS objetivo_codigo,
       oc.descripcion   AS objetivo_descripcion,
       oc.progreso      AS objetivo_progreso,
       oc.semaforo::text AS objetivo_semaforo,
       ar.codigo        AS area_codigo,
       ar.nombre        AS area_nombre
FROM accion_plan a
JOIN objetivo_cg oc ON oc.id = a.objetivo_cg_id AND oc.tenant_id = a.tenant_id
JOIN area ar         ON ar.id = a.area_id        AND ar.tenant_id = a.tenant_id
LEFT JOIN usuario u  ON u.id = a.responsable_id
WHERE a.tenant_id = @TenantId
  AND a.ciclo_id  = @CicloId
  AND (@AreaIdFiltro IS NULL OR a.area_id = @AreaIdFiltro)
ORDER BY oc.orden ASC, oc.codigo ASC, a.orden ASC, a.codigo ASC;
```

**Notas de DAL-G1:**
- **No se hace JOIN a `ciclo`**: los metadatos del ciclo (`año_fiscal`, `mes_inicio`) llegan por DAL-D1 con `CicloEntity`; así se evita además el alias con `ñ` (`año_fiscal`).
- Los `JOIN` a `objetivo_cg` y `area` llevan **también** la condición de tenant (aislamiento por si un id quedara cruzado; además la `RLS` de ambas tablas ya filtra — ADR-009: funciones de RLS en `public.*`).
- Los alias en `snake_case` resuelven por `MatchNamesWithUnderscores = true` (Dapper), igual que `a.*` con `AccionPlanEntity`.
- `LEFT JOIN usuario` → `ResponsableNombre` puede venir `null` (el `responsable_id` es nullable en el DDL L293 y desde `ea14558` es opcional en el formulario). Se tolera `null` en cliente (`—`).
- Los enums se proyectan **`::text`** (mismo criterio que `ObtenerPorIdAsync`/`ListarPorObjetivoCgAsync` de HU-019) para que Dapper los desserialice en `string`.
- **No hay `SELECT COUNT`, ni `SUM`, ni `FILTER`, ni `CASE` de negocio**: los campos derivados (`TotalAcciones`, `ConteoPorStatus`, `Escala`) se calculan en BLL (**DB-04**).
- **Índice (F3 → RESUELTO, ADR-012 Aceptado 2026-09-27):** el DDL actual solo tiene `idx_accion_plan_objetivo(objetivo_cg_id)`, `idx_accion_plan_area(area_id)` e `idx_accion_plan_status(status)` — **ninguno cubre `tenant_id` + `ciclo_id`**, que es el filtro real de esta query. Se crea la migración versionada **`db/migrations/V005__indice_accion_plan_gantt.sql`** (pendiente de ejecución):
  ```sql
  CREATE INDEX IF NOT EXISTS idx_accion_plan_ciclo_area
      ON accion_plan (tenant_id, ciclo_id, area_id);
  ```
   El prefijo `(tenant_id, ciclo_id)` cubre el caso Gerente (filtro por ciclo) y la tercera columna `area_id` cubre el caso JefeArea (`tenant_id + ciclo_id + area_id`): un solo índice para ambos roles. Respaldo: **ADR-012** (Aceptado) exigido por DB-01/DB-02; alta pendiente en `06_MODELO_DATOS.md` § 7 junto a V001–V004.
- **RLS:** `accion_plan_policy` (06 L532-539) ya deja pasar al rol `Gerente` y restringe por `area_id` al resto; la DAL aplica además su propio filtro (capa 2, ARCH-04). El DAL usa la conexión `service_role` (BYPASSRLS) según ADR-008 → **la seguridad no depende de la RLS**, depende de `areaIdFiltro` (SEC-07), que por eso es obligatorio y testeado.

## Validaciones FluentValidation

**No aplica.** El endpoint es `GET` sin body y sin query params (SEC-06), por lo que no hay DTO de entrada que validar — patrón idéntico a HU-016. **No se crea ningún validator nuevo.**

### 4. Estructura del payload hacia DHTMLX (`data` + `links` + `parse` en cliente)

**Decisión D-E/H: la API devuelve DTOs del dominio; la conversión al formato DHTMLX ocurre en `gantt-plan.js`.** El payload crudo de la API **no** filtra el formato de una librería de terceros: si mañana se cambia la librería, el contrato de la API no cambia (HU-023 y los reportes reutilizarán los mismos datos). Además, con esta decisión **no se depende de la carga dinámica** (función PRO).

- El controller MVC (`AccionPlanController.Gantt`) llama **una vez** a `GET /api/v1/acciones/gantt` vía `IApiClient` (patrón D-3 de HU-019/HU-045: MVC full page load, sin AJAX, sin JWT en el navegador) y **serializa el resultado dentro de la vista**:
  ```html
  <script id="gantt-plan-data" type="application/json">@Html.Raw(Model.JsonPlan)</script>
  ```
  `Model.JsonPlan` se genera en el controller con `System.Text.Json` usando el **`JavaScriptEncoder.Default`** (el que escapa `<`, `>`, `&` a `\u003C`…). **Prohibido `UnsafeRelaxedJsonEscaping`**: el patrón de ADR-003 aplica solo a los snapshots de `log_auditoria` en BD, nunca a JSON embebido en HTML (SEC-05 / XSS).
- Conversión en `gantt-plan.js` (`construirTareasDhtmlx(datos)`), **en memoria, sin red**:
  ```js

  { id: 'cg-' + g.objetivoCgId, text: g.codigo + ' · ' + g.descripcion,
    type: 'project',            // barra resumen, sin fechas propias
    parent: 0,
  ```

### 5. Escala mensual de 12 meses (CA #1)

```js

  { unit: 'year',  step: 1, format: function (d) { return d.getFullYear(); } },
```

### 9. Filtros (CA #5 + selector de área del Gerente — F6) — cliente, sobre el payload ya cargado

**Cuatro** selectores en una `card-pe` (componentes `.form-pe-label` / `.form-pe-select` del DS § 5.6, igual que el selector de CG de `AccionPlan/Index`), con `id` `filtroObjetivoCg`, `filtroStatus`, `filtroClasificacion`, **`filtroArea`**, más un botón **Limpiar filtros**:

- Opciones de CG: las de `Grupos` (`codigo — descripcion`, con `areaCodigo` delante si el usuario es Gerente).
- Opciones de status: `Terminado`, `EnProgreso`, `Atrasado`, `NoIniciado` (literales del enum, ver § DTOs).
- Opciones de clasificación: `Proyecto`, `Iniciativa`, `Operativa`.
- **Opciones de área (`filtroArea`) — requisito de UI aprobado por Jorge (F6):**
  - **Se construye dinámicamente en `gantt-plan.js`** a partir de los **grupos del payload** (`datos.grupos`), **no** desde una lista hardcodeada ni desde un endpoint adicional. Se deduplican por `areaId` conservando el orden de aparición en `grupos`.
  - **Etiqueta exacta de cada opción:** `g.areaCodigo + ' — ' + g.areaNombre` (p. ej. `GOL1 — CEDIS FARMA`).
  - Se renderiza **solo si el rol es `Gerente`**; con rol `JefeArea` el selector no se renderiza (su payload tiene una sola área por SEC-07 y filtrar por área no aportaría nada).
  - Al filtrar por área, se descartan tanto las **acciones** cuyo `areaId` no coincida como los **grupos** (CG) cuya `areaId` no coincida; los padres `type:"project"` supervivientes se incluyen solo si al menos una hija pasa el filtro.
  - Combina con los otros tres filtros por conjunción (AND) dentro del mismo `aplicarFiltros()`.

```js
// gantt-plan.js — construcción dinámica del selector de área (F6)
function poblarFiltroArea(grupos, esGerente) {
    if (!esGerente) return [];                       // JefeArea: no se renderiza
    const vistos = new Set();
    const opciones = [];
    grupos.forEach(function (g) {
        if (vistos.has(g.areaId)) return;
        vistos.add(g.areaId);
        opciones.push({ value: g.areaId, label: g.areaCodigo + ' — ' + g.areaNombre });  // etiqueta exacta
    });
    return opciones;
}
```

- Al cambiar cualquiera: `aplicarFiltros()` recalcula el conjunto en memoria y hace `gantt.parse({ data: tareasFiltradas, links: [] })`. Los padres (`type:"project"`) se **incluyen solo si al menos una hija sobrevive al filtro**; el resto se descarta. No hay llamada a la API.
- Si el filtro deja **0 acciones**: dentro de la `card-pe` del Gantt se muestra el estado vacío `.empty-state` con el mensaje "Ninguna acción coincide con los filtros" y botón **Limpiar filtros** (UX-05), en vez de un Gantt vacío.

**Por qué cliente y no servidor (D-E):** el payload es una sola query de un ciclo acotado (≤ 200 acciones, la escala de datos de RNF-004); filtrar en memoria es instantáneo, no añade round-trips, no introduce un segundo contrato de endpoint ni parámetros de cliente que auditar (SEC-06), y evita repetir el filtro en tres capas. El selector de área de F6 **no contradice** este criterio: los datos de todas las áreas **ya vienen** en el payload del Gerente (D-F) — el filtro es puramente de presentación.

**Evolución futura documentada (F10 — resuelta por Jorge):** si un tenant superara **~500 acciones por ciclo**, se agreegan **paginación y filtros por query string** al endpoint, **sin romper el contrato actual**: `GET /api/v1/acciones/gantt` **sin parámetros sigue siendo válido** y devuelve el mismo payload; los parámetros `page`/`size` (y los filtros) son **opcionales** y con **valores por defecto** que reproducen el comportamiento actual. Es una evolution aditiva, no un cambio de contrato. Ver § «Extensión futura — paginación y filtros en servidor (F10)».

## Extensión futura — paginación y filtros en servidor (F10, resuelta por Jorge 2026-09-27)

> Registro textual de la resolución de **F10**. **No es alcance de esta HU**; queda como evolution documentada para que ninguna HU futura rompa el contrato vigente.

**Umbral fijado por Jorge:** los filtros son de cliente y el payload no se pagina mientras un tenant **no supere ~500 acciones por ciclo** (el volumen de referencia del proyecto es de 200 acciones, RNF-004).

**Qué pasa si se supera el umbral:** se agregan **paginación y filtros por query string** al endpoint `GET /api/v1/acciones/gantt`, y los filtros de cliente del § UI punto 9 pasan a delegar en el servidor.

**Garantía de no ruptura del contrato actual (requisito explícito de F6/F10):**

- `GET /api/v1/acciones/gantt` **sin parámetros sigue siendo una petición válida** y sigue devolviendo el mismo `ApiResponse<GanttPlanResponse>` con el payload completo.
- Los nuevos parámetros (`page`, `size` y los filtros) son **todos opcionales** y tienen **valores por defecto** que reproducen exactamente el comportamiento actual (`page = 1`, `size = ∞`/sin límite, sin filtros) → un cliente que no los envía obtiene el payload idéntico al de hoy.
- Es una **evolution aditiva**: no se elimina ni se renombra ningún campo de `GanttPlanResponse`, y ningún parámetro nuevo es obligatorio. SEC-06 se mantiene: ningún parámetro de tenant (`tenant_id`) ni de aislamiento por rol puede entrar por query string — el `area_id` del Jefe de Área sigue resolviéndose **solo** desde el `TenantContext` (SEC-07).
- Cuando entre, requerirá su propio validator FluentValidation, sus casos de prueba de SEC-07 y alta en `06_MODELO_DATOS.md` si afecta al índice.

> **Única excepción, autorizada por @Arquitecto y aplicada por @Documenter en el cierre del 2026-09-27:** el bloque de **F1** y la fila **F1** de § «Resolución de flags» recibieron una **corrección de transcripción** (no de decisión) para reflejar la procedencia realmente aplicada — Community **MIT** `v10.0.3` desde el **registro oficial de npm**, **8 temas visuales integrados** (no «7 skins») y la corrección de la premisa de licencia del paquete npm. > **F1 — Licencia de DHTMLX Gantt (BLOQUEANTE — condiciona STACK-07).**
> `STACK-07` fija "DHTMLX Gantt versión Open Source", pero hoy ese "Open Source" **no es una sola cosa**:
> - **Opción A — Community Edition, licencia MIT** (`github.com/DHTMLX/gantt`, `LICENSE.md` = MIT, disponible desde Gantt **10.0**; última estable **v10.0.3**, 2026-09-03). Incluye todo lo que HU-021 necesita: jerarquía padre/hijo, milestone, vista de proyecto, edición inline, drag & drop, escalas personalizadas, **8 temas visuales**, zoom, smart rendering (30 000+ tareas), import/export XML/JSON, accesibilidad y responsive. **No** incluye (y no se necesita): gestión de recursos, auto-scheduling, ruta crítica, agrupamiento WBS, carga dinámica, elementos custom en la línea de tiempo, WBS codes, export a PDF/Excel sin marca de agua. **Impacto:** ninguna obligación de licencia (solo conservar el aviso de MIT), usable en un SaaS propietario. **Riesgo (premisa corregida en el cierre del 2026-09-27):** cuando se escribió este texto se sabía que «el paquete npm `dhtmlx-gantt` sigue etiquetado GPL-2.0 (v9.1.4) y puede ser un build distinto». **Verificado y desmentido para `10.0.3`:** el tarball `dhtmlx-gantt@10.0.3` del **registro oficial de npm** trae `LICENSE.md` = **MIT** y el bundle `codebase/`; la etiqueta GPL-2.0 era de la rama `v9.1.4` y por eso se propuso el release de GitHub, que resultó **inejecutable** (no incluye el bundle). Procedencia adoptada en ADR-011: **npm + verificación de `dist.shasum` antes de extraer**. Nota sobre los temas: en `10.0.3` **no existe `codebase/skins/`** — los **8** vienen **integrados** dentro de `dhtmlxgantt.css` vía `--dhx-gantt-theme` / `data-gantt-theme`, con `terrace` por defecto.
> - **Opción B — Standard GPL v2** (lo que muchos leen como "la versión gratis de DHTMLX"). **Impacto:** copyleft — obligaría a distribuir el código fuente completo de la aplicación derivada bajo GPL v2, lo que es incompatible con un SaaS comercial de código propietario. **No recomendable.**
> - **Opción C — Licencia comercial DHTMLX (Individual/Commercial).** **Impacto:** uso en SaaS explícitamente permitido, soporte oficial y sin copyleft; **coste desde ~USD 799–749 por desarrollador** (Gantt) y ~USD 3 749+ (Planning pack) — decisión financiera, no técnica. A cambio añade auto-scheduling, ruta crítica, export a PDF/Excel sin marca de agua y agrupamiento WBS, que **ningún CA de esta HU necesita**.
>
> **Recomendación: Opción A (Community Edition MIT, v10.0.3)**, fijada por **ADR-011** (licencia + vendorización + versión exacta). Convierte STACK-07 de "una dependencia copyleft" en "una librería MIT sin riesgo legal para el SaaS" y no cuesta un céntimo ni obliga a features que no vamos a usar. Si prefieres la Opción C por el soporte oficial, se cambia la versión en el ADR y el resto del spec no varía. **Mientras no se resuelva, `@FrontendDev` no vendoriza nada** (lo demás sí puede avanzar: backend + tests).

Gantt (DHTMLX Gantt)` al DS con los tokens `--gantt-bar-verde/amarillo/rojo/gris/cg` (los cuatro primeros apuntando a `--color-verde/--amarillo/--rojo/--color-border-dark`; `--gantt-bar-cg` al neutro oscuro `primary`), las clases `.gantt-bar--*`, `.gantt-tooltip*`, `--gantt-row-height`, `.gantt-pe`, y volcar los valores a `wwwroot/css/gantt.css`. **Alternativa:** un ADR de excepción a UX-01 con el CSS encapsulado solo en la vista.

> **F3 — Índice de BD + migración `V005`.**
> El DDL no tiene ningún índice que cubra `tenant_id + ciclo_id` en `accion_plan` (solo `objetivo_cg_id`, `area_id`, `status`), que es el filtro real de la query del Gantt. Con el volumen actual (decenas/cientos de filas) un seq scan es irrelevante, pero RNF-001 (< 2 s) es un requisito duro y crecerá con multi-tenancy.
> **Propuesta:** `V005__indice_accion_plan_gantt.sql` con `CREATE INDEX idx_accion_plan_ciclo_area ON accion_plan (tenant_id, ciclo_id, area_id);` + **ADR-012** (DB-01/DB-02 obligan a ADR para tocar el esquema) y alta en `06_MODELO_DATOS.md` § 7 junto a V001–V004.
> **Alternativa:** aplazar la migración hasta que un tenant tenga volumen (RNF-004 asume 200 acciones como techo de los reportes).
> **Recomendación: emitir V005 + ADR-012.** El costo es una migración `CREATE INDEX` trivial y deja el Sprint 4 alineado con el estándar de migraciones que ya se sigue; aplazar significa abrir una deuda de esquema justo en la HU que introduce la consulta por ciclo.

> **F4 — Discrepancia de backlog.** El encabezado de HU-021 dice **"Sprint: 6"** (L427) y la tabla de Sprint Planning la asigna al **Sprint 4** (L928). Es el mismo patrón corregido en los cierres de HU-011 (L238), HU-012 (L254), HU-013 (L278), HU-014 (L293) y HU-015 (L316).
> **Recomendación: Sprint 4 según la tabla de planning** (además es la primera HU del Sprint 4 por planificación vigente); @Documenter corrige el encabezado al cierre.

> **F5 — ¿El color usa el `status` persistido o se recalcula?**
> La BLL **no** recalcula el status (D-M): lee el que HU-020 mantiene. Si un JEF no actualiza una acción y su fecha de vencimiento pasa, el Gantt seguirá mostrándola como "En progreso" hasta que alguien la actualice o exista el batch RN-040 (Sprint 8). La alternativa es recalcular RN-017 en la BLL del Gantt (como hizo HU-016 con "atrasadas"), lo que exige mover `CalcularStatus` —hoy `private static` en `AccionPlanService` L76— a un helper reutilizable (extendiendo `SemaforoHelper`, que ya existe en `PE-GOL.Utility/Helpers/` y hoy solo expone `Evaluar` para umbrales; sin ADR) y aceptar que el Gantt pueda mostrar un color distinto al del listado.
> **Recomendación: leer el persistido (D-M).** Una sola fuente de verdad y cero divergencia visual entre el listado (HU-019) y el Gantt; el desfase temporal se resuelve con el batch de Sprint 8, que actualizará el status de todas las acciones. Si prefieres el color "en vivo", el cambio es pequeño (extraer el helper + un método nuevo en el servicio) y hay que actualizar el test 17 y la decisión D-M.

> **F6 — Granularidad del filtro / selector de área del Gerente.**
> El endpoint **no acepta `area_id`** (D-F) y el Gerente ve **todas** las áreas del ciclo (RN-006) en un solo payload, con el código de área visible en cada grupo (`GOL1 · CG-01 · …`). Preguntas: (a) ¿el Gerente necesita un **selector de área** en la barra de filtros? (b) ¿el Jefe de Área puede ver algo de otras áreas?
> **Recomendación:** (a) **sí, como filtro de cliente** (los datos ya vienen; es un `<select>` más, sin endpoint ni riesgo SEC-07); (b) **no** — SEC-07 es tajante y el JEF ya tiene el consolidado gerencial de CGs (HU-018) para eso. Si quieres el filtro de área **en servidor** (por volumen futuro), sería un segundo endpoint o un query param: dímelo y lo diseño, con su propio caso de prueba de SEC-07.

> **F7 — Alcance de rol del Gantt y del ítem de menú.**
> El backlog dice "**Como JEF**" (L416) y RF-032 (consolidado del Plan para el Gerente) es **HU-023**. La propuesta de este spec: el **endpoint y la vista aceptan `JefeArea, Gerente`** (SEC-07 ya se define para ambos roles y el filtro por área del JEF no cuesta nada), y el **ítem de menú se agrega a "Mi Área" (JEF) y también a "Contenido" (GERENTE)**.
> **Recomendación:** incluir el ítem del Gerente ahora (1 línea, sin trabajo de backend) — el Gantt es la única vista que muestra la distribución temporal de todas las áreas y el Gerente es su principal beneficiario. Si prefieres no anticipar HU-023, se quita el ítem del Gerente y la vista sigue funcionando si navega a mano. Confirma también si el ítem del JEF va como entrada propia ("Gantt del Plan") o como pestaña dentro de "Plan de Acción".

> **F8 — RF-031 (conteo por status) entra en esta HU?**
> RF-031 es de prioridad **Media**: *"conteo de acciones por status a nivel de objetivo CG y de área"*. El spec incluye solo el **total global de los 4 status** (D-J), que da contenido a la leyenda y sale gratis de los datos ya cargados; **no** incluye el conteo por CG ni por área.
> **Recomendación:** dejarlos para **HU-023** (Vista Consolidada del Plan — Gerente), que es donde el conteo por área cobra sentido (comparativa entre áreas). Si prefieres el conteo por CG en las filas del Gantt, es un campo más en `Grupos` y una línea de BLL — dímelo y lo agrego al spec.

> **F9 — ¿Drag & drop persistente en el futuro?**
> Esta HU lo descarta (D-N, 4 razones en § "Solo lectura"). Si en algún momento lo quieres, no es "activar una opción" de la librería: requiere un endpoint nuevo (p. ej. `PATCH /api/v1/acciones/{id}/fechas`), re-validación de RN-019/RN-021 en BLL, auditoría ADR-003 con snapshot, recalculo de RN-017/RN-018 y los tests correspondientes — es una HU nueva.
> **Recomendación:** mantenerlo fuera. Pregunto solo para dejar constancia de que la decisión es **deliberada** y no un olvido.

> **F10 — Volumen y filtros en servidor.**
> Los filtros son de cliente porque el payload cabe en una query (≤ 200 acciones, la escala de RNF-004). Si un tenant llegara a miles de acciones por ciclo, el Gantt dejaría de cumplir RNF-001 y los filtros tendrían que pasar al servidor (parámetros opcionales + validator + tests).
> **Recomendación:** dejarlo así en v1.0 y documentar el umbral. ¿Algún tenant previsto con más de ~500 acciones en el plan de un ciclo? Si la respuesta es "podría", el diseño del endpoint debería incluir paginación ya en esta HU.

> **F11 — ¿Segunda barrera de área en la BLL o solo en la DAL?**
> SEC-07 dice "la DAL debería incluir `AND area_id = @AreaId`", y así se implementa (DAL-G1). La pregunta es si la BLL **además** descarta en memoria las filas que vinieran de otro `area_id`. En el código actual **no se hace** en ningún servicio: `AreaService.ListarAreasAsync` y `ResponsableService.ListarAsync` filtran solo en la DAL, y el test 11 de este spec fija ese comportamiento (la BLL devuelve lo que da la DAL).
> - A favor de añadirlo: ARCH-04 pide dos capas de aislamiento; un filtro en memoria es gratis (la lista ya está cargada) y protege aunque la DAL cambie.
> - En contra: **enmascara un fallo del DAL** (un `areaIdFiltro` mal pasado pasaría los tests de BLL y el fallo explotaría en producción), y agrega una regla que no existe en los demás servicios.
> **Recomendación: mantener el filtro solo en la DAL** (consistente con el código vigente y con el patrón de `AreaService`/`ResponsableService`), y dejarlo asentado aquí para que la decisión sea explícita y no un olvido. Si prefieres defensa en profundidad, dímelo: es un `Where(...)` en el paso 5 de la BLL más un caso de test, sin ADR.
