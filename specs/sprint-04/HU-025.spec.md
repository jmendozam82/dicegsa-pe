## Contexto

Backlog `03_BACKLOG.md` L487-498.

> **Como** JEF · **Quiero** crear, editar y eliminar KRs dentro de cada OKR con descripción y peso ponderado · **Para** definir las métricas concretas que evidenciarán el logro del objetivo.

**Criterios de Aceptación (CA) a cubrir en esta HU** — numeración canónica del backlog L492-497:

| # | CA (backlog L492-497) | Dónde se cumple |
|---|----------------------|-----------------|
| CA #1 | Campos por KR: código (KR.N), descripción, peso (%) | § DTOs `KeyResultCreateRequest`/`KeyResultUpdateRequest` (`Descripcion`, `Peso`) + `KeyResultResponse` (`Codigo` = `"KR.1"` auto-generado) · § Lógica BLL `CrearAsync` paso 7 + § Queries DAL «Siguiente secuencia» — `MAX(regexp_match(codigo,'^KR\.(\d+)$'))+1` **por `okr_id`** (patrón DAL-P5 de `PilarService`, **F4 resuelto**) · capa 2 = `UNIQUE (okr_id, codigo)` → 23505 → 422 |
| CA #2 | Entre 1 y 5 KRs por OKR | § Lógica BLL `CrearAsync` paso 4 — constante `MaxKeyResultsPorOkr = 5` (**F2 resuelto: 5**, discrepancia con RF-034 «hasta 3» resuelta a favor de RN-022 + CA #2) + `ContarKeyResultsAsync` → 422. **Alcanzable gracias a F0**: el `POST` singular no valida Σ (ver CA #3) |
| CA #3 | Validación: suma de pesos de KRs del mismo OKR debe ser 1.0 (100%); error si difiere | § Lógica BLL `ActualizarPesosAsync` paso 5 — `Math.Round(request.Pesos.Sum(p => p.Peso), 3, AwayFromZero) != 1.000m` → **422** (regla **dura**, **F0 resuelto = opción B**, sobre el **vector completo**) · § Endpoints `PUT .../key-results/pesos` · **el `POST`/`PUT` singular NO validan Σ** (F0) · § UI indicador vivo de Σ pesos |
| CA #4 | No se puede eliminar un KR con valores reales registrados en el ciclo activo | § Lógica BLL `EliminarAsync` paso 3 — `ContarValoresRealesAsync` > 0 → 422 (RC-12) |

**Decisiones de diseño (F0–F7)**

| # | Decisión | Resolución |
|---|----------|------------|
| F0 | ¿Dónde validar Σ pesos = 1.000? | **Opción B**: solo en el endpoint masivo `PUT .../key-results/pesos` (regla dura sobre el vector completo). El `POST`/`PUT` singular NO validan Σ — permite crear KRs incrementalmente y ajustar el reparto al final |
| F1 | ¿Límite de KRs por OKR? | **5** (RN-022 + CA #2). RF-034 dice «hasta 3» pero RN-022 y el backlog son posteriores y más específicos |
| F2 | ¿Código KR secuencial global o por OKR? | **Por OKR** (`MAX(N)+1` donde `okr_id = @OkrId`). Patrón DAL-P5 de `PilarService` |
| F3 | ¿Qué pasa al eliminar un KR con valores? | **Bloqueo** (422). HU-026 registra valores mensuales; no se puede borrar un KR con datos reales |
| F4 | ¿Auditoría de la reasignación masiva? | **Una sola entrada** con el reparto completo en `Detalle` (JSON) |
| F5 | ¿Migración de BD? | **No requerida** — la tabla `key_result`, su `UNIQUE (okr_id, codigo)` y su RLS `key_result_policy` ya existen en el DDL base (`06_MODELO_DATOS.md`) |
| F6 | ¿Ítem en `_Sidebar.cshtml`? | **No** — entrada desde `Okr/Index.cshtml` con botón por fila (contexto: los KRs pertenecen a un OKR específico) |
| F7 | ¿Icono para el botón «KRs»? | **`bi-bullseye`** (Bootstrap Icons 1.11) — sincronizado en `docs/07_DESIGN_SYSTEM.md` § 7 |

**Justificación detallada de cada decisión:**

**F0 — Validación de Σ pesos:**
El enfoque de validar Σ = 1.000 solo en el endpoint masivo permite un flujo de trabajo incremental: el JEF puede crear KRs uno a uno sin preocuparse por la suma, y al final ajustar todos los pesos de una vez. Esto es más usable que exigir Σ = 1.000 en cada creación individual, que obligaría a recalcular todos los pesos cada vez que se añade un KR. La regla se aplica con `Math.Round(..., 3, MidpointRounding.AwayFromZero)` para evitar problemas de precisión de punto flotante.

**F1 — Límite de 5 KRs:**
Aunque RF-034 menciona «hasta 3», la RN-022 y el backlog (CA #2) son más recientes y específicos. El límite de 5 da más flexibilidad sin ser excesivo. La constante `MaxKeyResultsPorOkr = 5` se define en el servicio para facilitar cambios futuros.

**F2 — Código secuencial por OKR:**
El código `KR.N` se reinicia por cada OKR. Esto es más legible para el usuario final (`KR.1`, `KR.2`... dentro de cada OKR) que un código global. La query usa `regexp_match(codigo, '^KR\.(\d+)$')` para extraer el número y calcular el siguiente.

**F3 — Bloqueo de eliminación con valores:**
Una vez que HU-026 registre valores mensuales reales, eliminar un KR destruiría información histórica. El bloqueo (422) fuerza a que el JEF primero elimine los valores asociados o cancele el KR de otra forma.

**F4 — Auditoría masiva:**
La reasignación de pesos es una operación atómica que afecta a múltiples KRs. Registrar una sola entrada con el reparto completo en formato JSON es más útil que N entradas individuales, ya que captura el estado completo del OKR en un momento dado.

**F5 — Sin migración:**
La tabla `key_result` fue definida en el DDL base desde el inicio del proyecto. No se requiere migración porque el esquema ya existe con todas las columnas, índices y RLS necesarios.

**F6 — Navegación contextual:**
Los KRs son hijos de un OKR específico. No tiene sentido un ítem global en el sidebar. El acceso es desde `Okr/Index` con un botón por fila, que pasa el `okrId` como parámetro de ruta.

**F7 — Icono `bi-bullseye`:**
El icono de "diana" (bullseye) representa visualmente el concepto de "Key Result" — una métrica concreta que se quiere alcanzar. Está disponible en Bootstrap Icons 1.11 y se sincronizó en el Design System.

**Relación con HUs anteriores y posteriores:**

- **HU-024 (CRUD de OKRs)**: Esta HU es la continuación natural. Los KRs son hijos de los OKRs creados en HU-024. La navegación desde `Okr/Index` permite ver los KRs de cada OKR.
- **HU-026 (Registro Mensual Valores KRs)**: La HU-026 añadirá la capacidad de registrar valores mensuales reales para cada KR. La validación de Σ = 1.000 en el endpoint masivo es fundamental para garantizar que los valores registrados se distribuyan correctamente.
- **HU-027 (Consolidado OKRs)**: El consolidado de OKRs usará los KRs y sus valores calculados para mostrar el progreso de cada OKR.

**Entidades relacionadas:**

- `okr` — entidad padre (HU-024)
- `key_result` — entidad principal de esta HU
- `valor_mensual_kr` — entidad hija (HU-026)
- `ciclo` — entidad de contexto (validación de ciclo activo)
- `area` — entidad de contexto (validación de área del JEF)

**Reglas de negocio aplicables:**

- **RC-12**: Las operaciones de escritura están bloqueadas cuando el ciclo está `Cerrado`
- **SEC-06**: El `tenant_id` se inyecta desde el JWT, nunca del body/query string
- **SEC-07**: El JEF solo puede acceder a KRs de OKRs que pertenecen a su área
- **DB-04**: Los campos calculados se persisten en la BLL, no en triggers

## Endpoints

| Método | Ruta | Auth | Descripción |
|--------|------|------|-------------|
| `GET` | `/api/v1/okrs/{okrId}/key-results` | JEF | Lista todos los KRs de un OKR con su código, descripción, peso y Σ pesos |
| `POST` | `/api/v1/okrs/{okrId}/key-results` | JEF | Crea un nuevo KR (código auto-generado `KR.N`, peso libre — **no valida Σ**) |
| `PUT` | `/api/v1/okrs/{okrId}/key-results/{id}` | JEF | Actualiza descripción y/o peso de un KR (**no valida Σ**) |
| `PUT` | `/api/v1/okrs/{okrId}/key-results/pesos` | JEF | **Reasignación masiva de pesos** — valida Σ = 1.000 (regla dura) y actualiza todos en una transacción atómica |
| `DELETE` | `/api/v1/okrs/{okrId}/key-results/{id}` | JEF | Elimina un KR (bloqueado si tiene valores reales registrados) |
| `GET` | `/api/v1/okrs/{okrId}/key-results/{id}` | JEF | Obtiene un KR específico por ID |

**Notas de seguridad:**
- Todos los endpoints requieren rol `JEF` (`[Authorize(Roles = "JEF")]`)
- `okr_id` va en la ruta (no en body ni query string) — SEC-06
- `tenant_id` se inyecta desde el JWT vía `TenantMiddleware` — SEC-06
- Respuestas con wrapper `ApiResponse<T>` — ARCH-07

**Códigos de respuesta HTTP:** 200 (éxito GET/PUT), 201 (éxito POST), 400 (request mal formado), 401 (no autenticado), 403 (sin permiso), 404 (no encontrado), 422 (error de validación de negocio), 500 (error interno).

## Lógica BLL (paso a paso)

### `KeyResultService.CrearAsync`

1. **Validar ciclo activo** — `ObtenerCicloActivoAsync` → si no hay ciclo `Activo`, throw `BusinessException(422, "No hay ciclo activo")` (RC-12)
2. **Verificar OKR padre** — `ObtenerOkrPadreOThrowAsync(okrId)` → 404 si no existe · **SEC-07**: verifica que el OKR pertenece al área del JEF
3. **Contar KRs existentes** — `ContarKeyResultsAsync(okrId)` → si `>= MaxKeyResultsPorOkr (5)`, throw `BusinessException(422, "Máximo 5 KRs por OKR")` (CA #2)
4. **Generar código** — `ObtenerSiguienteCodigoAsync(okrId)` → `"KR." + (MAX(N)+1)` (CA #1, F2)
5. **Crear entidad** — mapear DTO → `KeyResult` entity con `Codigo`, `Descripcion`, `Peso`, `OkrId`, `TenantId`
6. **Persistir** — `_repository.CrearAsync(entity)`
7. **Auditoría** — `_auditoriaService.RegistrarAsync("KeyResult", "CREATE", entity.Id, detalle)` (ADR-003)
8. **Retornar** — mapear a `KeyResultResponse`



### `KeyResultService.ActualizarAsync`

1. **Validar ciclo activo** — igual que Crear
2. **Obtener KR existente** — `_repository.ObtenerPorIdAsync(id)` → 404 si no existe
3. **Verificar OKR padre** — `ObtenerOkrPadreOThrowAsync(okrId)` → **SEC-07**: doble compuerta
4. **Verificar pertenencia** — `kr.OkrId == okrId` → 404 si no coincide
5. **Actualizar campos** — `Descripcion`, `Peso` (sin tocar `Codigo`)
6. **Persistir** — `_repository.ActualizarAsync(kr)`
7. **Auditoría** — `_auditoriaService.RegistrarAsync("KeyResult", "UPDATE", kr.Id, detalle)`
8. **Retornar** — mapear a `KeyResultResponse`

**Nota F0**: Este método **NO valida Σ pesos**. La validación de Σ solo ocurre en `ActualizarPesosAsync`. Esto permite al JEF ajustar pesos individualmente sin restricciones, y la validación global se hace al final con el endpoint masivo.

### `KeyResultService.ActualizarPesosAsync` (masivo — F0)

1. **Validar ciclo activo** — igual que Crear
2. **Verificar OKR padre** — `ObtenerOkrPadreOThrowAsync(okrId)` → **SEC-07**
3. **Obtener todos los KRs del OKR** — `_repository.ListarPorOkrAsync(okrId)`
4. **Validar que todos los IDs del request existen** — comparar `request.Pesos.Select(p => p.Id)` con `existingKrs.Select(k => k.Id)` → 422 si hay IDs desconocidos o faltantes
5. **Validar Σ = 1.000** — `Math.Round(request.Pesos.Sum(p => p.Peso), 3, MidpointRounding.AwayFromZero) != 1.000m` → **422** con mensaje `"La suma de pesos debe ser exactamente 1.000 (100%). Suma actual: {suma}"` (CA #3, F0)
6. **Actualizar pesos en transacción atómica** — `_repository.ActualizarPesosAsync(request.Pesos)` → un solo `TransactionScope` con rollback automático si algo falla
7. **Auditoría** — **una sola entrada** con el reparto completo: `_auditoriaService.RegistrarAsync("KeyResult", "UPDATE_PESOS", okrId, detalle: json)` donde `detalle` es un JSON con todos los KRs y sus nuevos pesos (F4)
8. **Retornar** — lista actualizada de `KeyResultResponse`



### `KeyResultService.EliminarAsync`

1. **Validar ciclo activo** — igual que Crear
2. **Obtener KR existente** — `_repository.ObtenerPorIdAsync(id)` → 404 si no existe
3. **Verificar OKR padre** — `ObtenerOkrPadreOThrowAsync(okrId)` → **SEC-07**
4. **Verificar pertenencia** — `kr.OkrId == okrId` → 404 si no coincide
5. **Verificar valores reales** — `ContarValoresRealesAsync(kr.Id)` → si `> 0`, throw `BusinessException(422, "No se puede eliminar un KR con valores reales registrados")` (CA #4, RC-12)
6. **Eliminar** — `_repository.EliminarAsync(id)`
7. **Auditoría** — `_auditoriaService.RegistrarAsync("KeyResult", "DELETE", id, detalle)`



### `KeyResultService.ListarPorOkrAsync`

1. **Verificar OKR padre** — `ObtenerOkrPadreOThrowAsync(okrId)` → **SEC-07**
2. **Listar KRs** — `_repository.ListarPorOkrAsync(okrId)`
3. **Calcular Σ pesos** — `kr.Sum(k => k.Peso)`
4. **Retornar** — `KeyResultListResponse` con lista, suma y cantidad

**Pseudocódigo detallado:**

```csharp
public async Task<KeyResultListResponse> ListarPorOkrAsync(Guid okrId)
{
    // 1. Verificar OKR padre (SEC-07)
    var okr = await _okrService.ObtenerOkrPadreOThrowAsync(okrId);
    if (okr == null)
        throw new BusinessException(404, "OKR no encontrado");

    // 2. Listar KRs
    var krs = await _repository.ListarPorOkrAsync(okrId);

    // 3. Calcular Σ pesos
    var sumaPesos = krs.Sum(k => k.Peso);

    // 4. Retornar
    return new KeyResultListResponse
    {
        KeyResults = _mapper.Map<List<KeyResultResponse>>(krs),
        SumaPesos = sumaPesos,
        Cantidad = krs.Count
    };
}
```

### `KeyResultService.ObtenerPorIdAsync`

1. **Verificar OKR padre** — `ObtenerOkrPadreOThrowAsync(okrId)` → **SEC-07**
2. **Obtener KR** — `_repository.ObtenerPorIdAsync(id)` → 404 si no existe
3. **Verificar pertenencia** — `kr.OkrId == okrId` → 404 si no coincide
4. **Retornar** — mapear a `KeyResultResponse`

**Pseudocódigo detallado:**

```csharp
public async Task<KeyResultResponse> ObtenerPorIdAsync(Guid okrId, Guid id)
{
    // 1. Verificar OKR padre (SEC-07)
    var okr = await _okrService.ObtenerOkrPadreOThrowAsync(okrId);
    if (okr == null)
        throw new BusinessException(404, "OKR no encontrado");

    // 2. Obtener KR
    var kr = await _repository.ObtenerPorIdAsync(id);
    if (kr == null)
        throw new BusinessException(404, "Key Result no encontrado");

    // 3. Verificar pertenencia
    if (kr.OkrId != okrId)
        throw new BusinessException(404, "El KR no pertenece a este OKR");

    // 4. Retornar
    return _mapper.Map<KeyResultResponse>(kr);
}
```
