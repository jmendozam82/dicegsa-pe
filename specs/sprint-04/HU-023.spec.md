> ## Revisión v3 (2026-09-30) — Defecto E: el JS llama a la API en ruta relativa al MVC → 404 (proxy MVC aprobado)
>
> Los Defectos A, B y C de la Revisión v2 están **implementados y validados contra la API real** (los 4 endpoints del contrato de § UI § 3 y los 5 escenarios de fecha de ADR-015 devuelven 200). Pero la validación en navegador de ese hotfix destapó un **cuarto defecto, de otra clase**, que ningún test C# puede detectar — la misma clase de defecto que AGENTS.md v1.25 documentó para HU-021. Jorge decidió corregirlo **spec primero** (LOOP-01) y **aprobó ampliar el hotfix con el proxy MVC el 2026-09-30**. Esta revisión corrige el **contrato**; el código lo corrigen después @QA (tests en rojo) → @BackendDev/@FrontendDev.
>
> | # | Defecto | Evidencia | Causa raíz | Corrección que se implementará | Archivo: línea |
> |---|---|---|---|---|---|
> | **E** | El JS llama a la API en **ruta relativa al origen del MVC** (`https://localhost:7200`) → **HTTP 404**. Síntoma en el navegador: `alert('Error al cargar los datos: Error 404')`. | Verificado en vivo: `GET https://localhost:7200/api/v1/planes/consolidado` → **404** · `GET https://localhost:7200/api/v1/planes/consolidado/exportar` → **404** · `GET https://localhost:7269/api/v1/planes/consolidado` → **200** (con JWT de `Gerente`) · `GET https://localhost:7269/api/v1/planes/consolidado/exportar` → **200**. | `plan-consolidado.js:14` declara `var API_BASE = '/api/v1/planes/consolidado'` — una ruta **relativa al origen del MVC**. Pero la API vive en **otro origen/puerto** (`https://localhost:7269`, de `Api:BaseUrl`): el navegador acaba pidiendo `https://localhost:7200/api/v1/...` y el proyecto MVC **no tiene ninguna ruta `/api/v1` ni proxy alguno** (`Program.cs` solo hace `MapControllerRoute` de MVC; el `ApiClient` C# sí usa el `BaseAddress` absoluto de `Api:BaseUrl`). | **Proxy por acciones MVC (ADR-016):** 2 acciones nuevas en el controller MVC (`ConsolidadoDatos` y `ConsolidadoExportar` — contrato abajo) que proxean la API con `IApiClient` (JWT en sesión), y el JS pasa a llamar esas rutas **relativas al MVC**. | `PE-GOL.Aplicacion/wwwroot/js/plan-consolidado.js:14` (`API_BASE`) · `:92` (fetch de `obtenerConsolidado`) · `:128` (fetch de `exportarExcel`) · `:315` (`alert`) · `PE-GOL.Aplicacion/Controllers/PlanController.cs` (2 acciones nuevas) |
>
> **Alcance del daño:** la tabla inicial se ve bien porque el MVC la renderiza **server-side**, pero **ninguna interacción del usuario funciona**: los `fetch` de `obtenerConsolidado()` (L92 — **filtros y paginación**) y `exportarExcel()` (L128) están **ambos** rotos.
>
> **Por qué ningún test C# lo detectó** (lección documentada — misma clase que la de HU-021 en AGENTS.md v1.25): los tests de `PlanControllerTests` mockean `IApiClient` — **nunca ejercitan una URL construida en JS**. El defecto vive en el navegador (el **origen** contra el que resuelve la ruta), donde xUnit no llega.
>
> **Corrección sobre la Revisión v2:** la v2 decía «JS (`plan-consolidado.js` — sus rutas ya son correctas)» — era cierto a nivel de **path** (las rutas coinciden con los endpoints reales de la API), pero falso a nivel de **origen**: en el navegador, `/api/v1/...` resuelve contra el origen del MVC (`:7200`), no contra el de la API (`:7269`). La lección: el contrato de una llamada JS debe verificar la **ruta completa (origen + path)**, no solo el path.
>
> **La decisión de Jorge (2026-09-30) — proxy por acciones MVC:**
>
> > «Es la única opción consistente con el patrón del repo. El principio es que el navegador habla con el MVC y el MVC habla con la API — el `ApiClient` con JWT en sesión es exactamente el puente diseñado para eso. Romper ese patrón crearía una excepción que complica el mantenimiento y abre un vector de seguridad (JWT cross-origin en el navegador).»
>
> **Descartadas explícitamente por Jorge:** (a) inyectar `Api:BaseUrl` al JS — abre CORS y expone el JWT cross-origin; (b) renderizar todo server-side como HU-021/Gantt — una reescritura grande que mueve la paginación al navegador. **Precedente del repo:** `wwwroot/js/gantt-plan.js` (HU-021, validado en navegador) **no hace ningún `fetch`** — su vista documenta literalmente «no hay form GET, no hay AJAX y no se vuelve a llamar a la API»; los datos se renderizan server-side. `plan-consolidado.js` es hoy el **único** fichero de `wwwroot/js/` que usa `API_BASE` (los demás no hacen fetch; `entregables.js`, de HU-022, tiene 3 fetch en ruta relativa = mismo defecto E, **fuera de alcance** — ver ADR-016 y HANDOFF «Deuda técnica pendiente», ítem 3).
>
> **Contrato de las 2 acciones MVC proxy (Revisión v3 — cerrado):**
>
> | Acción | Método | Ruta | Auth | Query string permitido | Devuelve |
> |---|---|---|---|---|---|
> | `ConsolidadoDatos` | `GET` | `/Plan/ConsolidadoDatos` | `[Authorize(Roles = "Gerente")]` (la del controller MVC — caso 36) | los 7 filtros + `page`/`pageSize` de `FiltrosConsolidadoRequest` (`areaId`, `cgId`, `status`, `clasificacion`, `tipo`, `fechaDesde`, `fechaHasta`, `page`, `pageSize`). **SEC-06: nunca `tenant_id`.** | Proxea `GET /api/v1/planes/consolidado` **reenviando los filtros como query string** y devuelve el payload (`ConsolidadoResponse`) íntegro al JS (JSON 200). |
> | `ConsolidadoExportar` | `GET` | `/Plan/ConsolidadoExportar` | ídem | ídem | Proxea `GET /api/v1/planes/consolidado/exportar` con los mismos filtros y devuelve **`FileResult` binario**: `FileContentResult` con el `byte[]`, `ContentType = "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"` y `FileDownloadName = "PlanConsolidado_{ciclo}.xlsx"`. |
>
> **Whitelist explícita (SEC-06):** las 2 acciones declaran los 9 parámetros permitidos y **construyen** el query string para la API — sin passthrough crudo del query string recibido (ningún parámetro ajeno, y jamás `tenant_id`, puede llegar a la API).
>
> **Contrato de errores del proxy (parte del contrato v3):**
>
> - `ApiClientException` → `_logger.LogError` con los detalles internos (ruta absoluta de la API, status, mensaje) **solo al log del servidor**; al navegador, el **mismo código HTTP** con un **mensaje genérico** («Error al consultar el plan consolidado»). **El cuerpo de la respuesta nunca contiene el JWT, el header `Authorization` ni la URL interna (`Api:BaseUrl`)** — `ex.Message` crudo puede contener la URL interna (casos 46/47).
> - `UnauthorizedException` (refresh agotado / sesión expirada) → **HTTP 401**, **no** redirect a login: es un endpoint consumido por `fetch` (un 302 se seguiría de forma transparente y el JS recibiría el HTML del login como 200). El JS trata el 401 como sesión expirada y redirige.
>
> **Cambios en el JS (parte del contrato v3):** `plan-consolidado.js` elimina `API_BASE` (L14) y sus 2 `fetch` pasan a rutas **relativas al MVC**: `obtenerConsolidado()` (L92) → `GET /Plan/ConsolidadoDatos?…` y `exportarExcel()` (L128) → `GET /Plan/ConsolidadoExportar?…`, siempre con los filtros actuales como query string. El navegador se autentica con la **cookie de sesión del MVC** — el JWT deja de viajar en peticiones del navegador (ADR-016).
>
> **Desviación de contrato que introduce el fix (aprobada por Jorge, 2026-09-30):**
>
> - `PlanController` (MVC) — **gana 2 acciones** proxy (`ConsolidadoDatos`, `ConsolidadoExportar`). Es cambio de la capa MVC de `PE-GOL.Aplicacion`, no de `PE-GOL.DTO` ni de la API → el patrón N-Tier no cambia (ARCH-02 intacto); **ADR-016** lo registra como decisión de arquitectura.
> - `plan-consolidado.js` — cambian las 2 rutas de `fetch` (y desaparece `API_BASE`). Sin más cambios: misma paginación server-side, mismos filtros, mismo `alert` de error (L315).
> - `PlanConsolidadoViewModel.AccessToken` — **sin cambios en este hotfix** (mantener el cambio mínimo): queda **sin consumidor** en el JS (el proxy usa el JWT de la sesión server-side); su retirada del ViewModel se registra como **deuda menor** (el token ya no necesita renderizarse en la página).
> - **Sin cambios**: API (los 2 endpoints y su Swagger), BLL (`PlanConsolidadoService`), DAL, DTOs, validators, la vista Razor (salvo las 2 líneas de § UI § 3/§ UI § 6 que este contrato ya actualiza), menú `_Sidebar`.

## Lógica BLL (paso a paso)

Servicio: `PE-GOL.BLL/Services/PlanConsolidadoService.cs` — **nuevo** (no se extiende `AccionPlanService`). Implementa `IPlanConsolidadoService` (`PE-GOL.BLL/Interfaces/`).

```csharp
Task<ConsolidadoResponse> ObtenerConsolidadoAsync(FiltrosConsolidadoRequest filtros, CancellationToken ct = default);
Task<byte[]> ExportarConsolidadoAsync(FiltrosConsolidadoRequest filtros, CancellationToken ct = default);
```

### Método 1 — `ObtenerConsolidadoAsync`

1. **Tenant (SEC-06):** `tenantId = ObtenerTenantIdOThrow()` — helper privado. `null` → `NotFoundException` → **404**.
2. **Rol (RN-006):** si `_tenantContext.Rol != "Gerente"` → `AccesoDenegadoException` → **403**. El atributo `[Authorize(Roles = "Gerente")]` ya lo bloquea; la re-validación en BLL es defensa en profundidad.
3. **Ciclo activo (RC-01):** `ciclo = await _cicloRepository.ObtenerCicloActivoAsync(tenantId, ct)`. `null` → `NotFoundException("No hay un ciclo activo para el tenant")` → **404**.
4. **Validar filtros:** si `FechaDesde > FechaHasta` → `ValidacionException` → **422**. Si `Page < 1` o `PageSize < 1` o `PageSize > 100` → `ValidacionException` → **422**.
5. **Query consolidada paginada:** `items = await _repository.ListarConsolidadoAsync(tenantId, ciclo.Id, filtros, ct)` — retorna `List<ConsolidadoItemResponse>` paginada (OFFSET/FETCH).
6. **Count total:** `total = await _repository.CountConsolidadoAsync(tenantId, ciclo.Id, filtros, ct)` — para paginación.
7. **Resumen (DB-04):** `resumen = await _repository.ObtenerResumenAsync(tenantId, ciclo.Id, filtros, ct)` — retorna `ResumenConsolidado` con conteos por status. Se calcula en BLL sobre las filas o con query `GROUP BY status`.
8. **Construir respuesta:** `ConsolidadoResponse { Items = items, Resumen = resumen, Paginacion = new() { Page, PageSize, TotalItems = total, TotalPages = (int)Math.Ceiling(total / (double)pageSize) } }`.
9. **Retornar** el DTO plano. El controller envuelve en `ApiResponse<T>` (ARCH-07).

### Método 2 — `ExportarConsolidadoAsync`

1. **Pasos 1-4 idénticos** al Método 1 (tenant, rol, ciclo, validación de filtros).
2. **Query sin paginación:** `todos = await _repository.ListarConsolidadoAsync(tenantId, ciclo.Id, filtros, skipPaginacion: true, ct)` — retorna **todas** las filas que coinciden con los filtros.
3. **Generar Excel con ClosedXML (STACK-08):**
   - Crear `XLWorkbook`.
   - Hoja "Consolidado" con encabezados: Área, Pilar, CG, Código Acción, Descripción, Fecha Inicio, Fecha Vencimiento, Status, Clasificación, Tipo, Progreso %, Peso, Responsable.
   - Filas con los datos.
   - Auto-ajustar columnas.
   - Retornar `byte[]` del stream.
4. **Retornar** `byte[]`. El controller devuelve `FileContentResult` con `contentType = "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"` y `fileDownloadName = "PlanConsolidado_{ciclo}.xlsx"`.

**Sin auditoría** (solo lectura) · **sin transacción** · **sin escrituras de ningún tipo**.

### Query 1 — ListarConsolidado (SELECT paginado)

```sql
SELECT
    a.id                    AS AccionId,
    a.codigo                AS AccionCodigo,
    a.descripcion           AS AccionDescripcion,
    a.fecha_inicio          AS FechaInicio,
    a.fecha_vencimiento     AS FechaVencimiento,
    a.clasificacion::text   AS Clasificacion,
    a.tipo_presupuesto::text AS TipoPresupuesto,
    a.progreso              AS Progreso,
    a.status::text          AS Status,
    a.peso                  AS Peso,
    u.nombre                AS ResponsableNombre,
    oc.id                   AS ObjetivoCgId,
    oc.codigo               AS ObjetivoCodigo,
    oc.descripcion          AS ObjetivoDescripcion,
    oc.progreso             AS ObjetivoProgreso,
    oc.semaforo::text       AS ObjetivoSemaforo,
    p.codigo                AS PilarCodigo,
    p.nombre                AS PilarNombre,
    ar.id                   AS AreaId,
    ar.codigo               AS AreaCodigo,
    ar.nombre               AS AreaNombre,
    c.id                    AS CicloId,
    c.nombre                AS CicloNombre,
    c.año_fiscal            AS CicloAnioFiscal
FROM accion_plan a
JOIN objetivo_cg oc ON oc.id = a.objetivo_cg_id AND oc.tenant_id = a.tenant_id
JOIN pilar p       ON p.id = oc.pilar_id       AND p.tenant_id = a.tenant_id
JOIN area ar       ON ar.id = a.area_id         AND ar.tenant_id = a.tenant_id
JOIN ciclo c       ON c.id = a.ciclo_id        AND c.tenant_id = a.tenant_id
LEFT JOIN usuario u ON u.id = a.responsable_id
WHERE a.tenant_id = @TenantId
  AND a.ciclo_id  = @CicloId
  AND (@AreaId       IS NULL OR a.area_id = @AreaId)
  AND (@CgId         IS NULL OR a.objetivo_cg_id = @CgId)
  AND (@Status       IS NULL OR a.status::text = @Status)
  AND (@Clasificacion IS NULL OR a.clasificacion::text = @Clasificacion)
  AND (@Tipo        IS NULL OR a.tipo_presupuesto::text = @Tipo)
  AND (@FechaDesde   IS NULL OR a.fecha_inicio >= @FechaDesde)
  AND (@FechaHasta   IS NULL OR a.fecha_inicio <= @FechaHasta)
ORDER BY ar.codigo ASC, oc.codigo ASC, a.fecha_inicio ASC
OFFSET @Offset ROWS FETCH NEXT @PageSize ROWS ONLY;
```

**Sin paginación:** omitir `OFFSET ... FETCH NEXT ...` cuando `skipPaginacion = true`.

### Query 3 — ObtenerResumen (GROUP BY status)

```sql
SELECT
    COUNT(*) AS Total,
    COUNT(*) FILTER (WHERE a.status::text = 'NoIniciado')  AS NoIniciado,
    COUNT(*) FILTER (WHERE a.status::text = 'EnProgreso')  AS EnProgreso,
    COUNT(*) FILTER (WHERE a.status::text = 'Terminado')   AS Terminado,
    COUNT(*) FILTER (WHERE a.status::text = 'Atrasado')    AS Atrasado
FROM accion_plan a
WHERE a.tenant_id = @TenantId
  AND a.ciclo_id  = @CicloId
  AND (@AreaId       IS NULL OR a.area_id = @AreaId)
  AND (@CgId         IS NULL OR a.objetivo_cg_id = @CgId)
  AND (@Status       IS NULL OR a.status::text = @Status)
  AND (@Clasificacion IS NULL OR a.clasificacion::text = @Clasificacion)
  AND (@Tipo        IS NULL OR a.tipo_presupuesto::text = @Tipo)
  AND (@FechaDesde   IS NULL OR a.fecha_inicio >= @FechaDesde)
  AND (@FechaHasta   IS NULL OR a.fecha_inicio <= @FechaHasta);
```

**Todas las queries:**
- `WHERE tenant_id = @TenantId` primero (SEC-06).
- Parámetros nombrados (SEC-05).
- Sin concatenación de strings SQL.
- Gerente: sin filtro `area_id` (RN-006, SEC-07 no aplica).

### Contrato de parámetros tipados (Revisión v2 — ADR-015, obligatorio)

> **Por qué (Defecto C).** Con el objeto anónimo, un `DateTime?` en null viaja a Npgsql **sin tipo declarado**; en la primera aparición (`@P IS NULL`) el parser de Postgres no obtiene contexto de tipo y, al llegar a `a.fecha_inicio >= $n` con la columna `DATE` (`V000__schema_base.sql:286`), el operador `>=` tiene **múltiples candidatos** (`date`/`timestamp`/`timestamptz`) → `PostgresException 42P08` («could not determine data type of parameter»). Los otros 5 filtros no fallan porque su lado derecho tiene un **único** candidato (`uuid`/`text`). **El cast SQL `@P::date` NO funciona** (probado contra la BD real: sigue 42P08) — la única corrección verificada empíricamente es declarar el tipo **en el cliente**.

Las 3 queries (`ListarConsolidadoAsync`, `CountConsolidadoAsync`, `ObtenerResumenAsync`) construyen **`DynamicParameters`** (no objeto anónimo) con **`DbType` declarado para los 9 parámetros**:

```csharp
var parametros = new DynamicParameters();
parametros.Add("TenantId",       tenantId,              DbType.Guid);
parametros.Add("CicloId",        cicloId,               DbType.Guid);
parametros.Add("AreaId",         filtros.AreaId,        DbType.Guid);
parametros.Add("CgId",           filtros.CgId,          DbType.Guid);
parametros.Add("Status",         filtros.Status,        DbType.String);
parametros.Add("Clasificacion", filtros.Clasificacion,  DbType.String);
parametros.Add("Tipo",           filtros.Tipo,          DbType.String);
parametros.Add("FechaDesde",     filtros.FechaDesde,    DbType.Date);   // ← ADR-015: OBLIGATORIO
parametros.Add("FechaHasta",    filtros.FechaHasta,     DbType.Date);   // ← ADR-015: OBLIGATORIO
// Solo Query 1 (paginada):
parametros.Add("Offset",   (filtros.Page - 1) * filtros.PageSize, DbType.Int32);
parametros.Add("PageSize", filtros.PageSize,                      DbType.Int32);
```

| Parámetro | `DbType` | Notas |
|---|---|---|
| `@TenantId` | `Guid` | SEC-06 |
| `@CicloId` | `Guid` | |
| `@AreaId` | `Guid` | nullable |
| `@CgId` | `Guid` | nullable |
| `@Status` | `String` | nullable |
| `@Clasificacion` | `String` | nullable |
| `@Tipo` | `String` | nullable |
| `@FechaDesde` | **`Date`** | nullable — **obligatorio `DbType.Date`** (ADR-015) |
| `@FechaHasta` | **`Date`** | nullable — **obligatorio `DbType.Date`** (ADR-015) |
| `@Offset` / `@PageSize` | `Int32` | solo Query 1 |

El SQL de las 3 queries **no cambia** (mismas cláusulas `IS NULL OR`, SEC-05 intacto); solo cambia **cómo viaja el parámetro**. `LogAuditoriaRepository` y los demás repositorios con el patrón `IS NULL OR` **no se tocan** (Defecto D: `DateTimeOffset?` sobre `timestamptz` y uuid/text/enum, sin ambigüedad — verificado en vivo).

### 7. Estados vacíos y errores de carga (Revisión v2 — contrato cerrado)

> La v1 decía «Sin ciclo activo (API 404)» — eso **causó el Defecto A**: cualquier 404 de cualquier llamada se pintaba como empty state de ciclo. El contrato v2 separa los casos por su **causa real**, no por código HTTP.

| Situación | Causa real (única) | Comportamiento exacto del controller | Qué renderiza la vista |
|---|---|---|---|
| **Sin ciclo activo** | `GET /api/v1/ciclos` responde 200 con lista vacía o **sin** ciclo `Activo` (RC-01). **Único caso legítimo — no es excepción.** | `HayCicloActivo = false`, `ErrorCarga = false`, **sin** `TempData["Error"]`, **sin** log de error. No se llaman los endpoints 2-4. | `.empty-state` con `bi-calendar-range`: «No hay un ciclo activo» (UX-05). Sin banner. |
| **Error de carga** | `ApiClientException` de **cualquier** llamada (403 del consolidado, 500 del DAL, 404 de un catálogo por carrera…). **Ningún 404 se etiqueta como «sin ciclo activo».** | `_logger.LogError` + `TempData["Error"] = ex.Message` + vista con `ErrorCarga = true`. `HayCicloActivo` **conserva el valor ya resuelto** (`true` si el paso 1 pasó) — el error no miente sobre el ciclo. | **Solo el banner** `alert-danger` de `TempData["Error"]` (ya existe, `Consolidado.cshtml:34-40`). **Ningún** `.empty-state` de ciclo, ni filtros, ni tabla. |
| `UnauthorizedException` | Refresh agotado / sesión expirada. | `RedirectToAction("Login", "Auth")` (sin cambios). | Redirección a login. |
| Ciclo activo con 0 acciones | 200 con `Items` vacío (D-C). | `HayCicloActivo = true`, `HayAcciones = false`. | `.empty-state` con `bi-list-check`: «No hay acciones en el plan». |
| Filtros sin coincidencias | 200 con `Items` vacío tras filtrar (JS). | — (la maneja el JS). | `.empty-state` dentro de la card + botón «Limpiar filtros». |

**Por qué el código v1 confundía los 3 casos:** el `catch (ApiClientException ex) when (ex.StatusCode == 404)` (`PlanController.cs:65-70`) trataba el 404 de **routing** de la ruta inventada (Defecto A) como «sin ciclo activo», y el 403 del endpoint JEF (Defecto B) caía en el catch genérico → `TempData["Error"]` **y además** `HayCicloActivo = false` → la vista pintaba el banner de error **encima** del empty state «No hay un ciclo activo» (falso). Tres causas distintas (sin ciclo / ruta inexistente / rol incompatible) colapsaban en 2 estados de UI engañosos. El fix convierte «sin ciclo activo» en una **condición de datos** (lista sin `Activo`), de modo que **ningún código HTTP puede suplantarla**, y el `when (ex.StatusCode == 404)` **desaparece** del controller (cualquier `ApiClientException` es ya un error genuino).

## ADR creado

**ADR-014** — ClosedXML en PE-GOL.BLL para exportación Excel.

- **Contexto:** HU-023 CA #4 requiere exportar el consolidado a Excel. STACK-08 define ClosedXML como tecnología obligatoria, pero el paquete NuGet no estaba instalado en ningún proyecto de la solución.
- **Decisión:** ClosedXML en `PE-GOL.BLL` (lógica de presentación). El controller solo envuelve `byte[]` en `FileContentResult`.
- **Consecuencias:** `PE-GOL.BLL.csproj` gana dependencia NuGet `ClosedXML` (MIT). Separación limpia; BLL testeable sin HTTP; controller sin lógica de formato.

**ADR-015** — Tipado explícito de parámetros opcionales de fecha en Dapper con Npgsql (Revisión v2, 2026-09-30).

- **Contexto:** el patrón `AND (@P IS NULL OR col OP @P)` falla con `PostgresException 42P08` cuando `@P` es una fecha (`DateTime?` en null viaja sin tipo declarado a Npgsql) y la columna es `DATE`: el operador `>=` tiene múltiples candidatos (`date`/`timestamp`/`timestamptz`). Detectado en la validación visual de HU-023 (Defecto C); los 735 tests automatizados no lo detectaron.
- **Decisión:** `DynamicParameters` con `DbType.Date` explícito — **obligatorio** para cualquier parámetro de fecha en el patrón `IS NULL OR`. Aplica a las 3 queries de `PlanConsolidadoRepository`. `LogAuditoriaRepository` **no se toca** (`DateTimeOffset?` sobre `timestamptz`, sin ambigüedad — Defecto D).
- **Consecuencias:** el SQL no cambia (SEC-05 intacto); los repositorios con filtros de fecha construyen `DynamicParameters` en vez de objeto anónimo (más verboso); regla operativa para @QA/@BackendDev: todo filtro de fecha nuevo se testea afirmando su `DbType`, no solo su nombre en el SQL.

**ADR-016** — El navegador nunca consume la API interna; el MVC hace de proxy con `IApiClient` (Revisión v3, 2026-09-30).

- **Contexto:** el Defecto E — `plan-consolidado.js` llama a la API en ruta relativa al origen del MVC (`:7200`) → 404; la API vive en otro origen (`:7269`, `Api:BaseUrl`) y el MVC no tiene rutas `/api/v1` ni proxy. Ningún test C# lo detectó (los mocks de `IApiClient` no ejercitan URLs construidas en JS); salió en la validación visual en navegador.
- **Decisión:** proxy por acciones MVC con `IApiClient` (JWT en sesión): 2 acciones nuevas (`ConsolidadoDatos`, `ConsolidadoExportar`) y el JS pasa a rutas relativas al MVC. Descartadas: inyectar `Api:BaseUrl` al JS (CORS + JWT cross-origin) y renderizar todo server-side (reescritura grande, paginación al navegador).
- **Consecuencias:** el JWT deja de exponerse en peticiones cross-origin (SEC-01/SEC-05); sin CORS en esta vista; `entregables.js` (HU-022) tiene el mismo defecto (L225/372/401) y queda como deuda para su propio hotfix; regla operativa: un `fetch` a `/api/v1/...` en `wwwroot/js/` es un defecto — la vista que necesite datos de la API añade una acción MVC proxy.
