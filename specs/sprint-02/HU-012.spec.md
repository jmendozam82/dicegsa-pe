## Contexto

Backlog `03_BACKLOG.md` L242-254 (EP-03, L223-225): **Como GER** quiero registrar, ordenar y eliminar los Valores Corporativos de la gerencia para el ciclo, para comunicar los principios que guían la actuación de todas las áreas.

**Criterios de Aceptación:**
1. Lista de valores con campo de texto por valor (ej: "Liderazgo", "Excelencia").
2. Agregar y eliminar valores individualmente.
3. Reordenar valores mediante drag-and-drop o flechas de orden.
4. Mínimo 1 valor requerido; máximo 15.
5. Visualización en modo lectura para Jefes de Área.

> **Nota de backlog (L254):** la HU figura con "Sprint: 3" en su encabezado, pero la tabla de Sprint Planning (L888-901) la asigna al **Sprint 2** (L897, 29 pts, 8 HUs). Se sigue la tabla de planning (fuente de verdad del sprint en curso) — mismo hallazgo que HU-011 L238, ya corregido. Hallazgo menor para @Documenter.

**Reglas de dominio aplicables** (`02_REQUERIMIENTOS.md`):
- **RF-014** (L49): el sistema debe permitir al Gerente registrar y gestionar la lista de **Valores corporativos** del ciclo (lista de ítems de texto).
- **RN-006** (L270): el Gerente tiene acceso de **lectura y escritura al contenido estratégico del ciclo (Filosofía, Pilares, OKRs, Plan de Acción)**; la configuración de la estructura (ciclos, umbrales, áreas) es responsabilidad del AdminTenant. Precedente: decisión D-A de HU-007 (ADM gestiona estructura, GER contenido).
- **RN-007** (L271): el Jefe de Área tiene acceso de **solo lectura** a Filosofía, Pilares y configuración del ciclo.
- **RC-12** (`05_DOMINIO.md` L554): ciclo `Cerrado` = solo lectura (patrón HU-007..HU-011).

**Modelo de datos** (`06_MODELO_DATOS.md` L164-174):
```sql
CREATE TABLE filosofia (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id   UUID         NOT NULL REFERENCES tenant(id),
    ciclo_id    UUID         NOT NULL REFERENCES ciclo(id) ON DELETE CASCADE,
    vision      TEXT,
    mision      TEXT,
    valores     JSONB        NOT NULL DEFAULT '[]',
    updated_by  UUID         REFERENCES usuario(id),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    UNIQUE (tenant_id, ciclo_id)
);
```
- **`valores` (L170): `JSONB NOT NULL DEFAULT '[]'`** — lista **ordenada** de strings. **El orden del array JSONB ES el orden de visualización** (D-C): drag-and-drop/flechas = reordenar el array. **No se requiere columna `orden` adicional** (Flag #2).
- RLS `filosofia_policy` (L561): `tenant_id = auth.tenant_id()` — **política simple por tenant, sin filtro por área** (SEC-07 NO APLICA, D-E).
- `accion_auditoria` (L46) incluye `UPDATE` → la escritura de valores se audita como `UPDATE` (D-D).
- **El DDL YA tiene `valores` y el `UNIQUE (tenant_id, ciclo_id)`** (L173) → sirve como target del `ON CONFLICT` del UPSERT (DB-06, D-B) y como capa 2 ante carreras (23505 → 422, patrón ADR-001). **No se requiere migración ni ADR nuevo** (ver § Hallazgos).

**Nota de alcance — UI diferida (CA #3):** siguiendo la decisión establecida de UI diferida (HU-006..HU-011 entregadas 100% backend), el drag-and-drop del CA #3 se entrega como **contrato de datos**: el request lleva la lista **ya ordenada** (el orden del array es el orden final). La vista Razor con drag-and-drop se planifica con el cimiento de frontend (HU-045+). Los endpoints y DTOs de este spec quedan listos para ser consumidos por el frontend en ese sprint.

## Endpoints

Anidados bajo `/api/v1/ciclos/{cicloId}/filosofia`, en `PE-GOL.API/Controllers/CicloController.cs` (mismo controller de HU-007..HU-011: la filosofía es **hija del agregado Ciclo** — D-I). `{cicloId}` es `:guid` en la ruta. **SEC-06:** `tenant_id` NUNCA viaja en body/query; se resuelve del JWT vía `TenantContext.TenantId`. **SEC-07 NO APLICA** (D-E, idéntico a HU-011): `filosofia` es **corporativa** (una fila por ciclo por tenant, sin columna `area_id`; RLS `filosofia_policy` solo filtra por tenant) → el JefeArea lee los valores completos del ciclo (RN-007: solo lectura), sin `AND area_id`. Respuestas siempre con `ApiResponse<T>` (ARCH-07).

| Método | Ruta | Auth | Descripción |
|--------|------|------|-------------|
| GET | `/api/v1/ciclos/{cicloId}/filosofia` | `[Authorize(Roles = "AdminTenant,Gerente,JefeArea")]` | **EXTENDIDO aditivamente (HU-011 → HU-012):** ahora incluye `Valores` (`List<string>`) en `FilosofiaResponse` (CA #5: JEF lee). Mismo comportamiento defensivo D-H: si no existe fila `filosofia`, retorna 200 con `Valores = []` (lista vacía). **No se crea endpoint GET nuevo** (D-A): el GET existente ya devuelve la fila completa; añadir el campo es backward-compatible. |
| PUT | `/api/v1/ciclos/{cicloId}/filosofia/valores` | `[Authorize(Roles = "Gerente")]` | **NUEVO (HU-012):** registra/ordena/elimina la lista de Valores Corporativos del ciclo (CA #1-4, RF-014, RN-006). Body: `ValoresUpdateRequest` (lista **ya ordenada** — el orden del array es el orden final, D-C). Retorna 200 con `ApiResponse<FilosofiaResponse>` (estado completo de la filosofía). **403** rol ≠ GER (D12) · **404** ciclo inexistente/otro tenant/sin tenant · **422** si: ciclo `Cerrado` (RC-12), 0 valores, >15 valores, valor vacío tras trim, valor >100 chars, o duplicados case-insensitive (CA #4). **UPSERT** `ON CONFLICT (tenant_id, ciclo_id) DO UPDATE` (DB-06, D-B): crea la fila en el primer guardado con `vision=''`/`mision=''` y solo actualiza `valores`/`updated_by`/`updated_at` (no pisa vision/mision). |

> **Nota de ruteo:** `valores` (segmento literal) no colisiona con `filosofia` (HU-011) ni con `areas/{areaId:guid}`/`responsables/{responsableId:guid}` (constraints `:guid`).
> **No existe DELETE** (mismo criterio D15 de HU-007/HU-011): los valores se gestionan como lista completa en el PUT (agregar/eliminar/reordenar = enviar la lista resultante). El ciclo `Cerrado` la congela (RC-12).

**Códigos HTTP posibles:** 200 (GET/PUT), 400 (body malformado), 401 (sin token), 403 (rol distinto — p. ej. ADM o JEF intentando PUT), 404 (ciclo inexistente o `TenantContext.TenantId` null), 422 (regla de negocio violada), 500 (error no controlado, `ExceptionMiddleware`).

## Lógica BLL (paso a paso)

**Extensión del servicio existente** `PE-GOL.BLL/Services/FilosofiaService.cs` (HU-011): se añade el método `ActualizarValoresAsync(Guid cicloId, ValoresUpdateRequest request, CancellationToken ct)` a `IFilosofiaService`/`FilosofiaService`. **No se crea servicio nuevo** (D-I). Ctor intacto: `(ICicloRepository, TenantContext)` + overload `(..., ILogger<FilosofiaService>?)` (D-J/D13).
**Constantes existentes reutilizadas:** `RolGerente = "Gerente"`, `EntidadAuditoria = "Filosofia"`, `JsonOpcionesAuditoria` con `UnsafeRelaxedJsonEscaping` (ADR-003).
**Constantes nuevas:** `MaxValores = 15`, `MinValores = 1`, `MaxLongitudValor = 100`.
**Helpers:** `ObtenerTenantIdOThrow()` (existente), `SerializarValores(List<string>)`/`DeserializarValores(string)` (auditoría ADR-003 + mapeo), `MapToResponse` **extendido** para parsear `Valores`.

### 1. `ObtenerAsync(Guid cicloId, CancellationToken ct)` — EXTENSIÓN (mapeo de Valores)
Pasos 1-3 idénticos a HU-011 (tenantId 404 → ciclo 404 → DAL-F1). Cambio en el paso 4:
4. Mapear → `FilosofiaResponse` con `Valores = DeserializarValores(e.Valores)` (parseo del JSONB string → `List<string>`; si `e` es null → `Valores = []` — D-H; si el JSONB es `"[]"` o inválido → `[]` defensivo).

### 2. `ActualizarValoresAsync(Guid cicloId, ValoresUpdateRequest request, CancellationToken ct)` — NUEVO
1. **D12:** `_tenantContext.Rol != RolGerente` → `AccesoDenegadoException` (403). *(RN-006: el GER es el único con escritura del contenido estratégico — mismo criterio D-A de HU-011.)*
2. `tenantId = ObtenerTenantIdOThrow()` → 404.
3. Ciclo existe: `_repository.ObtenerPorIdAsync(tenantId, cicloId, ct)` (DAL-C2 reutilizada) → null → 404.
4. **RC-12:** `ciclo.Estado == "Cerrado"` → `ValidacionException` (422) "Un ciclo Cerrado es de solo lectura". *(Borrador y Activo permitidos — Flag #6, mismo criterio D-F de HU-011.)*
5. **Normalizar (trim):** `valores = request.Valores.Select(v => v.Trim()).ToList()` — se eliminan espacios iniciales/finales de cada valor (D-G).
6. **CA #4 — re-validación BLL (fuente de verdad, UX-04):**
   - `valores.Count < 1` → 422 "Debe registrar al menos 1 valor corporativo".
   - `valores.Count > 15` → 422 "Máximo 15 valores corporativos".
   - `valores.Any(v => string.IsNullOrWhiteSpace(v))` → 422 "Cada valor es requerido" (valor vacío tras trim).
   - `valores.Any(v => v.Length > 100)` → 422 "Cada valor no puede exceder 100 caracteres".
   - Duplicados case-insensitive: `valores.GroupBy(v => v, StringComparer.OrdinalIgnoreCase).Any(g => g.Count() > 1)` → 422 "No se permiten valores duplicados".
7. **Snapshot de auditoría (CA #4, ADR-003):** `previo = _repository.ObtenerFilosofiaAsync(tenantId, cicloId, ct)` (DAL-F1) → `valorAnterior = previo is null ? null : SerializarValores(DeserializarValores(previo.Valores))` (si no existía fila, el primer guardado se audita como `UPDATE` con `valor_anterior = null` — D-D, mismo criterio que HU-011).
8. **Serializar:** `valoresJson = JsonSerializer.Serialize(valores)` (string JSON para el parámetro `@Valores::jsonb` de DAL-F3).
9. **Transacción única** (`BeginTransactionAsync`, patrón HU-001..HU-011):
   - `_repository.UpsertFilosofiaValoresAsync(new FilosofiaValoresUpsertDto { TenantId, CicloId, Valores = valoresJson, UpdatedBy = _tenantContext.UserId ?? Guid.Empty }, tx, ct)` (DAL-F3, DB-06) → filas afectadas 0 → `InvalidOperationException`.
   - Auditoría: `_repository.InsertLogAsync(new LogAuditoriaInsert { TenantId, UsuarioId = _tenantContext.UserId, Accion = "UPDATE", Entidad = "Filosofia", EntidadId = cicloId.ToString(), ValorAnterior = valorAnterior, ValorNuevo = SerializarValores(valores) }, tx, ct)` (DAL-C11 reutilizada, ADR-003).
   - `tx.Commit()`.
10. Re-lectura post-commit (DAL-F1) → 200 `FilosofiaResponse` (con `Valores` poblado).
11. `catch (PostgresException ex) when (ex.SqlState == "23505")` → rollback explícito + 422 "Ya existe un registro de filosofía para este ciclo" (capa 2 BD del `UNIQUE (tenant_id, ciclo_id)` — patrón ADR-001; residual, el UPSERT lo evita en la práctica). `catch` general → rollback + rethrow.

> **No se toca `CicloService.ActivarAsync`** (HU-011 CA #2 ya valida vision/mision al activar). **Decisión abierta (no bloqueante):** ¿debe la activación exigir también ≥1 valor? El CA #4 de HU-012 dice "mínimo 1 valor requerido" pero no especifica *cuándo* (¿al activar o al guardar?). Propuesta: **solo al guardar** (el PUT valida min 1) — la activación ya valida vision/mision (HU-011) y añadir valores a esa validación sería una extensión de HU-011 ya cerrada. Se documenta como hallazgo para Jorge (Flag #7).

| ID | Método | SQL (parametrizado) |
|----|--------|---------------------|
| DAL-F1 | `ObtenerFilosofiaAsync` | **Reutilizada** (HU-011, ya selecciona `f.valores`) — sin cambios |
| DAL-F3 | `UpsertFilosofiaValoresAsync(FilosofiaValoresUpsertDto, tx, ct)` | `INSERT INTO filosofia (tenant_id, ciclo_id, vision, mision, valores, updated_by, updated_at) VALUES (@TenantId, @CicloId, '', '', @Valores::jsonb, @UpdatedBy, NOW()) ON CONFLICT (tenant_id, ciclo_id) DO UPDATE SET valores = EXCLUDED.valores, updated_by = EXCLUDED.updated_by, updated_at = NOW() RETURNING id, updated_at;` (DB-06, D-B — target = UNIQUE del DDL L173; **solo toca valores/updated_by/updated_at, NO pisa vision/mision**; INSERT inicial con `vision=''`/`mision=''` para que el GER pueda registrar valores sin haber escrito visión/misión aún) |

> **Sin migración:** la columna `valores` ya existe en el DDL (L170, `JSONB NOT NULL DEFAULT '[]'`) y el `UNIQUE (tenant_id, ciclo_id)` (L173) ya existe → target del `ON CONFLICT` (DB-06) y capa 2 ante carreras (23505 → 422, patrón ADR-001). **Sin ADR nuevo** (ver § Hallazgos).
