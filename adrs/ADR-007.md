# ADR-007 — Índice único parcial `uq_area_responsable_unico` para garantizar RN-012 a nivel BD (HU-009)

**Fecha:** 2026-09-17 · **Estado:** Aceptado
**Autor:** Jorge (Dicegsa) / @Arquitecto

## Contexto

La HU-009 (Gestión de Áreas Estratégicas) exige en su criterio de aceptación #3: **"Validar que un responsable no esté asignado a más de un área en el mismo ciclo (RN-012)"** (`docs/03_BACKLOG.md` líneas 185-199). Esta regla es la **RN-012** del dominio (`docs/02_REQUERIMIENTOS.md` L283): "un responsable (Jefe de Área) puede ser asignado a **una sola área** por ciclo. No puede ser responsable de dos áreas simultáneamente en el mismo ciclo".

Sin embargo, el DDL de `06_MODELO_DATOS.md` (líneas 194-212) **no define ninguna restricción que garantice RN-012 a nivel de base de datos**:

```sql
CREATE TABLE area (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID         NOT NULL REFERENCES tenant(id),
    ciclo_id        UUID         NOT NULL REFERENCES ciclo(id),
    codigo          VARCHAR(10)  NOT NULL,
    nombre          VARCHAR(150) NOT NULL,
    comentarios     TEXT,
    responsable_id  UUID         REFERENCES usuario(id),
    orden           INT          NOT NULL DEFAULT 0,
    activa          BOOLEAN      NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    UNIQUE (ciclo_id, codigo)   -- L206: garantiza unicidad del código GOL, NO RN-012
);
```

El único índice único existente es `UNIQUE (ciclo_id, codigo)` (L206), que cubre la unicidad del código GOL pero **no** RN-012: nada impide que dos filas del mismo ciclo tengan el mismo `responsable_id` simultáneamente.

El spec `specs/sprint-02/HU-009.spec.md` resuelve RN-012 en la capa de aplicación mediante la query **DAL-A8** (`ContarAreasConResponsableAsync`, paso 7 de `CrearAsync` y paso 8 de `ActualizarAsync`):

```sql
SELECT COUNT(1) FROM area
WHERE tenant_id = @TenantId
  AND ciclo_id = @CicloId
  AND responsable_id = @ResponsableId
  AND activa = TRUE
  AND (@ExcludeAreaId IS NULL OR id <> @ExcludeAreaId);
```

esa validación BLL es correcta como **primera capa** (mensaje de error amigable → HTTP 422), pero deja una **condición de carrera TOCTOU** (time-of-check to time-of-use): dos `AdminTenant` del mismo tenant pueden ejecutar `CrearAsync` en paralelo sobre áreas distintas del mismo ciclo (ambos `COUNT` ven 0), ambos pasan la validación y ambos `INSERT` persisten — quedando **un mismo responsable asignado a dos áreas del mismo ciclo**, violando RN-012. La carrera fue documentada explícitamente en el spec como decisión pendiente de ADR (**Flag #1**, sección «Flags para @Orquestador / Jorge», y **D-F** en «Decisiones de diseño»).

Conforme a [DB-01], toda modificación al esquema de base de datos requiere **ADR aprobado antes de ejecutar la migración**. Jorge aprobó la creación de este ADR el **2026-09-17** (Flag #1 del spec HU-009) para resolver la contradicción entre el DDL y el CA #3, **siguiendo el mismo patrón ya aceptado en ADR-006/ADR-001/ADR-002** (índice único + captura de SQLSTATE 23505 → 422).

**Requerimientos trazables:** RF (crear/editar/desactivar áreas estratégicas) · CA #3 HU-009 (responsable no asignado a más de un área por ciclo) · RN-012 (`02_REQUERIMIENTOS.md` L283) · [DB-01] (ADR previo a migración) · [DB-02] (scripts SQL versionados en `db/migrations/`) · [DB-04] (sin triggers para lógica de negocio).

## Opciones consideradas

1. **Índice único parcial: `CREATE UNIQUE INDEX uq_area_responsable_unico ON area (ciclo_id, responsable_id) WHERE responsable_id IS NOT NULL AND activa = TRUE;`**
   Garantiza RN-012 a nivel de base de datos de forma **declarativa y nativa de PostgreSQL**: el índice solo indexa las filas con responsable asignado y área activa, y su unicidad sobre `(ciclo_id, responsable_id)` impide que existan **dos áreas activas del mismo ciclo con el mismo responsable** (el segundo `INSERT`/`UPDATE` falla con `unique_violation` SQLSTATE 23505). No requiere modificar el DDL publicado; se aplica como migración versionada aditiva (`V004`). Costo de mantenimiento mínimo: el volumen de filas indexadas es acotado (una entrada por área activa con responsable). **Consistente con ADR-006/ADR-001/ADR-002**: misma solución, misma captura de SQLSTATE 23505 → `ValidacionException` → HTTP 422, mismo patrón de defensa en dos capas (BLL + BD).

2. **Trigger `BEFORE INSERT OR UPDATE` en `area` que cuente las asignaciones del responsable y aborte si ya existe una.**
   Implementaría la regla con lógica procedural en PostgreSQL. **Rechazada**: [DB-04] prohíbe explícitamente el uso de triggers PostgreSQL para lógica de negocio ("Los campos calculados ... deberán calcularse en la BLL antes de persistirse. No se usarán triggers PostgreSQL para lógica de negocio"). Además, un trigger es código imperativo que duplica la regla en dos lenguajes (SQL + C#), es más difícil de testear con xUnit/Moq y de auditar, y rompe el principio del proyecto de que la BLL es la fuente de verdad de las reglas de negocio.

3. **Solo validación BLL existente (DAL-A8) + aceptar el riesgo TOCTOU en concurrencia.**
   Mantiene la implementación actual del spec sin cambios de BD. Simple, sin migración, pero el CA #3 no queda garantizado en escenarios de concurrencia: dos `AdminTenant` del mismo tenant asignando el mismo JefeArea a dos áreas distintas en milisegundos pueden persistir ambas asignaciones. El requisito "un responsable por área por ciclo" quedaría dependiente del timing, no de una invariante — un defecto de integridad de datos. **Rechazada**: es la misma razón por la que se rechazó la opción equivalente en ADR-001/ADR-002/ADR-006; el costo del índice parcial es mínimo y la violación del CA es un defecto de integridad de datos.

## Decisión

Se adopta la **Opción 1**: índice único parcial sobre `area(ciclo_id, responsable_id)` con `WHERE responsable_id IS NOT NULL AND activa = TRUE`.

- Se crea la migración versionada **`db/migrations/V004__unico_responsable_area.sql`** (nomenclatura conforme a [DB-02]) con el siguiente contenido:

```sql
-- ============================================================
-- V004__unico_responsable_area.sql
-- ADR-007 (Aceptado 2026-09-17): garantizar RN-012 "un
-- responsable por área por ciclo" a nivel de base de datos
-- (CA #3 HU-009).
-- Autor: Jorge (Dicegsa) / @Arquitecto · Fecha: 2026-09-17
-- ============================================================
CREATE UNIQUE INDEX uq_area_responsable_unico
    ON area (ciclo_id, responsable_id)
    WHERE responsable_id IS NOT NULL AND activa = TRUE;
```

- **Defensa en profundidad en dos capas:**
  1. **Capa 1 — BLL (se mantiene):** la validación `ContarAreasConResponsableAsync` (DAL-A8, `COUNT` con `activa = TRUE` y `ExcludeAreaId`) se conserva tal cual en `AreaService.CrearAsync` (paso 7) y `AreaService.ActualizarAsync` (paso 8) para devolver el mensaje de error amigable "El responsable ya está asignado a otra área activa de este ciclo" → HTTP 422, sin depender de excepciones de BD.
  2. **Capa 2 — BD (nueva):** el índice único parcial elimina la condición de carrera TOCTOU. Si una asignación concurrente logra pasar la capa 1, el `INSERT` (DAL-A1) o `UPDATE` (DAL-A4) fallará con `unique_violation` (SQLSTATE 23505) y **no se persistirá la segunda asignación**.

- **Nota de manejo de la violación de constraint (nota de implementación):** en `AreaService.CrearAsync` y `AreaService.ActualizarAsync`, dentro del `try/catch` alrededor de la operación de escritura transaccional, capturar `PostgresException` con `SqlState == "23505"` (`unique_violation`) y traducirla a `ValidacionException` ("El responsable ya está asignado a otra área activa de este ciclo") → el `ExceptionMiddleware` la devuelve como HTTP 422. Importante: al detectarse la violación la transacción PostgreSQL queda en estado `aborted`; la BLL debe ejecutar `rollback` de la `IDbTransaction` **antes** de propagar la `ValidacionException`, para no reutilizar una transacción inválida ni enmascarar el error con un `InvalidOperationException` posterior. **Mismo patrón exacto que `TenantService` de HU-001, `PlanService` de HU-002 y `CicloService` de HU-007** (ver ADR-001, líneas 52-56; ADR-002, línea 68; ADR-006, línea 79).

- **Nota de alcance del índice:** el predicado `WHERE responsable_id IS NOT NULL AND activa = TRUE` limita la unicidad **solo a las filas con responsable asignado y área activa**. Las áreas sin responsable (`responsable_id IS NULL`) no participan del índice (RN-011 solo exige responsable en áreas Activas, pero el índice cubre el caso general). Las áreas inactivas (`activa = FALSE`) tampoco participan: **desactivar libera al responsable** para reasignación en el mismo ciclo — comportamiento deseado (Flag #7 / D-G: RN-012 aplica solo a áreas activas). El índice no interfiere con `UNIQUE (ciclo_id, codigo)` (L206), que sigue garantizando la unicidad del código GOL para todos los estados.

## Consecuencias

**Positivas:**
- RN-012 ("un responsable por área por ciclo") garantizada a nivel de BD como invariante, eliminando la condición de carrera TOCTOU documentada en el spec (Flag #1 / D-F).
- CA #3 de HU-009 queda satisfecho incluso bajo asignaciones concurrentes de dos `AdminTenant` del mismo tenant.
- El mensaje amigable de la BLL se conserva (capa 1), por lo que el usuario final no ve errores de BD crudos.
- Costo de mantenimiento nulo y de escritura despreciable: el índice lo mantiene PostgreSQL automáticamente y su volumen es acotado (una entrada por área activa con responsable).
- Máxima consistencia con los precedentes aceptados: misma solución, misma migración aditiva, mismo manejo de 23505 que ADR-001/ADR-002/ADR-006 — reduce el coste cognitivo de revisión y de implementación.
- Alineado con la recomendación ya documentada en el spec (Flag #1, sección «Flags para @Orquestador / Jorge», y Criterio de Done, línea 347).

**Trade-offs aceptados:**
- La violación de constraint residual en concurrencia debe capturarse como `23505` y traducirse a `ValidacionException` → HTTP 422 en la BLL, con rollback explícito de la transacción (costo de manejo acotado a 2 métodos: `CrearAsync` y `ActualizarAsync`).
- Migración nueva `V004` pendiente de aplicar en Supabase (junto a V001/V002/V003) — no ejecutada en este ADR.
- El índice parcial **no aplica a áreas inactivas**: si en el futuro Jorge relaja RN-012 (p. ej. múltiples ciclos activos simultáneos con el mismo responsable en áreas distintas), el índice debe **reemplazarse** (drop + recreación con el nuevo predicado), previo ADR nuevo — no es un cambio aditivo trivial.
- El DDL publicado en `06_MODELO_DATOS.md` (líneas 194-212) no refleja el índice; la migración `V004` es el artefacto que aplica el cambio en BD. **Acción de seguimiento para @Documenter:** actualizar `06_MODELO_DATOS.md` para reflejar el índice `uq_area_responsable_unico` (o referenciar este ADR) al cierre del Sprint 2, sin ejecutar ninguna migración adicional (misma acción que quedó pendiente para `uq_tenant_nombre` en ADR-001, `uq_plan_nombre` en ADR-002 y `uq_ciclo_unico_activo` en ADR-006).
