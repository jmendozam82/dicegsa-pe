# ADR-003 — Estandarizar `UnsafeRelaxedJsonEscaping` para la serialización JSON de auditoría

**Fecha:** 2026-09-13 · **Estado:** Aceptado
**Autor:** Jorge (Dicegsa) / @Arquitecto

## Contexto

Todos los servicios de escritura del sistema deben registrar auditoría en `log_auditoria` (RF-006, CA "log de auditoría" de EP-01). El DDL (`06_MODELO_DATOS.md` L110-121) persiste los cambios como `valor_anterior`/`valor_nuevo` de tipo `JSONB`, y el patrón establecido (spec HU-001/HU-002) serializa los snapshots con `JsonSerializer.Serialize`.

Al serializar objetos de dominio que contienen texto en español (p. ej. `descripcion = "Plan Estándar"`), las opciones por defecto de `System.Text.Json` generan escapes Unicode del tipo `"Est\u00E1ndar"`. El requisito RNF-023 (`02_REQUERIMIENTOS.md` — logging/auditoría en formato legible) exige que el JSON de auditoría sea **legible por humanos**, tanto en la vista de `log_auditoria` del SuperAdmin (HU-005) como en los reportes y exportaciones que consumirán ese JSON.

Durante HU-002 se evidenció la inconsistencia: `PlanService` ya resuelve el problema con `JsonSerializerOptions` usando `UnsafeRelaxedJsonEscaping` (verificado: `PE-GOL.BLL/Services/PlanService.cs` L46-48 y L198-199), pero `TenantService` y los futuros servicios (ciclo/área/OKR) usan el encoder por defecto — el JSON de auditoría del tenant quedaría ilegible (con `\u00E1`).

> Decisión de Jorge (2026-09-13, HANDOFF_PE_GOL.md L177 y L191): crear **ADR-003** (estandarizar `UnsafeRelaxedJsonEscaping` en todos los servicios que emiten JSON de auditoría), implementado a partir de HU-003 en `UsuarioService`. NO se parchea cada servicio con comentarios inline; el ADR documenta el patrón antes de que llegue a servicios de ciclo/área.

## Opciones consideradas

1. **Opción de Jorge — Opciones `JsonSerializerOptions` compartidas con `UnsafeRelaxedJsonEscaping` en todos los servicios BLL que emiten `valor_anterior`/`valor_nuevo`.**
   Define una instancia estática (p. ej. `JsonOpcionesAuditoria`) en cada servicio de escritura — o idealmente un helper compartido en `PE-GOL.Utility` — aplicando el encoder relajado **únicamente** a la serialización de auditoría. El JSON resultante conserva caracteres no-ASCII legibles (`"Estándar"`), satisface RNF-023 y es idéntico al patrón ya aprobado en `PlanService` (HU-002, verificado). Escopo: solo JSON interno de auditoría; no afecta a las respuestas de la API.

2. **Mantener el encoder por defecto (`JsonSerializerOptions` sin configurar) en todos los servicios.**
   Cero cambios de código, pero el JSON de auditoría de `usuario` y de las futuras tablas de dominio emite escapes Unicode → viola RNF-023 (legibilidad) y genera inconsistencias entre `PlanService` (legible) y `TenantService` (ilegible). **Rechazada**: el Handoff ya registra que HU-002 avanzó la solución en `PlanService` y Jorge pidió estandarizarla.

3. **Aplicar `UnsafeRelaxedJsonEscaping` al serializador global de la API (respuestas HTTP).**
   Resolvería la legibilidad en todas partes, pero expone el encoder no-escaped en el contrato HTTP → riesgo de inyección de marcado en respuestas consumidas por navegador (el encoder relajado no escapa `<`, `>`, `&`, `'`, `"`). El valor de auditoría se persiste y se sirve dentro del wrapper `ApiResponse<T>`; romper la seguridad de salida por legibilidad de auditoría sería un trade-off inaceptable (SEC-05). **Rechazada parcial**: el encoder relajado queda aislado en la serialización de auditoría; las respuestas HTTP conservan el encoder por defecto.

## Decisión

Se adopta la **Opción 1**: toda serialización de JSON de auditoría (`valor_anterior`/`valor_nuevo` en `log_auditoria`) usará opciones `JsonSerializerOptions` con `Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping`, replicando el patrón ya implementado y verificado en `PlanService` (HU-002).

Reglas del patrón (obligatorias para todos los servicios de escritura a partir de HU-003):

1. **Único alcance:** el encoder relajado se USA **solo** para el JSON que se persiste en `log_auditoria.valor_anterior` / `valor_nuevo`. Prohibido aplicarlo en DTOs de respuesta de la API o en cuerpos de request serializados (esos usan la serialización por defecto de ASP.NET Core).
2. **No duplicar opciones por servicio:** definir preferentemente una helper estática compartida (si se crea, en `PE-GOL.Utility`), o en su defecto una instancia estática por servicio siguiendo exactamente el patrón de `PlanService` L46-48 (constante `JsonOpcionesAuditoria` con `UnsafeRelaxedJsonEscaping`).
3. **No usar comentarios inline** en el spec o en código para justificar el encoder: el ADR-003 es la fuente de verdad del patrón (HANDOFF L191).

**Restricciones de seguridad (no negociables):**
- El encoder relajado NO se aplica a respuestas HTTP ni a logs que alimenten directamente plantillas HTML.
- La auditoría sigue siendo interna (tabla fuera de RLS, accesible solo por SuperAdmin — decisión de Jorge, HANDOFF L156); nunca se expone al navegador mezclándola con HTML sin escapado.
- El JSON de auditoría se escribe como texto de auditoría y se renderiza en la UI de log (HU-005) mediante renderizado seguro (nunca `@Html.Raw` sin sanitización).

## Consecuencias

**Positivas:**
- RNF-023 satisfecho de forma uniforme desde HU-003 en adelante (legibilidad del JSON de auditoría con caracteres no-ASCII).
- Elimina la inconsistencia HU-001 (ilegible) vs HU-002 (legible) detectada en Sprint 1.
- Patrón único, documentado en ADR → `@QA` puede escribir tests que verifiquen que `valor_nuevo` contiene texto sin escapes Unicode (p. ej. `"descripcion":"Estándar"`), y `@Documenter` lo referencia desde el spec HU-003.
- No requiere migración de BD ni cambios de esquema; es una decisión de serialización de la capa BLL.

**Trade-offs aceptados:**
- El encoder produce strings que NO son HTML-safe: su propagación accidental a una respuesta HTML requeriría escapado. Se mitiga restringiendo el uso a `log_auditoria` (SEC-05, segunda línea) y a la renderización segura de HU-005.
- Depende de la disciplina de los servicios futuros para replicar el patrón (mitigado por el ADR + test de QA).
