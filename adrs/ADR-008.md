# ADR-008 — Bypass RLS para recálculo de progreso de Objetivo CG (HU-020)

**Fecha:** 2026-09-20 · **Estado:** Aceptado
**Autor:** @Arquitecto / @Documenter

## Contexto

Durante la implementación de la HU-020 (Actualización de Progreso de Acciones), se identificó un problema crítico de seguridad a nivel base de datos:
La operación de actualización de una acción de plan requiere recalcular el `progreso` y `semaforo` del **Objetivo CG** (Objetivo Corporativo) padre. El cálculo requiere obtener la suma ponderada del progreso de **todas las acciones del plan** asociadas a dicho objetivo (regla RN-018).

Sin embargo, en Supabase, la tabla `accion_plan` posee políticas Row-Level Security (RLS) estrictas, particularmente `accion_plan_policy` que, para un usuario con rol `JefeArea`, restringe los registros visibles únicamente a las acciones pertenecientes a su propia área.
Si el método `RecalcularProgresoAsync` se ejecuta bajo el `TenantContext` estándar de un `JefeArea`, la consulta en base de datos filtrará inadvertidamente las acciones de otras áreas. Como resultado, la suma del progreso del Objetivo CG será **incorrecta** (solo sumará el progreso de un área, en lugar de toda la compañía).

## Opciones consideradas

1. **Resolver el recálculo en Memoria (BLL):** Modificar la lógica para que el BLL recupere todas las acciones, pero como la BLL lee desde el DAL (sujeto a RLS), igual se requiere una vía de bypass de lectura.
2. **PostgreSQL SECURITY DEFINER:** Crear un Stored Procedure o Función en PostgreSQL con el modificador `SECURITY DEFINER`, el cual se ejecuta con privilegios de administrador y elude el RLS para realizar el recálculo. La DAL invocaría esta función.
3. **Uso de `service_role` Connection String (Bypass RLS):** De forma análoga a la decisión documentada en `HANDOFF_PE_GOL.md` (Punto 4b de Decisiones de Jorge: uso de `service_role` para DAL-P8 `ObtenerConteosUsoAsync`), crear/instanciar una conexión específica utilizando la key `service_role` de Supabase exclusivamente para este recálculo en la DAL.

## Decisión

Se elige la **Opción 3 (service_role Connection)** por consistencia arquitectónica.

Ya existe un precedente aprobado en el proyecto para bypassear RLS en cálculos de agregación globales de sistema (`ObtenerConteosUsoAsync`).
El repositorio `ObjetivoCgRepository` o el inyector de dependencias (IOC) deberá proveer una instancia de conexión separada configurada con `service_role` (bypass RLS) exclusivamente para el método `RecalcularProgresoAsync`.

## Consecuencias

- **Positivas:** El cálculo del progreso del corporativo será matemáticamente exacto, contemplando todas las áreas sin que el RLS lo filtre, manteniendo las reglas de dominio (RN-018).
- **Negativas / Trade-offs:** Introduce la necesidad de gestionar una segunda cadena de conexión en el DAL, lo cual incrementa ligeramente la complejidad en la inyección de dependencias (`IDbConnectionFactory` requerirá soportar conexiones elevadas).
- **Acción requerida (Deploy):** Al momento del deploy a Supabase, el `BackendDev` debe asegurar que la variable de entorno para la cadena de conexión "Elevada" (usando el token `service_role`) esté correctamente configurada.
