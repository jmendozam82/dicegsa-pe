# ADR-006 — Índice único parcial `uq_ciclo_unico_activo` para garantizar RC-01 a nivel BD (HU-007)

**Fecha:** 2026-09-14 · **Estado:** Aceptado
**Autor:** Jorge (Dicegsa) / @Arquitecto

## Contexto

La HU-007 (Gestión de Ciclos Anuales) exige en su criterio de aceptación #3: **"El ADM puede activar un ciclo (pasa a estado Activo); solo un ciclo puede estar Activo a la vez"** (`docs/03_BACKLOG.md` líneas 151-163). Esta regla es la **RC-01** del dominio (`docs/05_DOMINIO.md` L543): "solo un ciclo Activo por tenant".

Sin embargo, el DDL de `06_MODELO_DATOS.md` (líneas 129-143) **no define ninguna restricción que garantice RC-01 a nivel de base de datos**:

```sql
CREATE TABLE ciclo (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID         NOT NULL REFERENCES tenant(id),
    nombre          VARCHAR(100) NOT NULL,
    año_fiscal      INT          NOT NULL,
    mes_inicio      INT          NOT NULL DEFAULT 1 CHECK (mes_inicio BETWEEN 1 AND 12),
    estado          estado_ciclo NOT NULL DEFAULT 'Borrador',
    created_by      UUID         NOT NULL REFERENCES usuario(id),
    activated_at    TIMESTAMPTZ,
    closed_at       TIMESTAMPTZ,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    UNIQUE (tenant_id, año_fiscal)   -- L141: garantiza CA #2 (un año fiscal por tenant), NO RC-01
);
```

El único índice único existente es `UNIQUE (tenant_id, año_fiscal)` (L141), que cubre el CA #2 pero **no** el CA #3: nada impide que dos filas del mismo tenant tengan `estado = 'Activo'` simultáneamente. El enum `estado_ciclo` (`06` L35: `'Borrador' | 'Activo' | 'Cerrado'`) tampoco aporta restricción entre filas.

El spec `specs/sprint-01/HU-007.spec.md` resuelve RC-01 en la capa de aplicación mediante la query **DAL-C7** (`ContarCiclosActivosAsync`, paso 6 de `ActivarAsync`):

```sql
SELECT COUNT(1) FROM ciclo
WHERE tenant_id = @TenantId
  AND estado = 'Activo'::estado_ciclo
  AND id <> @ExcludeId;
```

esa validación BLL es correcta como **primera capa** (mensaje de error amigable → HTTP 422), pero deja una **condición de carrera TOCTOU** (time-of-check to time-of-use): dos `AdminTenant` del mismo tenant pueden ejecutar `ActivarAsync` en paralelo sobre ciclos distintos (ambos `Borrador`), ambos `COUNT` ven 0 activos, ambos pasan la validación y ambos `UPDATE` persisten `estado='Activo'` — quedando **dos ciclos Activos en el mismo tenant**, violando RC-01. La carrera fue documentada explícitamente en el spec como decisión pendiente de ADR (**D-ADR-1**, sección «Decisiones de ADR (resueltas)», y **D9** en «Decisiones de diseño»).

Conforme a [DB-01], toda modificación al esquema de base de datos requiere **ADR aprobado antes de ejecutar la migración**. Jorge aprobó la creación de este ADR el **2026-09-14** (Flag #4 del spec HU-007) para resolver la contradicción entre el DDL y el CA #3, **siguiendo el mismo patrón ya aceptado en ADR-001/ADR-002** (índice único + captura de SQLSTATE 23505 → 422).

**Requerimientos trazables:** RF-002 (crear ciclos anuales por tenant) · CA #3 HU-007 (solo un ciclo Activo a la vez) · RC-01 (`05_DOMINIO.md` L543) · [DB-01] (ADR previo a migración) · [DB-02] (scripts SQL versionados en `db/migrations/`) · [DB-04] (sin triggers para lógica de negocio).

## Opciones consideradas

1. **Índice único parcial: `CREATE UNIQUE INDEX uq_ciclo_unico_activo ON ciclo (tenant_id) WHERE estado = 'Activo';`**
   Garantiza RC-01 a nivel de base de datos de forma **declarativa y nativa de PostgreSQL**: el índice solo indexa las filas con `estado = 'Activo'`, y su unicidad sobre `(tenant_id)` impide que existan **dos filas Activas del mismo tenant** (el segundo `UPDATE` a `'Activo'` falla con `unique_violation` SQLSTATE 23505). No requiere modificar el DDL publicado; se aplica como migración versionada aditiva (`V003`). Costo de mantenimiento mínimo: el volumen de filas indexadas es **siempre 0 o 1 por tenant** (invariante que el propio índice garantiza), por lo que el índice es diminuto y su costo de escritura despreciable. **Consistente con ADR-001/ADR-002**: misma solución, misma captura de SQLSTATE 23505 → `ValidacionException` → HTTP 422, mismo patrón de defensa en dos capas (BLL + BD).

2. **Trigger `BEFORE INSERT OR UPDATE` en `ciclo` que cuente los activos y aborte si ya existe uno.**
   Implementaría la regla con lógica procedural en PostgreSQL. **Rechazada**: [DB-04] prohíbe explícitamente el uso de triggers PostgreSQL para lógica de negocio ("Los campos calculados ... deberán calcularse en la BLL antes de persistirse. No se usarán triggers PostgreSQL para lógica de negocio"). Además, un trigger es código imperativo que duplica la regla en dos lenguajes (SQL + C#), es más difícil de testear con xUnit/Moq y de auditar, y rompe el principio del proyecto de que la BLL es la fuente de verdad de las reglas de negocio.

3. **Solo validación BLL existente (DAL-C7) + aceptar el riesgo TOCTOU en concurrencia.**
   Mantiene la implementación actual del spec sin cambios de BD. Simple, sin migración, pero el CA #3 no queda garantizado en escenarios de concurrencia: dos `AdminTenant` del mismo tenant activando ciclos distintos en milisegundos pueden persistir dos ciclos Activos. El requisito "solo un ciclo Activo a la vez" quedaría dependiente del timing, no de una invariante — un defecto de integridad de datos que además degradaría la semántica de `max_ciclos_activos` (DAL-P8 de HU-002 cuenta solo ciclos `Activo`). **Rechazada**: es la misma razón por la que se rechazó la opción equivalente en ADR-001/ADR-002; el costo del índice parcial es mínimo y la violación del CA es un defecto de integridad de datos.

## Decisión

Se adopta la **Opción 1**: índice único parcial sobre `ciclo(tenant_id)` con `WHERE estado = 'Activo'`.

- Se crea la migración versionada **`db/migrations/V003__unico_ciclo_activo.sql`** (nomenclatura conforme a [DB-02]) con el siguiente contenido:

```sql
-- ============================================================
-- V003__unico_ciclo_activo.sql
-- ADR-006 (Aceptado 2026-09-14): garantizar RC-01 "solo un
-- ciclo Activo por tenant" a nivel de base de datos (CA #3 HU-007).
-- Autor: @Arquitecto · Fecha: 2026-09-14
-- ============================================================
CREATE UNIQUE INDEX uq_ciclo_unico_activo
    ON ciclo (tenant_id)
    WHERE estado = 'Activo';
```

- **Defensa en profundidad en dos capas:**
  1. **Capa 1 — BLL (se mantiene):** la validación `ContarCiclosActivosAsync` (DAL-C7, `COUNT` con `estado='Activo'` y `ExcludeId`) se conserva tal cual en `CicloService.ActivarAsync` (paso 6) para devolver el mensaje de error amigable "Ya existe un ciclo activo en este tenant" → HTTP 422, sin depender de excepciones de BD.
  2. **Capa 2 — BD (nueva):** el índice único parcial elimina la condición de carrera TOCTOU. Si una activación concurrente logra pasar la capa 1, el `UPDATE ciclo SET estado='Activo'` (DAL-C5) fallará con `unique_violation` (SQLSTATE 23505) y **no se persistirá el segundo ciclo Activo**.

- **Nota de manejo de la violación de constraint (nota de implementación):** en `CicloService.ActivarAsync`, dentro del `try/catch` alrededor de la operación de escritura transaccional (paso 8 del spec), capturar `PostgresException` con `SqlState == "23505"` (`unique_violation`) y traducirla a `ValidacionException` ("Ya existe un ciclo activo en este tenant") → el `ExceptionMiddleware` la devuelve como HTTP 422. Importante: al detectarse la violación la transacción PostgreSQL queda en estado `aborted`; la BLL debe ejecutar `rollback` de la `IDbTransaction` **antes** de propagar la `ValidacionException`, para no reutilizar una transacción inválida ni enmascarar el error con un `InvalidOperationException` posterior. **Mismo patrón exacto que `TenantService` de HU-001 y `PlanService` de HU-002** (ver ADR-001, líneas 52-56, y ADR-002, línea 68).

- **Nota de alcance del índice:** el predicado `WHERE estado = 'Activo'` limita la unicidad **solo a las filas Activas**. Los estados `Borrador` y `Cerrado` no participan del índice: un tenant puede tener N ciclos `Borrador` y N ciclos `Cerrado` (históricos) sin colisión — comportamiento deseado (RC-01 aplica únicamente al estado Activo). El índice no interfiere con `UNIQUE (tenant_id, año_fiscal)` (L141), que sigue garantizando el CA #2 para todos los estados.

## Consecuencias

**Positivas:**
- RC-01 ("solo un ciclo Activo por tenant") garantizada a nivel de BD como invariante, eliminando la condición de carrera TOCTOU documentada en el spec (D-ADR-1 / D9).
- CA #3 de HU-007 queda satisfecho incluso bajo activaciones concurrentes de dos `AdminTenant` del mismo tenant.
- El mensaje amigable de la BLL se conserva (capa 1), por lo que el usuario final no ve errores de BD crudos.
- Costo de mantenimiento nulo y de escritura despreciable: el índice lo mantiene PostgreSQL automáticamente y su volumen es siempre 0 o 1 fila por tenant (la propia invariante lo acota).
- Máxima consistencia con los precedentes aceptados: misma solución, misma migración aditiva, mismo manejo de 23505 que ADR-001/ADR-002 — reduce el coste cognitivo de revisión y de implementación.
- Alineado con la recomendación ya documentada en el spec (D-ADR-1, sección «Decisiones de ADR (resueltas)», y Criterio de Done, línea 513).

**Trade-offs aceptados:**
- La violación de constraint residual en concurrencia debe capturarse como `23505` y traducirse a `ValidacionException` → HTTP 422 en la BLL, con rollback explícito de la transacción (costo de manejo acotado a 1 método: `ActivarAsync`).
- Migración nueva `V003` pendiente de aplicar en Supabase (junto a V001/V002) — no ejecutada en este ADR.
- El índice parcial **no aplica a otros estados**: si en el futuro Jorge relaja RC-01 (p. ej. un plan Premium con 2 ciclos activos, ver Flag #5 del spec HU-007 y `max_ciclos_activos=2` del seed `06` L583-586), el índice debe **reemplazarse** (drop + recreación con el nuevo predicado o con `(tenant_id, estado)`), previo ADR nuevo — no es un cambio aditivo trivial.
- El DDL publicado en `06_MODELO_DATOS.md` (líneas 129-143) no refleja el índice; la migración `V003` es el artefacto que aplica el cambio en BD. **Acción de seguimiento para @Documenter:** actualizar `06_MODELO_DATOS.md` para reflejar el índice `uq_ciclo_unico_activo` (o referenciar este ADR) al cierre del Sprint 1, sin ejecutar ninguna migración adicional (misma acción que quedó pendiente para `uq_tenant_nombre` en ADR-001 y `uq_plan_nombre` en ADR-002).
