# ADR-009 — Cimiento de frontend dentro de HU-045 + funciones RLS en schema public

**Fecha:** 2026-09-20 · **Estado:** Aceptado
**Autor:** @Arquitecto / @Documenter

> Este ADR documenta **dos decisiones** tomadas durante la implementación y el deploy de la HU-045 (UI de Gestión de Tenants — alcance ampliado). La Decisión 1 fue aprobada por **Jorge** el 2026-09-20 (vinculante, incorporada al spec). La Decisión 2 fue aceptada por **@Orquestador** como ajuste técnico necesario durante el deploy a Supabase Cloud (2026-09-20).

## Decisión 1 — Cimiento de frontend implementado DENTRO de HU-045 (no se crea HU-046)

### Contexto

`PE-GOL.Aplicacion` era la plantilla MVC por defecto (Program.cs de 27 líneas, `_Layout.cshtml` de plantilla, sin ApiClient, sin sesión/JWT, sin Design System). HU-045 era la **primera HU con UI real** del proyecto: HU-001..HU-020 se entregaron 100% backend con la UI diferida a "HU-045 y siguientes" (HANDOFF L229). El cimiento de frontend (ApiClient + sesión + AuthController MVC + Layout DS) era **requisito habilitador** de la UI de tenants y de todas las UI futuras.

El borrador del spec HU-045 contemplaba dos opciones: (a) HU-045 solo con la UI de tenants y una HU-046 separada para el cimiento, o (b) HU-045 absorbe TODO (cimiento + 15 vistas diferidas + migraciones).

### Opciones consideradas

1. **HU-046 separada para el cimiento** (recomendación original de @Arquitecto): ticket dedicado, menor riesgo de alcance, pero duplicaba la coordinación y dejaba la UI de tenants bloqueada hasta el Sprint siguiente.
2. **HU-045 absorbe TODO** (decisión de Jorge): cimiento + UI de tenants + 15 vistas diferidas de HU-006..HU-020 + migraciones V001–V004 en un solo ticket bien delimitado, como última HU del Sprint 3 (26 pts backend ya entregados en HU-016..HU-020).

### Decisión

Se elige la **Opción 2** — **aprobada por Jorge el 2026-09-20 (Flag 1 resuelto)**. El cimiento de frontend (ApiClient + SesionService + AuthController MVC + Layout DS) se implementa **dentro de HU-045** (3 pts nominales), absorbiendo las 15 vistas diferidas de HU-006..HU-020 y las migraciones V001–V004. **No se crea HU-046.**

**Desviación de puntos:** alcance efectivo ~30 pts absorbidos en ticket de 3 pts. Se documenta en el encabezado del spec y como nota en `docs/03_BACKLOG.md`.

### Consecuencias

- **Positivas:** el cimiento queda como activo reutilizable (ApiClient + sesión + AuthController + Layout DS) para todas las UI futuras; el Sprint 3 se cierra completo (6/6 HU) con la plataforma con UI operativa de punta a punta.
- **Negativas / Trade-offs:** ticket con alcance muy superior a sus puntos nominales (3 pts vs ~30 pts efectivos); el seguimiento de la HU requirió 4 tandas de implementación de UI. La desviación de puntos queda registrada en el backlog para el cálculo de velocidad.
- **Acción requerida:** `@Documenter` registra la desviación en `docs/03_BACKLOG.md` (HU-045) y el patrón del cimiento (ApiClient + sesión + cookie MVC) queda como referencia obligatoria para las UI futuras (HU-021..HU-044).

## Decisión 2 — Funciones auxiliares de RLS en schema `public` en lugar de `auth.*`

### Contexto

`06_MODELO_DATOS.md` indica que las funciones auxiliares de RLS (`tenant_id()`, `user_rol()`, `area_id()`) se crean en el schema `auth`. Durante el deploy de la HU-045 a **Supabase Cloud (PostgreSQL 17.6)**, al ejecutar `V000__schema_base.sql`, el rol `postgres` recibió el error **42501 permission denied** al intentar `CREATE FUNCTION auth.tenant_id()`: en Supabase el schema `auth` pertenece a `supabase_admin` y el rol `postgres` no tiene privilegios de CREATE sobre él.

### Opciones consideradas

1. **Crear las funciones en schema `auth`** (como indica el doc 06): bloqueado por Supabase — el rol `postgres` no puede CREATE en `auth` (42501 permission denied; el schema pertenece a `supabase_admin`).
2. **Crear las funciones en schema `public`** (ajuste técnico): Supabase permite CREATE en `public` al rol `postgres`. Las funciones leen `request.jwt.claims` (mismo mecanismo que la opción 1) y las políticas RLS las referencian como `public.tenant_id()` etc. Comportamiento idéntico.
3. **Elevar privilegios / usar `supabase_admin`**: no disponible — el acceso a `supabase_admin` no se expone a los clientes del proyecto.

### Decisión

Se elige la **Opción 2** — **aceptada por @Orquestador como ajuste técnico necesario** durante el deploy (2026-09-20). Las funciones auxiliares de RLS (`tenant_id`, `user_rol`, `area_id`) se crean en schema **`public`** en lugar de `auth.*`. La desviación queda documentada en el header de `db/migrations/V000__schema_base.sql` (NOTA DESVIACION 2026-09-20). Comportamiento idéntico: las funciones leen `request.jwt.claims` y las políticas RLS las referencian como `public.tenant_id()` / `public.user_rol()` / `public.area_id()`.

### Consecuencias

- **Positivas:** el DDL base se ejecuta sin errores en Supabase Cloud; el aislamiento multi-tenant por RLS queda operativo (ARCH-04) con el mismo comportamiento funcional.
- **Negativas / Trade-offs:** desviación documental respecto a `06_MODELO_DATOS.md` (las políticas RLS referencian `public.*` en lugar de `auth.*`). El documento 06 queda desactualizado en este punto; se recomienda actualizarlo en una revisión futura del modelo de datos.
- **Acción requerida:** ninguna adicional — la desviación está registrada en el header de `V000__schema_base.sql` y en este ADR. Las migraciones V001–V004 no se ven afectadas (DDL de índices, sin funciones).
