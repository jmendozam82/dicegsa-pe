# ADR-015 — Tipado explícito de parámetros opcionales de fecha en Dapper con Npgsql
**Fecha:** 2026-09-30 · **Estado:** Aceptado · **Autor:** @Arquitecto / Jorge (Dicegsa)

## Contexto

El patrón `AND (@P IS NULL OR col OP @P)` es el mecanismo estándar de filtros opcionales en todo el DAL de PE-GOL (`PlanConsolidadoRepository`, `LogAuditoriaRepository`, `ObjetivoCgRepository`, `CicloRepository`, `AccionPlanRepository`, `UsuarioRepository`, `TenantRepository`, `PlanRepository`). Funciona sin problemas con parámetros uuid/text/enum porque Postgres infiere un **único** tipo candidato del lado derecho (`a.area_id = $n` → uuid; `a.status::text = $n` → text).

**Falló en HU-023** con parámetros de fecha sobre columna `DATE`: `GET /api/v1/planes/consolidado` devolvía **HTTP 500** con `PostgresException 42P08` («could not determine data type of parameter $8»). Causa: con el objeto anónimo de Dapper y valor `null`, el parámetro viaja a Npgsql **sin tipo declarado**; en la primera aparición (`@P IS NULL`) el parser de Postgres no obtiene contexto de tipo y, al resolver `a.fecha_inicio >= $n` con la columna `DATE` (`accion_plan.fecha_inicio`, `db/migrations/V000__schema_base.sql:286`), el operador `>=` tiene **múltiples candidatos** (`date`/`timestamp`/`timestamptz`) → 42P08. Aislamiento empírico contra la BD real (los 7 filtros uno a uno): **solo los 2 de fecha fallan**; los otros 5 (uuid/text) tienen un único candidato y no fallan.

**Los 735 tests automatizados no lo detectaron** (`PlanConsolidadoRepositoryTests` usa dobles de `DbConnection` que capturan el SQL sin ejecutarlo contra Postgres); salió en la **validación visual en navegador** de HU-023 (2026-09-30) — misma clase de defecto runtime que AGENTS.md v1.25 documentó para HU-021.

## Opciones consideradas

1. **`Dapper.DynamicParameters` con `DbType.Date` explícito** — el repositorio construye `DynamicParameters` y declara el `DbType` de cada parámetro; Npgsql declara el parámetro como `date` y Postgres resuelve `date >= date` sin ambigüedad. **Verificada empíricamente contra la BD real** (5 escenarios: las 3 queries con filtros en null, con valores y combinados — pasan sin cambiar semántica).
2. **Cast en el SQL: `@P::date`** — descartada: **probada contra la BD real, sigue fallando con 42P08** (el parámetro sigue viajando sin tipo declarado a Npgsql; el cast en el texto del SQL no declara el tipo del parámetro en el protocolo).
3. **`COALESCE(@P, DATE '1900-01-01')` u otra reescritura de la cláusula** — descartada: funciona, pero sustituye el patrón uniforme del DAL por una cláusula especial solo para fechas, empeora la legibilidad y altera el plan de ejecución (el centinela `1900-01-01` participa en la comparación en lugar de un `OR` que la BD puede resolver por la rama nula).
4. **Construir las cláusulas WHERE dinámicamente en C# (StringBuilder)** — descartada: **SEC-05 prohíbe concatenar SQL** y rompe el patrón uniforme `IS NULL OR` de todo el DAL.

## Decisión

**Opción 1: `DynamicParameters` con `DbType` declarado.**

- **Obligatoria para cualquier parámetro de fecha** (`DateTime?`) usado en el patrón `IS NULL OR` sobre columnas `DATE`: se declara `DbType.Date` **en el cliente**; el SQL no se toca.
- **Aplica a `PlanConsolidadoRepository`** (HU-023): las 3 queries (`ListarConsolidadoAsync`, `CountConsolidadoAsync`, `ObtenerResumenAsync`) construyen `DynamicParameters` con `DbType` declarado para los 9 parámetros (`@FechaDesde`/`@FechaHasta` con `DbType.Date`; el resto `Guid`/`String`/`Int32`). El SQL no cambia (mismas cláusulas `IS NULL OR`, SEC-05 intacto).
- **`LogAuditoriaRepository` NO se toca**: usa `DateTimeOffset?` (`LogAuditoriaFiltrosDto.cs:25/28`) sobre `log_auditoria.created_at` que es `timestamptz` — **sin ambigüedad de candidatos**, verificado en vivo (funciona OK con `Desde`/`Hasta` en null). Tampoco `ObjetivoCgRepository`, `CicloRepository`, `AccionPlanRepository`, `UsuarioRepository`, `TenantRepository` ni `PlanRepository` (uuid/text/enum, verificados). **Nadie debe «arreglar» lo que no está roto.**

## Consecuencias

- **Positivo:** HU-023 funciona end-to-end (`GET /api/v1/planes/consolidado` → 200); el patrón `IS NULL OR` se conserva uniforme en todo el DAL (SEC-05); la regla queda escrita para HUs futuras que añadan filtros de fecha sobre columnas `DATE` (p. ej. rangos sobre `fecha_inicio`/`fecha_vencimiento`).
- **Trade-off:** cada repositorio con filtros de fecha debe construir `DynamicParameters` en vez de un objeto anónimo — un poco más verboso; las HUs futuras deben auditar que los parámetros de fecha viajen tipados.
- **Regla operativa para @QA y @BackendDev:** cuando un filtro de fecha nuevo se añada a un repositorio, el test debe verificar que el parámetro viaja **con `DbType` declarado** (`DbType.Date`), no solo que el SQL contiene el nombre del parámetro. El doble `ConexionCapturadora` de `PE-GOL.Tests` debe capturar `p.DbType`, no solo `p.Value` (extensión especificada en HU-023 v2 § Tests requeridos, casos R8/R9).
