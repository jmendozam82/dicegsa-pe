# ADR-012 — Índice `(tenant_id, ciclo_id, area_id)` en `accion_plan` y migración `V005`

**Fecha:** 2026-09-27 · **Estado:** Aceptado
**Autor:** @Arquitecto / Jorge (Dicegsa)

> Este ADR autoriza una **modificación del esquema de base de datos**: un índice compuesto sobre `accion_plan`. Nace del **flag F3** del spec `specs/sprint-04/HU-021.spec.md` (Vista Gantt del Plan de Acción) y es exigido por [DB-01] y [DB-02]. Jorge resolvió F3 el 2026-09-27 eligiendo la **Opción A**. Decisión relacionada: **ADR-011** (flag F1, licencia del DHTMLX Gantt que consume esta vista).

---

## Resumen ejecutivo

- Se crea el índice **`idx_accion_plan_ciclo_area`** sobre **`accion_plan (tenant_id, ciclo_id, area_id)`** mediante la migración versionada **`db/migrations/V005__indice_accion_plan_gantt.sql`**.
- El DDL base (`docs/06_MODELO_DATOS.md` L284-312) tiene índices en `objetivo_cg_id`, `area_id` y `status`, pero **ninguno cubre `tenant_id` + `ciclo_id`**, que es el filtro real de la query del Gantt.
- **Un solo índice cubre los dos roles:** el prefijo `(tenant_id, ciclo_id)` sirve al Gerente (RN-006) y la tercera columna `area_id` completa el filtro del Jefe de Área (SEC-07).
- Se aplica **ahora**, no cuando haya volumen: cierra la deuda de esquema antes de tener datos reales y alinea Sprint 4 con el estándar de migraciones ya vigente (V001–V004).

---

## Contexto

La query del Gantt (`AccionPlanRepository.ListarParaGanttAsync`, **DAL-G1** del spec HU-021) filtra por:

```sql
WHERE a.tenant_id = @TenantId
  AND a.ciclo_id  = @CicloId
  AND (@AreaIdFiltro IS NULL OR a.area_id = @AreaIdFiltro)
ORDER BY oc.orden ASC, oc.codigo ASC, a.orden ASC, a.codigo ASC;
```

Es decir, el filtro es siempre **`(tenant_id, ciclo_id)`**, y **`area_id` se agrega cuando el rol es `JefeArea`** (SEC-07: `AND area_id = @AreaId`; el Gerente ve todas las áreas por RN-006, de ahí el patrón `(@AreaIdFiltro IS NULL OR …)`).

El DDL actual de `accion_plan` (`docs/06_MODELO_DATOS.md` L310-312, `V000__schema_base.sql`) declara:

```sql
CREATE INDEX idx_accion_plan_objetivo ON accion_plan(objetivo_cg_id);
CREATE INDEX idx_accion_plan_area     ON accion_plan(area_id);
CREATE INDEX idx_accion_plan_status   ON accion_plan(status);
```

**Ninguno de los tres cubre `tenant_id` + `ciclo_id`**, que es el filtro real y obligatorio de la consulta. Los dos primeros solo ayudan como apoyo del `ORDER BY`/join; el tercero no participa del filtro.

Las consecuencias:

1. **Seq scan con multi-tenancy.** `accion_plan` es una tabla de dominio con `tenant_id` en todas sus filas ([DB-03]). Sin un índice que empiece por `tenant_id`, PostgreSQL tiene que recorrer filas de **todos** los tenants para resolver el filtro de un tenant concreto. Con un solo tenant es irrelevante; con N tenants el costo crece linealmente con N.
2. **RNF-001 (< 2 s en p95)** es un requisito duro, y la ventana de crecimiento es precisamente la de multi-tenancy — el caso para el que existe la arquitectura de aislamiento en dos capas ([ARCH-04], [SEC-07]).
3. El patrón del proyecto ya reconoce esta necesidad: `ciclo` tiene `uq_ciclo_unico_activo ON ciclo (tenant_id)` (ADR-006, `V003`) precisamente para resolver el ciclo activo de un tenant.

Con el volumen actual (decenas/cientos de filas) un seq scan es irrelevante en la práctica. El argumento no es el rendimiento de hoy, sino **no abrir una deuda de esquema justo en la HU que introduce la primera consulta por ciclo**, y cumplir lo que exigen [DB-01] y [DB-02].

---

## Opciones consideradas

### Opción A — Crear `CREATE INDEX (tenant_id, ciclo_id, area_id)` ahora ✅ ELEGIDA

Agrega el índice que cubre el filtro real de DAL-G1 con un solo objeto, para los dos roles.

**Impacto:** elimina el seq scan multi-tenant en la query del Gantt; costo de una migración `CREATE INDEX` trivial; Sprint 4 queda alineado con el estándar de migraciones versionadas; la deuda de esquema se cierra antes de tener datos reales, cuando crearla es más barata (sobre pocos datos, sin bloqueos largos).

### Opción B — Aplazar el índice hasta que haya volumen real

No crearlo hasta que un tenant alcance el volumen de RNF-004 (200 acciones) o que el plan de ejecución se degrade de forma medible en [RNF-001].

**Impacto:** cero trabajo ahora, pero abre deuda de esquema justo en la HU que crea la consulta por ciclo. Con datos ya cargados, crear el índice exige `CREATE INDEX CONCURRENTLY` y su propio procedimiento operativo.

**Descartada.**

---

## Decisión

Se elige la **Opción A**.

Esta decisión ejecuta lo que exigen las reglas inmutables del proyecto:

- **[DB-01]** — *"El schema de base de datos es el definido en `06_MODELO_DATOS.md`. Toda nueva tabla o modificación requiere un **ADR aprobado** antes de ejecutar la migración."* → Este ADR es esa aprobación.
- **[DB-02]** — *"Las migraciones de base de datos **deberán** ejecutarse con **scripts SQL versionados** en la carpeta `db/migrations/`, nombrados como `V{NNN}__{descripcion}.sql`. No se usa EF Core Migrations."* → `V005__indice_accion_plan_gantt.sql`.
- **[DB-03]** — el índice comienza por `tenant_id`, alineándose con el aislamiento multi-tenant de la tabla.
- **[DB-05]** — el índice **no** es `UNIQUE`: `accion_plan` permite múltiples acciones por ciclo, área y CG. No aplica el requisito de incluir `tenant_id` en índices únicos.

El DDL base de `06_MODELO_DATOS.md` § 2 **se mantiene intacto** (mismo criterio que V001–V004): el índice vive **solo** en la migración.

### Especificación exacta

| Atributo | Valor |
|---|---|
| **Nombre del índice** | **`idx_accion_plan_ciclo_area`** |
| **Tabla** | `accion_plan` |
| **Tipo** | `INDEX` no único, btree |
| **Columnas (en orden)** | `tenant_id`, `ciclo_id`, `area_id` |
| **Sentencia DDL** | ver abajo |
| **Migración** | `db/migrations/V005__indice_accion_plan_gantt.sql` |
| **ADR** | este documento (ADR-012) |

**DDL textual acordado:**

```sql
CREATE INDEX IF NOT EXISTS idx_accion_plan_ciclo_area
    ON accion_plan (tenant_id, ciclo_id, area_id);
```

> `IF NOT EXISTS` se incluye siguiendo el criterio de idempotencia de las migraciones del proyecto (`db/migrations/V002__unique_plan_nombre.sql` y `V004__unico_responsable_area.sql` lo omiten por ser la primera aplicación de un objeto de nombre único; aquí se mantiene por seguridad ante re-ejecuciones en entornos locales). @BackendDev confirma o ajusta el criterio al aplicar.

### Por qué este orden de columnas

| Rol | Filtro efetivo | Prefijo usado |
|---|---|---|
| **Gerente** (RN-006) | `tenant_id` + `ciclo_id` | `(tenant_id, ciclo_id)` — índice usado como **covering prefix**; la tercera columna no se evalúa |
| **Jefe de Área** (SEC-07) | `tenant_id` + `ciclo_id` + `area_id` | `(tenant_id, ciclo_id, area_id)` — coincidencia total |

Un solo índice cubre ambos casos; no hacen falta dos objetos ni un índice parcial por rol. `tenant_id` va **primero** por coherencia con el aislamiento ([DB-03], [ARCH-04]): en un escenario multi-tenant es la columna que más restringe el conjunto de filas y, por tanto, la que debe encabezar el índice.

## Consecuencias

### Positivas

- **Cierra la deuda de esquema antes de tener datos reales**, que es el momento más barato para crearla.
- **Elimina el seq scan multi-tenant** en DAL-G1 y sostiene [RNF-001] a medida que crece el número de tenants.
- **Alinea Sprint 4 con el estándar de migraciones** ya vigente (V001–V004), sin excepciones.
- El `ORDER BY` de DAL-G1 (`oc.orden, oc.codigo, a.orden, a.codigo`) puede aprovechar el índice para el prefijo `a.orden` vía los joins, reduciendo el sort en memoria.
- El DDL base queda **intacto** y el cambio queda **trazable y reversible** (un `DROP INDEX` documentado).

### Negativas / trade-offs (aceptados)

- **`CREATE INDEX` sin `CONCURRENTLY` bloquea escrituras durante la creación.** Es un trade-off consciente: `CONCURRENTLY` no puede ejecutarse dentro de una transacción, no admite `IF NOT EXISTS` en algunas versiones y es más lento. **Es aceptable en ventana de mantenimiento** — el Sprint 4 es pre-deploy y la tabla `accion_plan` está vacía o casi vacía, por lo que la creación es prácticamente instantánea.
- **Costo de escritura adicional** en cada `INSERT`/`UPDATE` de `accion_plan`: un índice más que mantener. Despreciable frente al volumen de RNF-004 y al beneficio en lectura.
- **Espacio en disco** adicional por el índice.
