# ADR-002 — Índice único sobre `plan(nombre)` para garantizar unicidad a nivel BD
**Fecha:** 2026-09-13 · **Estado:** Aceptado
**Autor:** Jorge (Dicegsa) / @Arquitecto

## Contexto

La HU-002 (Gestión de Planes de Suscripción) exige en su criterio de aceptación #1: **"Catálogo de planes con: nombre, max_areas, max_usuarios, max_ciclos_activos"** (`docs/03_BACKLOG.md` líneas 49-59). El nombre del plan es la clave natural del catálogo: el SuperAdmin identifica los planes por nombre y el seed ya persiste `Básico` / `Estándar` / `Premium` (06_MODELO_DATOS.md líneas 579-582). Sin embargo, el DDL de `06_MODELO_DATOS.md` (líneas 52-60) **no define ninguna restricción `UNIQUE` ni índice único sobre `plan.nombre`**:

```sql
CREATE TABLE plan (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    nombre              VARCHAR(50)  NOT NULL,
    max_areas           INT          NOT NULL DEFAULT 10,
    max_usuarios        INT          NOT NULL DEFAULT 20,
    max_ciclos_activos  INT          NOT NULL DEFAULT 1,
    descripcion         TEXT,
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
```

El spec `specs/sprint-01/HU-002.spec.md` resuelve la unicidad en la capa de aplicación mediante la query DAL-P4:

```sql
SELECT COUNT(1) FROM plan WHERE LOWER(nombre) = LOWER(@Nombre);
```

esa validación BLL es correcta como **primera capa** (mensaje de error amigable → HTTP 422), pero deja una **condición de carrera TOCTOU** (time-of-check to time-of-use): dos peticiones concurrentes de SuperAdmin pueden ejecutar el `COUNT` (ambas ven 0), pasar la validación y ejecutar ambos `INSERT`, persistiendo dos planes con el mismo nombre. Esta carrera fue documentada explícitamente en el spec ("Decisión pendiente de ADR D1-ADR", línea 494).

Conforme a [DB-01], toda modificación al esquema de base de datos requiere **ADR aprobado antes de ejecutar la migración**. Jorge aprobó la creación de este ADR para resolver la contradicción entre el DDL y la unicidad requerida del catálogo, **siguiendo el mismo patrón ya aceptado en ADR-001** (`uq_tenant_nombre` para `tenant`, HU-001).

**Requerimientos trazables:** RF-005 (configurar plan por tenant con límites) · CA #1 HU-002 (catálogo de planes con nombre) · [DB-01] (ADR previo a migración) · [DB-02] (scripts SQL versionados en `db/migrations/`).

## Opciones consideradas

1. **Índice único funcional: `CREATE UNIQUE INDEX uq_plan_nombre ON plan (LOWER(nombre));`**
   Garantiza unicidad a nivel de base de datos con comparación **case-insensitive** ("Estándar" y "estándar" colisionan → `unique_violation` SQLSTATE 23505). No requiere modificar el DDL publicado; se aplica como migración versionada aditiva. El índice se mantiene por PostgreSQL: los `INSERT`/`UPDATE` que colisionen fallan con error de constraint en lugar de persistir datos inválidos. Costo: una entrada extra de índice por escritura en `plan` (volumen bajo: tabla raíz del SaaS, catálogo acotado de ≤ 10-15 planes). **Consistente con ADR-001**: misma solución, mismo nombre de patrón (`uq_plan_nombre` vs `uq_tenant_nombre`), misma captura de SQLSTATE 23505.

2. **Solo validación BLL existente (COUNT con LOWER) + aceptar el riesgo TOCTOU en concurrencia.**
   Mantiene la implementación actual del spec (DAL-P4) sin cambios de BD. Simple, sin migración, pero el catálogo de planes no queda garantizado en escenarios de concurrencia: dos SuperAdmins creando en paralelo pueden obtener dos planes con el mismo nombre, degradando el identificador natural del catálogo y dificultando futuras asignaciones/reportes. El requisito quedaría dependiente del timing, no de una invariante. **Rechazada**: es la misma razon por la que se rechazó la opción equivalente en ADR-001; la violación es un defecto de integridad de datos.

3. **Tabla de secuencia/contador global para nombres de planes.**
   Implementar una tabla auxiliar que centralice la asignación de nombres/identificadores y serializar las creaciones con aislamiento `SERIALIZABLE`. Elimina la carrera, pero introduce: una tabla nueva (modifica el modelo de datos más allá de lo necesario, requiere más ADR), complejidad de coordinación transaccional, y degradación de concurrencia en un punto único de contención. **Rechazada**: over-engineering frente a la garantía declarativa y nativa que ya ofrece PostgreSQL con un índice único (mismo criterio que ADR-001, opción 3).

## Decisión

Se adopta la **Opción 1**: índice único funcional sobre `LOWER(nombre)` en `plan`, idéntico al patrón de ADR-001.

- Se crea la migración versionada **`db/migrations/V002__unique_plan_nombre.sql`** (nomenclatura conforme a [DB-02]) con el siguiente contenido:

```sql
-- ============================================================
-- V002__unique_plan_nombre.sql
-- ADR-002: Garantizar unicidad case-insensitive de plan.nombre
-- a nivel de base de datos (CA #1 HU-002).
-- Autor: Jorge (Dicegsa) / @Arquitecto · Fecha: 2026-09-13
-- ============================================================

-- Índice único funcional: colisionan nombres que difieren solo
-- por mayúsculas/minúsculas (comportamiento deseado, ver spec DAL-P4).
CREATE UNIQUE INDEX uq_plan_nombre
    ON plan (LOWER(nombre));
```

- **Defensa en profundidad en dos capas:**
  1. **Capa 1 — BLL (se mantiene):** la validación `ExisteNombreAsync` (DAL-P4, `COUNT` con `LOWER`, con `ExcludeId` en actualización) se conserva tal cual en `PlanService.CrearAsync`/`ActualizarAsync` para devolver el mensaje de error amigable "Ya existe un plan con el nombre 'X'" → HTTP 422, sin depender de excepciones de BD.
  2. **Capa 2 — BD (nueva):** el índice único elimina la condición de carrera TOCTOU. Si una colisión concurrente logra pasar la capa 1, el `INSERT`/`UPDATE` de planes fallará con `unique_violation` (SQLSTATE 23505) y **no se persistirá el dato inválido**.

- **Nota de manejo de la violación de constraint (nota de implementación):** en `PlanService.CrearAsync` (y `ActualizarAsync`), dentro del `try/catch` alrededor de la operación de escritura transaccional, capturar `PostgresException` con `SqlState == "23505"` (`unique_violation`) y traducirla a `ValidacionException` ("Ya existe un plan con el nombre 'X'") → el `ExceptionMiddleware` la devuelve como HTTP 422. Importante: al detectarse la violación la transacción PostgreSQL queda en estado `aborted`; la BLL debe ejecutar `rollback` de la `IDbTransaction` **antes** de propagar la `ValidacionException`, para no reutilizar una transacción inválida ni enmascarar el error con un `InvalidOperationException` posterior. **Mismo patrón exacto que `TenantService` de HU-001** (ver ADR-001, líneas 52-56).

- **Nota de tabla global:** `plan` es una tabla GLOBAL del SaaS (sin `tenant_id`, excepción explícita a [DB-03] confirmada en `06_MODELO_DATOS.md`) → el índice no se combina con tenant; la unicidad es global por diseño (el catálogo de planes es único en la plataforma).

## Consecuencias

**Positivas:**
- Unicidad de `plan.nombre` garantizada a nivel de BD como invariante, eliminando la condición de carrera TOCTOU documentada en el spec (D1-ADR, línea 494).
- CA #1 de HU-002 queda satisfecho incluso bajo creación concurrente de planes por SuperAdmins.
- El mensaje amigable de la BLL se conserva (capa 1), por lo que el usuario final no ve errores de BD crudos.
- Costo de mantenimiento nulo: el índice lo mantiene PostgreSQL automáticamente.
- Máxima consistencia con el precedente aceptado: misma solución, misma migración aditiva, mismo manejo de 23505 que ADR-001 — reduce el coste cognitivo de revisión y de implementación.
- Alineado con la recomendación ya documentada en el spec (Decisión pendiente de ADR D1-ADR, línea 494, y Criterio de Done, línea 470).

**Trade-offs aceptados:**
- La violación de constraint residual en concurrencia debe capturarse como `23505` y traducirse a `ValidacionException` → HTTP 422 en la BLL, con rollback explícito de la transacción (costo de manejo acotado a 2 métodos: `CrearAsync` y `ActualizarAsync`).
- El índice agrega costo mínimo en `INSERT`/`UPDATE` de `plan` (escritura + rebalanceo de índice); aceptable por el volumen de la tabla raíz SaaS (catálogo acotado).
- Nombres que difieren solo por mayúsculas/minúsculas colisionan y son rechazados — comportamiento deseado y consistente con la comparación `LOWER` de DAL-P4 del spec.
- El DDL publicado en `06_MODELO_DATOS.md` (líneas 52-60) no refleja el índice; la migración `V002` es el artefacto que aplica el cambio en BD. **Acción de seguimiento para @Documenter:** actualizar `06_MODELO_DATOS.md` para reflejar el índice `uq_plan_nombre` (o referenciar este ADR) al cierre del Sprint 1, sin ejecutar ninguna migración adicional (misma acción que quedó pendiente para `uq_tenant_nombre` en ADR-001).
